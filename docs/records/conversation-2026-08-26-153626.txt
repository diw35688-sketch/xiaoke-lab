  ---
  先搞懂这堆代码在解决什么问题

  这是一个语音控制的化学实验助手。用户对着麦克风说"把温度设到 80
  度"，系统要经过三步：

  1. 识别：把声音变成文字（ASR，语音识别）；
  2. 理解：把文字交给大模型，判断说了啥、缺什么信息；
  3. 追问：如果缺信息（比如"加热多长时间没说"），系统要追问。

  难点在哪？ 用户嘴不停地说，系统处理也要时间，所以好几件事是同时发生的（专业术
  语叫"并发"）。比如：系统还在处理上一句话，用户已经又说了两句。这时候如果处理不
  好，会出现"记录写串了""同一个请求被处理两次""A 实验的答案填到 B 实验头上"这类
  bug。这五个审查点，就是在检查代码有没有堵住这些漏洞。

  ---
  审查点 1：并发安全（两把锁）

  白话直觉

  想象一个白板，多个人同时往上写字，字会叠在一起、写乱。锁就是"谁拿着笔谁写，别
  人先等着"。

  但锁不能乱用：如果一把大锁管所有事，会又慢又容易"互相等死"。这段代码用了两把锁
  ，各管一摊事，这是它的设计精髓。

  两把锁各自的职责

  ┌─────────────────┬──────────────────┬────────────────────────────────────┐
  │       锁        │       类型       │               管什么               │
  ├─────────────────┼──────────────────┼────────────────────────────────────┤
  │ _submission_loc │ 普通 Lock        │ "排队收单"：提交字典、序号、关闭标 │
  │ k               │                  │ 志                                 │
  ├─────────────────┼──────────────────┼────────────────────────────────────┤
  │ _state_lock     │ RLock（可重入锁  │ "理解状态"：协调器 + 上下文        │
  │                 │ ）               │                                    │
  └─────────────────┴──────────────────┴────────────────────────────────────┘

  真实代码在 web/experiment_runtime_sessions.py:75-76：

  self._state_lock = RLock()
  self._submission_lock = Lock()

  专业术语（含英文）

  - 锁（Lock / Mutex，互斥锁）：同一时刻只允许一个线程拿到它。拿到才能进"受保护
  区域"，出来再还锁。
  - 可重入锁（RLock / Reentrant 
  Lock）：同一个线程可以重复拿同一把锁，不会自己把自己卡死。看
  _run_operation（:167-172）——它拿 _state_lock 执行操作，而操作内部如果再调用
  active_clarifications()（也拿 _state_lock），普通 Lock 就会死锁，RLock
  不会。这是选 RLock 的原因。
  - 原子性（Atomicity）："不可分割"。幂等判断 +
  写入必须要么都发生、要么都不发生，中间不能被别人插队。
  - 竞态（Race 
  Condition）：两个线程同时读写同一数据，结果取决于谁先谁后，产生时好时坏的
  bug。
  - 死锁（Deadlock）：两个线程各拿一把锁、又等对方那把，谁都动不了。

  代码怎么体现"原子性"

  web/experiment_runtime_sessions.py:104 起，submit 把"检查是否已有 +
  写入新记录"放进同一个 with 块：

  with self._submission_lock:
      if self._closed:
          raise RuntimeError(...)
      existing = self._submissions.get(request.request_id)
      if existing is not None:
          ...          # 复用旧的，不重复干活
      ...
      self._submissions[request.request_id] = _SubmissionRecord(...)

  从"查有没有"到"写进去"全程锁着，别人插不进来，所以不会有竞态。

  反面例子

  如果"查有没有"和"写进去"不在同一个锁块里（查完放开锁，再写），两个线程同时提交
  同一个 request_id，会都发现"没有"、都写进去，造成重复执行。这种 bug
  有个专业名字叫 TOCTOU（Time-Of-Check to
  Time-Of-Use，"检查到使用之间的时间差"漏洞）。

  审查点 2：跨会话隔离

  白话直觉

  每个实验（每个"对话 + 实验会话"组合）有自己的独立记事本，互不串门。就像图书馆
  给每个读者一个小格子，你永远拿不到别人的笔记。

  专业术语

  - 隔离（Isolation）：不同会话的状态互不影响。
  - 键（Key）：(conversation_id, lab_session_id)
  这个元组，唯一标识一个会话，是字典的钥匙。

  真实代码

  web/experiment_runtime_sessions.py:210 用元组做键，:73-74
  每个会话建自己的一套状态：

  key = (conversation_id, lab_session_id)
  ...
  self._coordinator = ReplyCoordinator()          # 这个会话自己的"问题协调器"
  self._context = SessionContext(max_events=...)   # 这个会话自己的"短期记忆"

  测试专门验证了"状态不串门"——A 实验缺"时间"、B 实验缺"浓度"，B 说"10
  分钟"只会填 B 的问题，绝不会误填 A。

  反面例子

  如果全局共享一个 ReplyCoordinator，A、B
  两个实验的问题都堆在同一个列表里，"问题 2，加热 10 分钟"这句答复就可能把 A
  的问题 2 关掉——数据串门，用户得到错误答复，而且极难排查。

  审查点 3：依赖构造

  白话直觉

  建一个会话的成本极低——就是一个空列表 + 一个空队列，不用开线程、不用联网、不用
  读文件。所以"每个会话各建一份"很安全，不会拖慢系统。

  专业术语

  - 构造开销（Construction Cost）：创建对象时花了多少资源。
  - 纯内存对象（In-memory Object）：只在内存里，不碰磁盘/网络/线程。

  真实代码

  reply_coordinator.py:62-65 的 __init__ 只初始化一个列表和两个计数器：

  def __init__(self) -> None:
      self._clarifications: list[PendingClarification] = []
      self._next_display_number = 1
      self._current_clarification_id: str | None = None

  session_context.py:27-31 只初始化一个双端队列：

  self._items: deque[str] = deque(maxlen=max_events)

  反面例子

  如果在 ReplyCoordinator.__init__ 里就 ThreadPoolExecutor(...) 或连数据库，那么
  "每建一个会话"就开一条连接/一个线程，会话一多就资源耗尽。这段代码把唯一的
  ThreadPoolExecutor
  放在会话层（experiment_runtime_sessions.py:80-83，一个会话一个
  worker），而不是塞进协调器——这是"谁重谁轻"的清晰划分。

  审查点 4：合同验证规则

  白话直觉

  合同 = 一条死规矩：你说是"打字来的"，就不能偷偷夹带一份语音识别结果；你说是"语
  音来的"，就必须带上最终识别结果，而且识别出的字必须和你提交的字一模一样。这样
  后面接手的人无法造假、也无法把"文字"和"语音证据"拆开。

  三种来源

  来自 src/core/conversation_turn.py:28-31 的 InputSource：

  ┌──────────────────┬──────────────────────┐
  │       来源       │         含义         │
  ├──────────────────┼──────────────────────┤
  │ TEXT             │ 键盘打字             │
  ├──────────────────┼──────────────────────┤
  │ SINGLE_RECORDING │ 单段录音             │
  ├──────────────────┼──────────────────────┤
  │ CONTINUOUS_CALL  │ 连续通话（持续监听） │
  └──────────────────┴──────────────────────┘

  合同规则：文字来源 → 不能带 ASR；两种语音来源 → 必须带 final 且转写一致。

  真实代码

  src/core/experiment_turn_input.py:76-86：

  if self.input_source == InputSource.TEXT:
      if self.asr_result is not None:
          raise ValueError("文字输入不能携带 ASR 证据。")
      return

  if self.asr_result is None:
      raise ValueError("语音输入必须携带 ASR 证据。")
  if not self.asr_result.is_final:
      raise ValueError("语音输入必须携带最终 ASR 证据。")
  if self.raw_text != self.asr_result.asr_transcript:
      raise ValueError("语音 raw_text 必须与 ASR 忠实转写一致。")

  专业术语

  - 合同/契约（Contract）：数据进入系统前必须满足的约束。这里用
  __post_init__（dataclass
  创建后自动跑的校验钩子）在数据一进门就拦下不合法的东西。
  - 不变量（Invariant）：永远成立的条件（"文字永远不带 ASR"）。
  - 不可变对象（Immutable）：@dataclass(frozen=True)，创建后不能改，防止后面有人
  偷偷改字段。

  反面例子

  - 允许文字带 ASR →
  后面的适配层能给打字内容"伪造"一份语音识别记录，把没说过的话当成说过的。
  - 允许非 final 的 ASR →
  可能把"还在变化的中间识别结果"当成最终答案，导致转写和实际内容对不上。

  审查点 5：幂等 / 冲突 / 背压 / 关闭

  这是提交入口的四道闸门，像餐厅前台的四条规矩。真实代码都在 submit
  里（experiment_runtime_sessions.py:104-141）。

  ① 幂等（Idempotent）

  白话：同一个请求重复提交，不重复干活，直接返回第一次的
  Future（那个"正在做的任务的回执单"）。就像按两次电梯按钮，不会来两台电梯。

  代码 :108-118：查到 existing 且内容一致 → 直接 return 旧的（replayed=True）。

  反面：不幂等 → 网络重试会重复执行副作用（比如重复填字段、重复播报）。

  ② 冲突（Conflict）

  白话：同一个 request_id 但内容不一样 →
  报错。就像同一个订单号对应两笔不同的订单，说明有人搞错了。

  代码 :110-113：existing.request != request 时抛
  ExperimentSubmissionConflictError。

  术语：request_id 就是幂等键（Idempotency 
  Key）——系统靠它判断"这是不是同一个请求"。

  ③ 背压（Backpressure）

  白话：排队的人太多就拒绝新请求，不无限堆积。就像餐厅满了就停止接客，不让人无限
  排队。

  代码 :120-127：数一下还没跑完的任务，超过 max_pending_tasks（默认 4）就抛
  ExperimentSessionBackpressureError。

  反面：不背压 → 队列无限变长，内存爆炸。

  ④ 关闭（Close / Graceful Shutdown）

  白话：关了就拒绝新提交，但会把已经接的活干完。就像打烊了不接新客，但已经进店的
  客人服务完。

  代码 :105-106（关闭后 submit 抛错）+ :158-165（close 里 shutdown(wait=True)
  等任务跑完）。

  术语：优雅关闭（Graceful Shutdown）——不粗暴砍掉正在跑的任务，避免丢数据。

  ┌───────────────────────────────────┬───────┬─────────────────────────┐
  │               操作                │ 结果  │          含义           │
  ├───────────────────────────────────┼───────┼─────────────────────────┤

  ├───────────────────────────────────┼───────┼─────────────────────────┤
  │ RLock 释放两次                    │ 成功  │ 拿两次要还两次          │
  └───────────────────────────────────┴───────┴─────────────────────────┘

  下面回到项目代码讲透。这个问题其实藏着两个独立的问题，我拆开讲：先讲"为什么类
  型不同（Lock vs RLock）"，再讲"为什么要两把（而不是一把）"。

  ---
  前置直觉：锁是"认线程"的

  先补一个关键认知（这是理解 RLock 的全部基础）：

  - 线程 = 一条独立干活的"流水线"。程序里可以有好几条流水线同时跑。
  - 锁 = 一扇门闩。哪个线程进去了就把门闩上，别的线程进不来，等它出来才开门。

  关键点在"锁认人"：

  ▎ 一个线程拿到了锁、还没还锁之前，如果它自己又回头想拿同一把锁——
  ▎ - 普通 Lock 认不出"这是我啊"，会傻傻地等自己还锁 → 永远等不到 → 死锁；
  ▎ - RLock 认得出"这是我的人"，直接放行，只多记一笔"你还欠一次"。

  这就是上面实验里 False 和 True 的区别。RLock 的正式名是可重入锁（Reentrant 
  Lock）："重入" = 同一个线程再次进入同一把锁。它内部记着"持有者是谁 + 
  拿了几次"，同一个线程每 acquire 一次计数 +1，每 release 一次计数
  −1，计数归零才真正把门开给别人。

  ---
  为什么 _state_lock 必须是 RLock

  看 web/experiment_runtime_sessions.py:167-172 的 _run_operation：

  def _run_operation(self, operation, ...):
      with self._state_lock:                    # ① 工人线程先把锁拿住
          return operation(self._coordinator, self._context)   # ② 
  再跑"调用方传来的任意代码"

  这句话的关键是：operation 是调用方（别人）传进来的代码，它在 _state_lock
  还锁着的期间执行。而 context_snapshot()（:151）和
  active_clarifications()（:155）这两行，也各自 with self._state_lock:。

  所以一旦这段"别人的代码"（现在或将来某一天）回头调用这两个读取方法，就会发生：

  ▎ 同一个线程，在 _state_lock 还没还的时候，再次拿 _state_lock。

  这正是上面实验演示的场景。用普通 Lock 就死锁，用 RLock 就没事。

  一句话总结：_state_lock
  包住的是不可控的任意代码，你没法保证它不会回头再碰这把锁，所以必须用 RLock
  兜底。

  ---
  为什么 _submission_lock 用普通 Lock 就够

  看 submit（:104-141），_submission_lock 包住的是一段已知的、扁平的记账代码：

  with self._submission_lock:
      if self._closed: ...
      existing = self._submissions.get(request.request_id)  # 查字典
      ...
      pending_count = sum(...)                              # 数数
      ...
      self._submissions[request.request_id] = _SubmissionRecord(...)  # 写字典

  这几行就是"查字典、数数、写字典、发序号"，绝对不会再回头拿
  _submission_lock。所以"自己锁自己"在结构上不可能发生，普通 Lock 就够了。

  而且用普通 Lock 还有两个额外好处：

  1. 更便宜：Lock 没有"持有者 + 计数"这套逻辑，开销略小。
  2. 它是活的"文档"：程序员一看到 Lock 就知道"这段代码禁止嵌套拿锁"；一看到
  RLock 就知道"这段代码可能被同一线程反复进入"。类型本身就是注释。

  ---
  为什么是"两把锁"，而不是一把大锁

  这是第二个问题，专业术语叫锁的粒度（Lock Granularity）和职责分离。

  _submission_lock 管"收单记账"（提交字典、序号、关闭标志），_state_lock
  管"理解状态"（协调器、上下文）——这是互不相关的两摊事。如果硬用一把大锁全包了：

  1. 性能会变差：一个线程正在跑一个很慢的操作（占着锁），另一个线程只是想问一句"
  现在排队几个任务"（pending_count，读个数字而已），也要跟着干等。两摊本不该互相
  阻塞的事被强行串行化了。
  2. 死锁风险上升：搅在一起后，不同路径的"拿锁顺序"容易写乱（路径1先拿 A 再拿
  B，路径2先拿 B 再拿 A → 互相等对方）。

  分开之后，submit 只碰 _submission_lock，_run_operation 只碰
  _state_lock，没有任何一条代码路径会同时持有两把锁。这正是审查结论里写的"锁获取
  顺序一致，无死锁"——死锁在结构上就被排除了。

  ---
  反面例子：不知道这些会怎样

  - 把 _state_lock 换成普通 Lock：将来某天有人在 operation 里调了
  context_snapshot()，程序会静默卡死——死锁不抛异常，只是"不动了"，没有报错、没有
  堆栈，极难排查。
  - 只写一把大锁：pending_count() 这种读个数字的操作，也要等一个慢任务跑完才能返
  回，本该并发的活被白白串行化，系统变慢。
  - 反过来把 _submission_lock 也换成 RLock：不会错，但属于"没必要的开销 +
  丢了'这段代码不许嵌套'的语义提示"。

  ---
  写代码时的判断口诀

  以后你自己写并发代码，选 Lock 还是 RLock，只问自己一个问题：

  ▎ 这段 with 里要跑的代码，会不会（现在或将来）回头再拿同一把锁？
  ▎ - 会，或不确定（包的是别人传进来的回调/操作）→ 用 RLock
  ▎ - 不会（包的是自己写的、几行就完的已知代码）→ 用 Lock

  本项目就是活例子：_state_lock 包"别人传进来的 operation"→
  RLock；_submission_lock 包"自己写的记账代码"→ Lock。

  ---
  这里有个要跟你说清楚的边界（不夸大）：在当前代码和测试里，operation
  拿到的其实是原始的 coordinator/context
  对象，直接调它们的方法，并没有真正回头调 session 的 context_snapshot()。所以

  ③ submit 幂等判断只看 request、不看 operation

  核心：None 有双重含义，取决于字段的"可空合同"

  这是整件事的钥匙。同样一个 None，在不同字段里意思完全相反：

  ┌──────────────────────┬─────────────────────────────────────┬────────────┐
  │       字段声明       │             None 的含义             │  正确异常  │
  ├──────────────────────┼─────────────────────────────────────┼────────────┤
  │ raw_text:            │ None 是非法的，你传了错类型         │ TypeError  │
  │ str（必填）          │                                     │            │
  ├──────────────────────┼─────────────────────────────────────┼────────────┤
  │ intent_id: str |     │ None 是合法的"没提供"，但 VOICE     │ ValueError │
  │ None = None（可选）  │ 块又必须填，所以你忘了填            │            │
  └──────────────────────┴─────────────────────────────────────┴────────────┘

  所以两个函数"不一致"不是 bug，是服务了不同的可空合同（nullability contract）：

  - _require_non_blank（experiment_turn_input.py）只服务 str 必填字段——None
  不该出现，抛 TypeError 才对。
  - _require_id（conversation_turn.py）服务 str | None 可选字段——None
  表示"缺失"，抛 ValueError 才对。

  我当初把"三个函数看起来重复、该统一"当成一个语法层面的判断，没看到语法背后有语
  义层面的差异。一旦统一成"非字符串抛 TypeError"，就把"忘了填
  intent_id"这个值错误误判成类型错误了——测试立刻炸，因为它守的就是这个语义。

  专业术语（这次你能叫上名的）

  - TypeError vs ValueError：TypeError＝"参数类型不对"；ValueError＝"类型对，但
  值不可接受"。None 到底是哪种，取决于这个字段允不允许 None。
  - 可空性 / 可选类型（Optional，str | None）：字段声明 str | None
  表示"字符串或什么都没有"。有了它，None 就成了一种合法值。
  - 语法重复 vs 语义差异（syntactic duplication vs semantic 
  difference）：两段代码长得一样（语法重复），不一定意思一样（语义不同）。DRY
  原则只该消除"语义重复"，不该消除"碰巧长得像但含义不同"的代码。
  - 伪债 / 伪技术债（pseudo-debt）：看起来像欠债（重复、不一致），其实不是债。它
  里面藏着有意义的区分，硬"清理"会丢信息，属于净亏损。
