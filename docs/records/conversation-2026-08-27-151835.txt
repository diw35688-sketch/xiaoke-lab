  一、labSessionReady 是什么、为什么删

  它是 turn_client.js 里一段"搬家后回旧家拿东西"的过渡代码（第 20-33 行）：

  const initialLabSessionId = localStorage.getItem(LAB_SESSION_KEY);
  const labSessionReady = fetch('/record/history').then(...).then(data => {
      if (!initialLabSessionId && data.session_id) {

   session 拿回来存本地
      }

  })

  它现在干的活：页面第一次打开时，如果本地还没有 lab_session，就调旧接口
  /record/history，把后端之前管的"全局实验会话 id"拿回来存到 localStorage。

  为什么分 lab_session 后要删它：旧接口 /record/history 只能给你一个 session
  id（一个字符串）。但我们现在要"free 一个、每个方案一个"的多个 session。这个旧
  id 该归到 free 还是归到方案 A？分不清。而且旧 /record 系列接口本来就是要废弃的
  。所以"回旧家拿东西"这个动作失去意义，删掉，直接本地生成新的。

  二、"旧 lab_session 弃用"是什么后果

  现在 lab_session 存在 localStorage 一个固定格子里：

  lab-agent-lab-session-id  =  "lab-abc123"   （一个字符串）

  分 lab_session 后，改成存在一个柜子里，柜子有好几个格子：

  lab-agent-lab-sessions  =  {
    "free":        "lab-free-xxx",
    "protocol:A方案": "lab-proto-A-xxx",
    "protocol:B方案": "lab-proto-B-xxx"
  }

  所以旧的固定格子 lab-agent-lab-session-id 就不再被读了（弃用）。

  后果：如果你之前那个固定格子里已经有值（lab-abc123），改完后前端不再读它，改用
  柜子里的新值（本地重新生成）。而 lab-abc123 对应的待确认问题还在后端 SQLite
  里（挂在 (conversation_id, lab-abc123) 下），前端用新 id 查不到——变成"孤儿"。

  但这个后果 demo 阶段无所谓：① 数据量小；②
  反正是要重新做实验的，旧的待确认问题不接回来也不影响。所以"弃用旧格子"不是丢数
  据，只是"旧的引用不再用、旧数据躺在那不碍事"。

❯ 为什么一直强调服务器权威                                                      

● 好问题，这戳到了"为什么非要多一步让服务器发"的核心。我用大白话讲。

  一、"服务器权威"是什么

  先给这个词一个定义：谁持有"事实的真相"，谁就是权威。（英文叫
  server-authoritative，游戏/协作系统里的常用概念）

  在这个场景里，"事实"是：这次口述，到底对照方案的第几步在评价？

  这个事实的真相，在服务器端，不在浏览器端。因为步骤游标（domain.session()）是服
  务器进程里的全局变量，浏览器只是"看到"它，不是"拥有"它。

  二、为什么真相在服务器，不在前端

  看代码，这条链是：

  服务器 domain.session()  ← 全局唯一的"当前第几步"
          ↓
  domain.step_view(session())  ← 生成 step（当前步骤内容）
          ↓
  存进 SQLite 的 lab_record["step"]  ← 这次记录对照哪一步，以这个为准

  所以"这次口述按第 3 步还是第 4 步评价"，决定权在服务器的 
  domain.session()。前端没法替它决定，前端能做的只是"去问一下现在是第几步"。

  三、前端临时塞的问题在哪（反面例子）

  前端临时塞的步骤卡，是它提交前那一刻 fetch
  到的快照。这个快照可能和服务器处理时的状态脱节：

  - 你在第 3 步"称量磷酸盐"，口述"称了 3.6 克"。
  - 提交瞬间，服务器端的步骤游标其实已经到第 4
  步"溶解试剂"了（比如你之前点了步骤卡跳转，前端还没同步）。
  - 服务器按第 4 步评价 → 追问"溶解现象是什么？"
  - 但前端界面还显示"第 3 步：称量磷酸盐"。

  结果：你看到的是第 3 步，系统按第 4 步记录、按第 4 步追问。界面和系统脱节了。

  四、"服务器权威"要保证什么

  就是三样东西来自同一个源头，不脱节：

  界面上显示的步骤卡  ┐
  服务器评价用的步骤   ├─ 都来自 domain.session() 这一个真相
  SQLite 存的 step     ┘

  所以最终 Turn 里的 step_card，不是"随便给你看一眼"，而是**"这次记录确实对照了
  这一步"的凭证**——它能和 SQLite 里的 lab_record["step"] 对上，可追溯。

  五、诚实的边界

  在这个项目里，因为 domain.session()
  是单用户、单会话的全局单例，时序脱节的风险其实很小（你不可能在同一瞬间一边提交
  一边切步骤）。所以"服务器权威"在这里不是救急的 bug 修复，而是：

  1. 一致性原则——显示 = 评价 = 存储，同源，这是实验记录"可追溯"的地基；
  2. 为将来留余地——哪天真做多会话/并发，这个"快照可能过期"的坑会立刻咬人，现在就
  把"权威在服务器"钉死，将来不用返工。

  所以我不是在强调"服务器比前端厉害"，而是在强调"事实的真相只有一份，谁持有它，
  谁负责把它原样传下去，别让两边各说各话"。

  这样解释，你理解"服务器权威"为什么被我反复提了吗？

  难点 3：执行顺序要调。 现在 execution 在 analysis

  ## 不建议开旁路                                                               
                                                                                
  旁路可能短期少改几行，但会形成两套实验处理链：                                
                                                                                
  ```text                                                                       
  free     → UnifiedObserver → ClarificationExecutor                            
  protocol → 另一条规则链    → ClarificationExecutor                            
  ```                                                                           
                                                                                
  以后以下能力都要维护两份接入：                                                
                                                                                
  - 回答已有追问                                                                
  - 确认、暂缓、回看                                                            
  - 结束实验                                                                    
  - evidence persistence                                                        
  - ReplyCoordinator 编号与 revision                                            
  - session FIFO 和重试一致性                                                   
  - Web 展示和语音授权                                                          
                                                                                
  这比当前 30～40 行覆盖代码的长期代价更大，而且容易重新出现“旁路创建的问题无法 
  被统一链回答”的状态割裂。                                                     
                                                                                
  ## 推荐结构：主链内增加一个明确的 Policy 阶段                                 
                                                                                
  理想数据流是：                                                                
                                                                                
  ```text                                                                       
  UnifiedObserver                                                               
    │                                                                           
    ├─ 路由、控制命令、已有追问回答                                             
    └─ accepted_analysis：LLM 提取出的实验事实                                  
                       │                                                        
                       ▼                                                        
          ExperimentClarificationPolicy                                         
          ├─ free     → 沿用 LLM 追问语义                                       
          ├─ protocol → domain.evaluate(entities)                               
          └─ degraded → NO_ACTION                                               
                       │                                                        
                       ▼                                                        
              final ClarificationAction                                         
                       │                                                        
                       ▼                                                        
             ClarificationExecutor                                              
  ```                                                                           
                                                                                
  这个阶段可以先做成 `turn_processors.py`                                       
  附近的纯函数，不必立刻大重构，例如概念上：                                    
                                                                                
  ```python                                                                     
  resolved = resolve_experiment_policy(                                         
      experiment_context=turn.experiment_context,                               
      accepted=observation.accepted_analysis,                                   
      analysis=analysis,                                                        
      llm_action=observation.pending_action,                                    
  )                                                                             
  ```                                                                           
                                                                                
  返回一个小而完整的结果：                                                      
                                                                                
  ```python                                                                     
  @dataclass(frozen=True)                                                       
  class ResolvedExperimentPolicy:                                               
      missing_fields: tuple[str, ...]                                           
      deviations: tuple[...]                                                    
      follow_up_required: bool                                                  
      follow_up_question: str | None                                            
      pending_action: ClarificationAction | None                                
  ```                                                                           
                                                                                
  后面所有消费者只读这一个结果：                                                
                                                                                
  - `ClarificationExecutor.execute(resolved.pending_action)`                    
  - `lab_record["evaluation"]`                                                  
  - `_reply_text(...)`                                                          
  - clarification card                                                          
  - `created_clarification`                                                     
                                                                                
  这样不会发生“四处分别判断 protocol”的漂移。                                   
                                                                                
  ## 顺序确实应该调整                                                           
                                                                                
  建议顺序固定为：                                                              
                                                                                
  1. `observe()`                                                                
  2. 校验 observation                                                           
  3. `materialize_analysis()`                                                   
  4. 聚合 entities                                                              
  5. 解析最终 policy                                                            
  6. 执行最终 `pending_action`                                                  
  7. 构造 lab record                                                            
  8. 构造 reply/card/voice                                                      
  9. 保存状态                                                                   
                                                                                
  这不是为了迁就某个补丁，而是在恢复正确的因果顺序：                            
                                                                                
  > 先得到事实，后做策略判断，最后执行状态变更。                                
                                                                                
  当前在 analysis 物化前执行 action，本身就说明 `pending_action` 过早固化了。   
                                                                                
  ## A 的两个方向都必须覆盖                                                     
                                                                                
  否则“确定性权威”只是名义上的。                                                
                                                                                
  | LLM 初始动作 | protocol 评价 | 最终动作 |                                   
  |---|---|---|                                                                 
  | CREATE | 不缺字段 | NO_ACTION |                                             
  | NO_ACTION | 缺字段 | CREATE |                                               
  | CREATE | 缺字段 | CREATE，但替换 question 和 missing_fields |               
  | NO_ACTION | 不缺字段 | NO_ACTION |                                          
                                                                                
  其中 `NO_ACTION → CREATE` 不需要复制一堆身份拼装代码到                        
  processor。最好给核心对象增加一个明确构造入口，例如：                         
                                                                                
  ```python                                                                     
  ClarificationAction.from_protocol_evaluation(                                 
      accepted,                                                                 
      protocol_eval,                                                            
  )                                                                             
  ```                                                                           
                                                                                
  这个 factory 负责：                                                           
                                                                                
  - 从 `accepted` 继承 request/session/segment/transcript 身份；                
  - 设置正确的 `PREPARE_CREATE`；                                               
  - 使用确定性的 question、missing_fields；                                     
  - 保留 evidence persistence 约束。                                            
                                                                                
  这样 frozen dataclass                                                         
  不是问题，反而能保证动作不会被半修改。`dataclasses.replace()` 可以用于        
  `CREATE → CREATE`，但从 `NO_ACTION → CREATE` 时字段语义变化太多，显式 factory 
   更安全。                                                                     
                                                                                
  ## DEGRADED NOTE 的边界                                                       
                                                                                
  你的判断正确：

● 要分两条路看，答案不一样。

  路 1：显式"回答追问"——已经可以分多次

  现状的机制是：你缺字段 → 系统追问 → 你显式回答 → 
  把缺的字段填上。这一步是累计的。

  具体例子（第 5 步 must_record = ["observation", "condition"]）：

  1. 你口述"倒转混匀，溶液透明"→ 提取 observation=透明 → 确定性评价发现缺
  condition → 追问"保存条件是什么？"（问题 1，缺 condition）
  2. 你回答 "问题 1 是室温保存"（或"室温保存"被识别为对问题 1 的回答）→
  coordinator.supply_fields 把 condition 填上 → 问题 1 resolved ✅

  这条路是通的，而且支持"一个追问分几次回答、每次填一部分"——因为 missing_fields
  是一个列表，supply_fields 一次填几个都行，填空了才 resolved。

  但有两个前提，都是未经验证的：

  - 你必须显式表达"我在回答问题 N"（说"问题 1 是
  XX"，或者说"是/对"针对当前问题）。你不能只说"室温保存"——那会被 LLM
  当成一条新的实验记录。
  - 依赖 LLM 准确判断"这句话是回答，不是新记录"。

  路 2：自然"持续口述"——还不支持，这就是累计语义的缺口

  如果你不显式回答追问，而是继续自然口述新的实验事实：

  1. 口述"倒转混匀，溶液透明"→ 缺 condition → 追问"保存条件？"

  - "分多次显式回答追问"：已经可以（路 1）。
