  一、方法论：怎么从一堆代码里理清数据流

  这是你要练进简历的能力，我给它起个正式名字，再拆成 5
  步。核心心法一句话：不要"读完所有文件"，要"追一条请求"。

  第 0 步：心态——别做"全量阅读"，做"入口驱动"

  - 白话：进一座陌生城市，你不会背整张地图，你会先找到地铁站（入口），坐一趟地铁
  把一条线走通，再逐步扩展。看代码同理。
  - 专业术语：这叫 入口驱动探索（entry-point-driven exploration），对立面是
  全量阅读（full-file reading）。
  - 反面例子：src/core/ 有 26 个文件、web/ 有 20+
  个文件。如果按字母顺序挨个读，你读三小时也答不出"用户说一句话，到底经过哪些代
  码"。因为大部分文件只在某条特定路径上跑，甚至有的是死代码。

  第 1 步：找入口（entry point）

  - 白话：每个能跑的程序一定有个"起点"。web 的起点就是
  app.py——框架从这启动、在这注册所有 URL。
  - 专业术语：入口文件 / 组合根（composition root）。FastAPI 里就是 app = 
  FastAPI(...) 那个文件。
  - 项目体现：web/app.py 第 24 行 app = FastAPI(...)，第 145-155 行
  app.include_router(...) 挂了 11 个路由。
  - 关键技巧：路由表就是"入口地图"。@app.route('/xxx') 或 include_router 一行就
  是一扇门。先扫一遍路由，你就知道这个系统对外提供了哪些"门"，再决定进哪扇。

  第 2 步：追一条请求（trace one request）

  - 白话：别问"这项目有哪些功能"，要问"用户点一下/说一句话，代码按什么顺序跑过哪
  些函数"。挑最典型的一条动作，从头追到尾。
  - 专业术语：请求追踪 / 调用链（call path）。
  - 项目体现：web 最典型的动作是"用户语音口述做实验"→ 我挑了 POST /record
  追，追出下面一整条链。
  - 反面例子：如果你先从 web/tools/calculator.py 这种叶子文件读起，你会读到一个
  孤立的四则运算函数，完全不知道它被谁、在什么时机调用。

  第 3 步：认数据合同（data contract）

  - 白话：模块之间"交接"的东西长什么样——是一个 dict？一个 dataclass？JSON
  字段名叫什么？合同就是数据流的"节点"，把节点连起来就是数据流图。
  - 专业术语：数据结构 / 契约（contract）。你 src 侧全是 frozen=True
  dataclass（ASRResult、UnifiedUnderstandingResult），web 侧靠
  domain.py、llm_bridge.py 里的字典结构交接。
  - 反面例子：如果只看函数名不看它返回什么结构，你会把"返回 {"events": 
  [...]}"和"返回 {"answer": "..."}"两个不同东西混成一团，图就画断了。

  第 4 步：分"大脑"和"手"（brain vs hands）

  - 白话：代码分两类——"想"的（判断意图、抽实体、调
  LLM）和**"做"的**（写库、改状态、返回页面）。理数据流时先把这两类分开，会发现"
  想"的那条链短而集中，"做"的链多但简单。
  - 专业术语：纯逻辑 vs 副作用（pure logic vs side effects），也就是理解层 vs 
  执行层。
  - 项目体现：你那份迁移计划"契约
  6"已经点破了这句话：统一链管理解、工具管执行。这是整个项目最值钱的一条边界线。

  第 5 步：画图验证（draw to verify）

  -
  白话：把追出的链路画成箭头图。画不出来、箭头断掉的地方，就是你还没理清的地方。
   图不是"结果"，图是"检验理解对不对"的工具。
  - 专业术语：数据流图（data flow diagram）。
  - 项目体现：最终产物就是那张"声音→ASR→理解→执行→呈现"的图，也是你要放简历的东
  西。

  ▎ 确认点：这 5 步里，"追一条请求"（第 2 步）是最关键的，其余四步都是在给它铺路
  ▎ 和收尾。这里有没有不清楚的？没有的话我接着回放我在 web 上是怎么用这 5 步的。

  1.1 工具调用：OpenAI 的 function calling

  - 白话：LLM 本身只能"吐字"，不能"干活"。你告诉它"有一堆工具可以用，每个工具叫
  什么、要什么参数"，它就在回复里不再吐普通文字，而是吐一个 
  JSON：我要调用某个工具，参数是这些。你的代码把这个 JSON
  接住、真正去执行、再把执行结果塞回给它，它再决定下一步。
  - 专业术语：这叫 function calling / tool calling，多轮循环叫 agentic 
  loop（代理循环）。
  - 项目体现：web/agent/core.py 的 run_agent（第 78-101
  行）就是这段循环，我把它拆给你看：

  # core.py 第 82-94 行（简化）
  for _ in range(6):                                        # 最多转 6 轮
      response = client.chat.completions.create(
          model=..., messages=messages, tools=TOOLS)         # 
  关键：把工具清单传给模型
      assistant = response.choices[0].message
      calls = assistant.tool_calls or []                     # 
  模型吐出的"要调哪个工具+参数"
      if not calls:
          return assistant.content                            # 没工具要调了 → 
  直接返回文字
      messages.append(assistant)
      for call in calls:
          result = run_tool(call.function.name,              # 真正执行工具
                            json.loads(call.function.arguments),
  conversation_id)
          messages.append({"role":"tool", "tool_call_id":call.id,
                           "content":json.dumps(result)})     # 
  结果塞回对话，再进下一轮

  一句话：工具清单是"菜单"，tool_calls 是模型点菜，run_tool 
  是后厨做菜，结果回桌让模型继续点。

  深挖二：后端产出怎么到前端

  有四条通道，别混：

  通道 A：普通 JSON（请求→响应）

  - 白话：前端 fetch 一个地址，后端返回一坨 JSON，前端拿字段渲染。
  - /record 这条：返回 {item, messages}。messages 是 WebRenderer
  渲染好的数组，每条长这样：{kind, screen_target, priority, text, voice_text}。
  - 前端接法（voice_asr.js 第 156-158 行）：
  if (window.labRender) window.labRender(d);              // 画实体 + 回执
  if (window.labSpeakMessages) window.labSpeakMessages(d.messages || []); // 念
    lab_panel.js 的 labRender 按 kind

  labSpeakMessages 只念 voice_text。
  - 关键契约（你迁移计划的契约 4/5）：前端只按 kind/screen_target 上样式、只念 
  text/voice_text，判断"要不要问"、措辞都在后端。

  通道 B：SSE 流式（Server-Sent Events）

  - 白话：后端不一次性返回，而是像水管一样持续往出挤字，前端边收边显示——打字机效
  果。
  - 专业术语：SSE（Server-Sent Events，服务器推送事件），单向流。
  - 项目体现：api/chat.py 的 chat_stream 返回
  StreamingResponse(media_type="text/event-stream")，逐段 yield "data: 
  {...}\n\n"。agent/core.py 的 stream_agent 用两个特殊标记夹带信息：
    - [[LABTHINK]] → 推理模型的心路历程，前端渲染成可折叠的"思考"行
    - [[LABCARD]] → 工具卡片的 JSON（调用前 pending、调用后 done）

  通道 C：后台任务 + 轮询

  - 白话：有些请求（"帮我创建明天的实验"）要跑很久，不能让用户干等，就先回一句"
  我交给后台了"，让用户继续聊，跑完再通知。
  - 项目体现：realtime/routing.py 的 requires_background_task()
  用正则判断——闲聊走实时、排期/查询/创建走后台。走后台时
  task_manager.submit()（task_manager.py 第 24-27 行）扔进 ThreadPoolExecutor（2
   线程），前端轮询 /tasks 查状态。

  通道 D：TTS（后端文字 → 前端声音）

  - 白话：前端把要念的文字 POST 给 /tts，后端合成音频，前端拿回音频 blob 播放。
  - 项目体现：local_tts.js 的 window.speak(text)：fetch('/tts', {body:{text}}) →
   拿 blob → new Audio(url).play()。带队列 + 打断（jobId 递增 + AbortController
  + stopSpeech），/tts 挂了就退回浏览器内置 speechSynthesis（browserFallback，第
   40-48 行）。

  ▎ 一个小技巧帮你记：问"数据怎么从前端到后端"就看 fetch 的 method 和 
  ▎ body；问"怎么从后端回前端"就看是 return（一次性 JSON）还是 
  ▎ StreamingResponse（流）还是 task_manager（异步）。

  深挖三：为什么前端入口散落各处

  - 白话：现代前端（React/Vue）会用 webpack/vite 把几十个文件打包成一个

  - 专业术语：IIFE（立即执行函数） 隔离作用域，无模块化（no bundler / no ES 
  modules）。
  - 项目体现：voice_asr.js、lab_panel.js、composer.js 每个都是 (function(){ ... 
  })()，各自 document.createElement('div') 创建自己的 DOM，自己 appendChild 到
