## 0. 结论先行

这六天把系统往"**坏掉之后也不丢数据、且能定位为什么坏**"的方向推了一步。这一步在 **demo 里几乎零价值**，在 **真实提供服务时是入场券**。

按性质切成三堆账，账目才清楚：

| 性质 | 内容 | 判断 |
|---|---|---|
| **真新价值**（旧路没有、服务必须有） | 单一决策点、证据先落盘、会话上下文不断链、可测量语料、风险/权限脚手架、能拦截数据丢失的验收流程 | 净收益，共 6 项（§3.1） |
| **还债**（旧路已有、迁移中弄丢又捡回） | 会话上下文、命令处理（review/defer/answer/confirm） | 非新价值，是修自己挖的坑（§3.2） |
| **倒退**（旧路有、至今没恢复、且未登记） | 非阻塞录音（后台线程→主线程）、LLM 降级的人话提示 | 净损失，共 2 项（§3.3） |

**一句话**：方向对（正确性要先焊死），但把"删双轨"做成了"删旧路的一切"，有两样跟"调用几次 LLM、有没有 flag"无关的独立能力被一起埋了，且至今没进待办。

## 2. 前提澄清：必须先纠正的两个错误事实

这两个错误出现在既有台账和架构文档中，若不纠正，会把本次重构的价值系统性高估。以下结论均来自代码。

### 2.1 "旧路两次 LLM 调用"不成立——"减半"卖点是假的

**错误说法**（架构文档 §4.2、台账"病1"/第4天）：旧路每段调两次 LLM（`analyze_segment → summarize`），新路一次，所以"省一半 token、省一次往返"。

**代码事实**：

- `src/core/segment_processor.py:100-108`（旧路主编排 `SegmentProcessor.process()`）**只调用 `analyze_segment` 一次**；
- `summarize`（`src/llm/processor.py:137`）只在**测试**和**脚本**（`scripts/test_deepseek_llm.py`、`scripts/compare_intent_architectures.py`）里出现，**从未被 `main.py` 调用**。

**结论**：旧路主流程每段本来就是 1 次 LLM 调用。"两次调用"是把"每段分析（1 次）"和"会话总结（另一时机、且未接入主循环）"混写成"每段 2 次"。因此"延迟减半 / token 减半"**不能作为本次重构的价值主张**。

> 附带影响：`INTENT-02-ARCH-01` 里记录的"独立两次 5.809/5.621s vs 统一一次冷缓存 10.980s"对比，比较对象也不是同一件事——独立方案是"意图分类 + 实验理解"两条独立链，统一方案是"分类+结构化"合为一次。这对比成立，但不能导出"新路比旧路快"。

### 2.2 "后台→主线程"不是"等价"，是丢掉了"非阻塞录音"

**错误说法**（架构文档 §5.3 SUBMIT-01 行、台账迁移表）：`SegmentProcessor 五步（后台线程）→ main 直接编排（主线程）✅ 等价`。

**代码事实**：

- 旧路用 `SessionProcessingQueue` 在后台单线程跑 LLM，主线程录完音**立即继续录下一段**（`LEARNING_REVIEW` §20–21 真机验收过"连续 5 段不卡麦"）；
- 新路 `src/main.py:327-443` 的 `while True` 循环内，`recognize_one_segment → observer.observe（调 LLM）→ asr_store.append → event_store.append → executor.execute` **全部同步**；
- grep 整个 `main.py`：无 `Thread` / `queue` / `Future` / 线程池（唯一的 `executor` 是 `ClarificationExecutor`，业务执行器，不是线程池）。

**结论**：非阻塞录音（吞吐能力）**丢失了**，不是"等价"。这是本次重构最严重的净倒退，且**全项目没有任何待办登记要恢复它**（详见 §3.3）。

## 3. 三堆账

### 3.1 真新价值（6 项工程硬资产）

这些是旧路没有、真实服务必须有、且已真机验收的能力。

| # | 价值 | 说明 | 证据 |
|---|---|---|---|
| 1 | **单一决策点，消除"双脑打架"** | 旧路命令识别（`InteractionCommandParser`）与实验理解（`ExperimentLLMProcessor`）是两处分开的逻辑，靠三道门卫 + `_new_chain_handled_answer` 补丁协调，存在"同句两判"裂缝。新路收进 `UnifiedUnderstandingRouter.route()` 一个入口 | 架构 §5.3 COMMAND-01 行 |
| 2 | **证据顺序硬约束：先落盘，再改内存状态** | `prepare → persist → commit`：ASR 原文先写 → 事件再写 → 最后才改内存。崩溃发生在任意一刻，原始事实都已在磁盘上。这是"丢一条就是事故"型产品的命根子 | `main.py:393-443`；`MAIN-EVIDENCE-COMMIT-01` |
| 3 | **会话上下文不断链** | 第二段口述的 prompt 里确实带着第一段事件（真机 `prompt_tokens 959→971`）。多轮服务若模型看不见上文，"补充上一句"永远接不住 | `MAIN-SESSION-CONTEXT-01`；`main.py:373-383` |
| 4 | **可测量体系（ASR 鲁棒性语料）** | 28→31 段噪声口述、spoken/observed 双文本、deterministic/real 双模式评测，21/28 一致、7 缺口逐条登记。"ASR 有时错"变成"我知道它具体在 7 种方式上错" | `INTENT-02-ASR-ROBUSTNESS-01` |
| 5 | **风险分层 + 最小权限脚手架** | `IntentPolicy` / `DispatchPlan` / `DispatchPermission`，纯规划器与副作用执行器分离。这是给后续"安全警示、查询、RAG"预留的承重墙 | `intent_policy.py`；`unified_dispatch.py` |
| 6 | **能拦截数据丢失的验收流程（最值钱）** | `SUBMIT-01` 首轮真机复验抓出 `event_store` 未传参 → **整场事件全丢** 的 bug。这 bug 不是自动测试抓的，是"改主流程必做真机复验"这条纪律抓的。对服务而言，这条拦截网比任何一行代码都值钱 | 任务清单 §3.1B 行 25 |

### 3.2 还债（非新价值，是修迁移挖的坑）

这些能力**旧路本来就有**，在迁移到新链的过程中被弄丢/弄降级，这六天里又捡回来或部分捡回。它们**不算新价值**，只算"把欠的还上"。

- 会话上下文接线（`MAIN-SESSION-CONTEXT-01`）——旧 `SegmentProcessor` 第 5 步本就有"事件落盘后更新上下文"；
- 命令处理 review/defer/answer/confirm 的迁移（`CLEANUP-COMMAND-01`）——三道旧门卫本就有这四种能力。

> 区分标准：判断一项工作是否"新价值"，看它**相对旧路的稳定形态是否新增了能力**。迁移期间丢失又恢复的，是还债。

### 3.3 倒退（旧路有、至今没恢复、且未登记）——本次重构的净损失

| # | 丢失的能力 | 现状 | 是否已登记待办 |
|---|---|---|---|
| 1 | **非阻塞录音**（说完一句麦继续听，LLM 后台算） | 主线程同步，LLM 处理时麦克风关闭，用户说完要干等（热缓存约 2.6s、冷缓存约 10.98s） | **否。全项目无任何任务要恢复它** |
| 2 | **LLM 降级的人话提示**（"原始记录已保存，结构化处理暂时不可用"） | LLM 失败时无面向用户提示，只有开发日志"[统一链]目标=degraded_note…" | 否（架构 §5.4 记为"丢失"，但未转成待办） |

**为什么这两项严重**：

- 第 1 项是**吞吐/节奏**能力的净损失，且被架构文档 §5.3 误标为"等价"（"无后台任务，无需等待"被写成了好事）。做实验的人手是湿的，不会为每句话干等 2.6 秒。
- 第 2 项是**信任**损失：用户看到 `目标=degraded_note` 会以为系统崩了，而实际上他的记录已经安全保存。"丢失"和"降级"性质不同——降级是话术丑，丢失是功能整个没了。

## 4. 一个设计死结：DEFER 的 `reversible` 字段没接线

这是本次重构里**设计意图与实现自相矛盾**的一处，也是 GAPS 里"按编号暂缓漏识别"（A/B）的**真正根因**，不是"schema 缺一个枚举值"。

**矛盾的双方**：

- 初心（`src/core/unified_prompts.py:20-22`）：用户可能用非标准自然表达传控制意图（如"我先跳过"），LLM 要能接住——这是"LLM 兜底"。
- 策略（`src/core/intent_policy.py:162-181`）：DEFER 是 MEDIUM，证据来自 LLM 候选（`LLM_CANDIDATE`）时直接 `DO_NOT_EXECUTE`（弃权）——这是"LLM 不可信"。

**死结**：`IntentPolicy` 里写了 `reversible=True`（`intent_policy.py:87`），本意是"可逆操作允许语义容错"；但 `IntentPolicyEvaluator.evaluate()` 的实际逻辑**没有按 `reversible` 放行**，而是按 `evidence` 来源一刀切：`LLM_CANDIDATE + MEDIUM → DO_NOT_EXECUTE`。于是：

```
自然表达的命令（"暂缓问题一""这个稍后再说"）
   ├─ 精确规则接不住（前缀+后缀只匹配"X先跳过"）
   └─ LLM 能识别，但被风险策略弃权
        → 结果：自然表达命令落进真空，谁都不接
```

**后果**：新路只在"实验内容"上兑现了"LLM 兜底"的初心，在"命令"上恰恰没有兑现——而命令，恰恰是模糊口述最常出错的地方。

**这不是"太保守"，是"字段写了但逻辑没接线"**：`reversible` 字段是死代码，设计意图（可逆→可语义容错）没有被实现。要么把 `reversible=True` 接上（让 LLM 候选走"上下文校验"而非"弃权"），要么承认命令侧不信任 LLM、只靠精确规则——两者必须选一个，不能既写"LLM 兜底"又写"LLM 弃权"。

## 5. 一句对用户说谎的文案（次要但必须记）

`src/main.py:320-321` 会话开始打印：

```python
print("现在可以连续口述，无需等待 LLM 处理完成。")
```

这是**旧后台线程时代的欢迎语**。删后台线程改同步后，这句承诺与 `main.py:327-443` 的实际行为矛盾：用户被告知"不用等"，实际每段都要等 LLM 算完才重新开麦。

**定性**：不是崩溃、不是数据错，所以"硬问题判据"拦不住它；但它属于"系统对用户的承诺与行为不一致"，是信任事故，应在恢复非阻塞（§3.3 第 1 项）时一并修复——若决定保留同步，则这句话必须改。

## 6. demo 与工程：同一份代码的两张卷子

这六天 95% 的精力投在"工程属性"上，而 demo 评委只看"demo 属性"。这是"感觉啥也没干"的根因。

| 维度 | demo 考什么 | 工程考什么 | 本六天投入在哪 |
|---|---|---|---|
| 目标 | 台上 3 分钟固定输入好看 | 连续运行任意输入不崩、不丢、可维护 | 工程 |
| 失败 | 尽量别崩，可重来 | 数据一条不能丢，能查"刚才发生了什么" | 工程 |
| 维护 | 一个人改得动 | 团队并行改，加功能不牵一发动全身 | 工程 |
| 改进 | 凭感觉调参 | 有基线，改完知道变好还是变坏 | 工程 |

**一句话**：demo 是"造一辆能开一圈的车"；工程是"造一辆能跑 10 万公里、刹车不失灵、故障能定位、别人能接手修的车"。这六天基本全在"刹车、仪表盘、维修手册"上，而 demo 评委只盯着"开一圈顺不顺、座舱漂不漂亮"。

**对本项目的意义**：项目定位是"面向高校实验场景的具身语音智能体"（要真用），所以补工程是对的；但必须清楚两张卷子都要答——demo 那张还缺"非阻塞"和"干净输出"（§3.3 那两项，恰恰是本六天弄坏的）。

## 8. 一句话总结

> 这六天做的是**正确性优先的重构（correctness-first refactor）**，方向对——正确性是服务的地基，要早打、打深。但犯了一个新手典型错误：**把"删双轨"当成了"删旧路的一切"**，将"非阻塞"和"干净输出"两样独立能力当成废料一起埋了，其中"非阻塞"至今没进待办。六天的净价值是 6 项工程硬资产 + 一条能拦数据丢失的验收流程；净损失是 2 项用户能力 + 1 个未接线的 `reversible` 字段 + 1 句谎话文案。
