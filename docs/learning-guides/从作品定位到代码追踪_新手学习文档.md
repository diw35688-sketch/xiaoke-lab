# 从作品定位到代码追踪：「小科」新手学习文档

> 文档边界：本文只整理本次对话中已讨论的内容，包括作品定位、作品背景、要解决的问题，以及如何从代码中追踪真实功能。未经代码闭环或验收证据支持的能力，不在本文中写成已完成事实。

## 一、我们先在定位什么

### 1. 白话理解

「小科」不只是一个把语音变成文字的工具，也不只是一个会聊天的大模型页面。

它想做的事是：

- 实验前，帮助管理方案、计算参数和组织资料；
- 实验中，让实验人员直接口述操作，系统帮忙记录、追问和核对流程；
- 实验后，让方案、记录和经验可以被回溯、复用和交流。

其中，最有辨识度的不是「页面多」或「工具多」，而是实验进行中的语音交互主线：

```text
听到实验口述
→ 理解实验事实
→ 形成结构化记录
→ 发现缺少信息
→ 主动追问
→ 核对方案执行
→ 真正保存结果
```

### 2. 专业设计

当前确认的总体定位是：

> 「小科」是一款面向实验全流程的智能体，重点解决实验过程中的语音记录与流程辅助问题，并集成方案管理、专业计算、资料管理和实验交流等功能。

作品名称确认为：

> **「小科」——实验语音交互与流程辅助智能体**

这里使用「语音交互」，而不只是「语音记录」，因为实验过程还包括语音追问、回答、流程控制和语音反馈。但不使用「语音驱动的全流程」，因为目前语音能力的主要实现和验证仍集中在实验进行阶段。

### 3. 为什么不叫「具身智能」

白话说，一个系统会听、会说、有虚拟形象，并不自动等于具身智能。

具身智能（Embodied Intelligence）通常强调：

```text
感知物理环境
→ 理解环境状态
→ 作出决策
→ 控制身体或物理设备
→ 再次感知行动结果
```

当前「小科」的主要闭环依然发生在语音、软件工具和数据之间，尚未形成对机械臂、实验仪器或传感器的物理执行闭环。因此，使用「实验语音交互与流程辅助智能体」更准确。

## 二、作品背景和「解决的问题」怎么区分

### 1. 白话理解

可以把一篇作品简介想成一次问诊：

- **作品背景**：为什么这件事值得做？
- **解决的问题**：我们具体要改变哪些矛盾？
- **核心功能**：系统具体怎样解决？

举例：

```text
背景：实验工作操作连续、信息专业，需要可追溯。
问题：实验人员戴手套时，如何不打断操作又不丢记录？
功能：单次录音或连续通话 → ASR → 结构化记录 → 持久化。
```

如果背景里已经把每个痛点、解决方法和功能都写完，后面一定会重复。所以我们后来把背景收缩为宏观动机，把具体矛盾集中放进「解决的问题」。

### 2. 专业写作设计

#### 作品背景的职责

背景只保留四层逻辑：

1. 实验是贯穿前、中、后的多阶段工作；
2. 大模型和语音交互带来了新的智能化机会；
3. 实验工作具有连续操作、专业信息、复杂状态和可追溯要求；
4. 因此，需要让智能体真正进入实验流程。

#### 「小科」具体解决的六类问题

1. 实验准备信息分散、工具入口不统一；
2. 实验操作与过程记录难以同步；
3. 自然口述难以直接形成完整、可靠的实验记录；
4. 实验方案与实际执行缺少持续核对；
5. 大模型生成能力与实验任务的可靠执行之间存在差距；
6. 实验资料、记录和经验缺少连续沉淀与协作渠道。

详细定稿见 `docs/learning-guides/作品简介_打磨稿.md`。

## 三、为什么不能凭页面和 README 直接写「核心功能」

### 1. 白话理解

页面上有一个按钮，只能证明「有一扇门」，不能证明门后的路已经修通。

例如，看到「语音记录」按钮，仍然要继续问：

1. 它把音频发给了哪个接口？
2. 接口有没有注册到真实服务？
3. 谁调用 ASR？
4. 谁区分聊天和实验记录？
5. 谁检查缺少参数？
6. 结果有没有真正写入数据库？
7. 有哪些测试和真实验收证据？

如果只看到前两步，就写「已实现可靠语音实验记录」，就容易把半成品当成完整功能。

### 2. 专业设计：端到端可追溯链

一项功能至少应该追踪五层：

```text
用户入口
→ API 接口
→ 应用服务
→ 领域逻辑
→ 状态或数据写入
→ 测试与真实验收
```

这种方法可以称为：

- **End-to-End Traceability**：端到端可追溯性；
- **Call Chain Tracing**：调用链追踪；
- **Evidence Boundary**：证据边界，即明确一项证据能证明和不能证明什么。

## 四、完整示范：怎样追踪「实验语音记录」

### 第 1 步：把抽象功能改写为具体用户动作

不要问：

> 「语音功能在哪里？」

而要问：

> 「用户录完一段实验语音后，系统怎样把它变成实验记录？」

抽象问题无法直接对应代码；具体动作可以提供搜索词，例如 `MediaRecorder`、`FormData`、`submitAudio` 或接口路径。

### 第 2 步：从前端搜索音频提交者

在 PowerShell 中执行：

```powershell
rg -n "/turn/audio|submitAudio" web\frontend
```

可以找到三个音频生产入口：

- `web/frontend/voice_asr.js`：单次录音；
- `web/frontend/mobile.js`：手机页录音；
- `web/frontend/phone_call.js`：连续通话录音。

它们共同调用：

```javascript
window.turnClient.submitAudio(...)
```

再搜索 `submitAudio` 的定义，可以进入 `web/frontend/turn_client.js`，并看到：

```javascript
fetch('/turn/audio', ...)
```

于是得到前端链：

```text
voice_asr.js / mobile.js / phone_call.js
→ turn_client.submitAudio()
→ POST /turn/audio
```

### 第 3 步：从接口字符串找后端路由

搜索：

```powershell
rg -n 'prefix="/turn"|@router.post\("/audio"\)' web
```

在 `web/api/turn.py` 中可以看到：

```python
router = APIRouter(prefix="/turn")

@router.post("/audio")
async def turn_audio(...):
    ...
```

前缀 `/turn` 与子路径 `/audio` 合起来，才是完整的 `POST /turn/audio`。

### 第 4 步：确认路由是否真正注册

定义了路由不代表运行时一定加载。继续搜索 `turn_router`：

```powershell
rg -n "turn_router" web
```

在 `web/app.py` 中可以看到：

```python
from api.turn import router as turn_router
...
app.include_router(turn_router)
```

这才能证明 `/turn/audio` 是现役 FastAPI 应用的一部分，而不是一个已经废弃的孤立文件。

### 第 5 步：在路由函数中找「下一个接手者」

`turn_audio()` 中最关键的调用是：

```python
submission = turn_application_service.submit_audio(
    envelope,
    payload,
    asr_service=get_asr_application_service(),
)
```

不需要一次读完整个路由文件。只需要问：

> 「它把音频交给了谁？」

答案是 `turn_application_service.submit_audio()`。

查看文件顶部的 import：

```python
from turn_application_service import TurnApplicationService
```

这句 import 就是导航地图，告诉我们下一个文件是 `web/turn_application_service.py`。

### 第 6 步：从公开方法找真正执行方法

搜索：

```powershell
rg -n "def submit_audio|def _execute_audio|def _execute_prepared" web\turn_application_service.py
```

调用关系是：

```text
submit_audio()
→ 线程池提交 _execute_audio()
→ asr_service.recognize_upload()
→ 用识别文本构造 TurnInput
→ _execute_prepared()
```

这里出现了两条支线：

- `asr_service.recognize_upload()`：追踪语音识别；
- `_execute_prepared()`：追踪识别之后进入哪种业务。

### 第 7 步：追踪 ASR 实现

路由调用时明确传入：

```python
asr_service=get_asr_application_service()
```

查看 import：

```python
from asr_application_service import get_asr_application_service
```

于是进入 `web/asr_application_service.py`，搜索：

```powershell
rg -n "def get_asr_application_service|def recognize_upload|def _get_backend" web\asr_application_service.py
```

可以继续沿着 ASR 工厂追踪到：

```text
ASRApplicationService
→ ASR factory
→ SenseVoiceBackend
→ FunASR AutoModel
```

对应代码主要位于：

- `web/asr_application_service.py`；
- `src/asr/factory.py`；
- `src/asr/sensevoice_backend.py`。

### 第 8 步：追踪业务模式分派

`_execute_prepared()` 中有显式分派：

```python
if turn.interaction_mode == InteractionMode.CHAT:
    processor = self._chat_processor
elif turn.experiment_context == ExperimentContext.TEMPLATE:
    processor = self._template_processor
elif turn.experiment_context == ExperimentContext.STORAGE:
    processor = self._storage_processor
else:
    processor = self._experiment_processor
```

这段代码证明：语音识别完成后，系统不是一律送去聊天，而是根据交互模式和实验上下文选择处理器。

要知道 `_experiment_processor` 运行时究竟是什么对象，必须倒查对象装配：

```python
turn_application_service = TurnApplicationService(
    ...
    experiment_processor=ExperimentProcessor(turn_store),
)
```

再查看 import：

```python
from turn_processors import ExperimentProcessor
```

于是进入 `web/turn_processors.py`。

### 第 9 步：在长处理器中使用业务词定位

`ExperimentProcessor.prepare()` 很长，不应该从第一行开始硬读。应该根据要验证的能力选择搜索词。

例如，追踪缺失信息与追问：

```powershell
rg -n "missing_fields|follow_up|clarification" web\turn_processors.py
```

追踪方案完成核对：

```powershell
rg -n "protocol_completion|resolve_protocol_completion" web\turn_processors.py
```

当看到：

```python
protocol_completion = resolve_protocol_completion(...)
```

再查看 import：

```python
from src.core.protocol_completion_policy import resolve_protocol_completion
```

下一个文件就是 `src/core/protocol_completion_policy.py`。

### 第 10 步：追踪最终数据写入

处理器返回 `PreparedTurn` 后，`_execute_prepared()` 调用：

```python
self.store.commit(...)
```

不要根据 `store` 这个名字猜。应该回到对象创建处：

```python
turn_store = TurnStore()
turn_application_service = TurnApplicationService(store=turn_store, ...)
```

再根据 import：

```python
from database.turn_store import TurnStore
```

进入 `web/database/turn_store.py`，搜索：

```powershell
rg -n "def commit|INSERT INTO|UPDATE " web\database\turn_store.py
```

在 `commit()` 中能看到真实 SQL 写入，包括 ASR 证据、实验事件、消息、实验记录和会话状态等。

走到这里，才能证明系统不只是返回一句「已记录」，而是存在真实的数据库事务提交。

## 五、语音实验主链的代码对照

| 用户眼中发生的事 | 专业职责 | 代码位置 |
|---|---|---|
| 用户单次录音 | 单次录音生产者 | `web/frontend/voice_asr.js` |
| 用户在手机页录音 | 移动端音频生产者 | `web/frontend/mobile.js` |
| 用户进行连续通话 | 连续通话音频生产者 | `web/frontend/phone_call.js` |
| 三种入口使用同一提交方式 | 前端 Turn 传输客户端 | `web/frontend/turn_client.js` |
| 服务器接收音频 | FastAPI 路由适配器 | `web/api/turn.py` |
| 校验请求、调度执行、提交结果 | 应用服务与事务边界 | `web/turn_application_service.py` |
| 保存音频并转写 | ASR 应用服务 | `web/asr_application_service.py` |
| 选择 ASR 后端 | 工厂模式 | `src/asr/factory.py` |
| 使用 SenseVoice 识别 | ASR 后端适配器 | `src/asr/sensevoice_backend.py` |
| 理解实验口述、处理追问和方案状态 | 实验业务处理器 | `web/turn_processors.py` |
| 判断方案步骤是否完整 | 确定性完成策略 | `src/core/protocol_completion_policy.py` |
| 提交 ASR 证据、实验事件和会话状态 | SQLite 持久化与事务边界 | `web/database/turn_store.py` |

完整调用链：

```text
voice_asr.js / mobile.js / phone_call.js
→ turn_client.submitAudio()
→ POST /turn/audio
→ api/turn.py::turn_audio()
→ TurnApplicationService.submit_audio()
→ TurnApplicationService._execute_audio()
→ ASRApplicationService.recognize_upload()
→ 构造 TurnInput
→ TurnApplicationService._execute_prepared()
→ ExperimentProcessor.prepare()
→ 语义理解 / 追问 / 方案核对
→ TurnStore.commit()
→ SQLite
```

## 六、如何把代码翻译成作品功能

### 1. 错误写法

直接抄代码名称：

> 系统使用 `TurnApplicationService`、`ExperimentProcessor` 和 `TurnStore`。

这句话对评委没有用，因为没有说用户得到了什么。

### 2. 翻译模板

使用：

> **用户做什么＋系统经过什么处理＋最终得到什么可靠结果**

例如：

> 实验人员可以通过语音口述实验操作。系统完成音频保存、语音识别和实验语义理解，将口述转化为结构化记录，并结合当前方案核对步骤完成情况和缺失参数，最终保存处理结果与实验状态。

这句功能描述的每一部分都能回到代码中找到对应责任。

## 七、代码中还能看到哪些核心功能候选

通过 `web/app.py` 中的 `app.include_router(...)`，可以找到下列真实 API 入口。它们目前属于「核心功能候选」：入口已经存在，但还应继续追踪服务、存储、测试和真实验收，再决定最终文案。

### 1. 实验语音交互主线

- 单次录音、手机录音和连续通话；
- 自由聊天、自由实验、方案实验等模式隔离；
- 结构化实验记录和原始证据保存；
- 主动追问和多轮信息补全；
- 方案执行跟踪与确定性核对；
- 查看、回答、确认、暂缓和结束等流程控制命令；
- 流式语音反馈与播放调度。

### 2. 实验前后的支撑功能

- `/protocols`：实验方案列表、详情、上传、草拟、修改、步骤管理和执行选择；
- `/reagent-prep`：试剂配制方案管理；
- `/calculator`：分子量、溶液配制和稀释计算；
- `/storage`：试剂、样品和存放位置管理；
- `/experiments`：实验安排与状态管理；
- `/memories`：经用户确认的长期信息管理；
- `/community`：实验内容浏览、发布和导入；
- `/chat`：通用智能体对话与 Function Calling 工具调用。

### 3. 最终作品简介建议收敛为六组功能

1. 多形态实验语音交互；
2. 结构化记录与原始证据保存；
3. 主动追问与多轮信息补全；
4. 方案执行跟踪与确定性核对；
5. 实验方案、专业计算和资源管理；
6. 智能体工具调用与实验交流。

其中前四组是差异化主线，后两组用于体现实验全流程的完整性。

## 八、功能证据的四个等级

| 等级 | 已找到的证据 | 可以怎样表述 |
|---|---|---|
| 1. 入口存在 | 页面按钮或 API 路由 | 「系统提供……入口」 |
| 2. 代码闭环 | API、服务、领域逻辑和存储均接通 | 「系统能够完成……」 |
| 3. 自动验证 | 相关单元、集成或回归测试通过 | 「该流程已通过自动测试……」 |
| 4. 真实验收 | 真实麦克风、浏览器、扬声器或外部服务跑通 | 「已在真实环境完成验证……」 |

这四级不能混写。特别是：

- `AUTO_OK` 只代表自动证据通过；
- `REAL_OK` 才代表真实环境功能验收；
- `UX_CONFIRMED` 代表真实用户对体验做出确认；
- 三者不能互相替代。

### 1. 看调用

看到：

```python
service.submit_audio(...)
```

就搜索：

```powershell
rg -n "def submit_audio" .
```

它回答：这个方法在哪里实现？

### 2. 看定义来源

看到：

```python
from turn_processors import ExperimentProcessor
```

```python
self._experiment_processor.prepare(...)
```

不要猜 `_experiment_processor` 是什么。先找构造函数中的：

```python
self._experiment_processor = experiment_processor
```

```python
experiment_processor=ExperimentProcessor(turn_store)
```

它回答：运行时实际装进去的是哪个对象？

## 十、练习：怎样自己追下一项功能

以「分子量计算」为例，不要直接相信页面标题。可以按下列顺序自己追踪：

1. 在前端搜索 `/calculator/molecular-weight`；
2. 找到发起 `fetch()` 的页面或工具调用者；
3. 在 `web/api/calculator.py` 找到对应路由；
4. 查看路由调用哪个计算函数；
5. 追到真正公式和输入校验；
6. 搜索函数名和接口路径，找对应测试；
7. 分别写下「能证明什么」和「不能证明什么」；
8. 最后再把代码翻译为用户能看懂的功能描述。

建议每追完一项功能，都填一张小表：

| 项目 | 记录 |
|---|---|
| 用户动作 | 用户做了什么？ |
| 前端入口 | 哪个 JS/HTML 发起？ |
| API | 请求路径和方法是什么？ |
| 应用服务 | 谁组织执行流程？ |
| 领域逻辑 | 真正业务规则在哪里？ |
| 存储/副作用 | 结果写到哪里？ |
| 自动测试 | 哪些测试覆盖了它？ |
| 真实验收 | 在哪种真实环境下跑通？ |
| 能证明 | 当前证据支持哪些结论？ |
| 不能证明 | 哪些仍然只是推测？ |
| 作品文案 | 最后怎样准确表述？ |

## 十二、本文用到的关键专业词

| 专业词 | 白话解释 | 本项目中的体现 |
|---|---|---|
| ASR | 把语音变成文字 | SenseVoice 识别实验口述 |
| TTS | 把文字变成语音 | 将追问或反馈播放给用户 |
| API Route | 前端访问后端的门 | `POST /turn/audio` |
| Application Service | 负责组织一次完整任务的调度员 | `TurnApplicationService` |
| Domain Logic | 真正决定业务对错的规则 | 缺失字段、方案完成判定 |
| Persistence | 把结果真正写到磁盘或数据库 | `TurnStore.commit()` |
| Transaction | 一组数据要么一起成功，要么一起失败 | SQLite 中统一提交 Turn 结果 |
| Function Calling | 大模型选择工具并生成结构化参数 | 计算、方案、储存等工具调用 |
| Deterministic Rule | 相同输入按明确规则得到可复现结果 | 方案完成策略、专业计算 |

## 十三、以后怎样讲解代码和架构

面向刚开始学习开发的读者，不应该一上来就堆函数名、类名和专业术语。以后讲解项目代码时，默认按以下顺序展开。

### 1. 先讲白话直觉

先用生活中的过程建立整体画面，让读者先知道「它到底在做什么」。

例如，讲解流式 TTS 时，可以类比为：

> 非流式像是十道菜全做完才一起上桌；流式像是一道菜做好就先端上来，用户吃第一道时，厨房继续做后面的菜。

这一步的目标是建立直觉，不是追求技术完整性。

### 2. 再走一遍真实过程

按用户动作的发生顺序，一步一步说明数据如何流动：

```text
用户做什么
→ 前端做什么
→ 后端做什么
→ 外部服务做什么
→ 结果怎样回到用户
```

例如流式 TTS：

```text
「小科」决定朗读一句话
→ 浏览器请求本地 /tts/stream
→ 后端带着 AppID 和 Access Token 连接火山
→ 火山每生成一小段 PCM 音频就返回一包
→ 后端收到一包就向浏览器转发一包
→ 浏览器收到一包就转换并排队播放
```

这一步要先讲清「事情怎样发生」，再让读者去看代码。

### 3. 然后把每一步对应到代码

每介绍一层代码，先说明它在整个过程中的职责，再给出文件、函数和关键语句。

例如：

```text
白话职责：浏览器向我们的后端提出「请把这句话变成声音」的请求。
代码位置：web/frontend/local_tts.js
关键代码：fetch('/tts/stream', ...)
```

禁止只给出一串文件名或函数名，却不解释为什么会走到这一层。

### 4. 解释为什么要这样设计

每个重要设计都要同时回答：

- 它解决了什么问题？
- 如果不这样做，会出现什么用户可见的问题？

例如，火山流式 TTS 由后端转发，而不是浏览器直连，主要因为：

- Access Token 不应暴露在浏览器中；
- 火山返回的是自定义二进制帧，需要后端拆包；
- 后端需要处理连接复用、断线、错误帧和中途取消；
- 否则可能出现凭证泄露、无法定位错误或上一句残留音频串入下一句等问题。

这一步要把代码设计与用户实际感受联系起来。

### 5. 最后补充专业术语

当读者已经理解整个过程后，再告诉他这些设计的正式名称，方便以后搜索、阅读文档和迁移到其他项目。

例如：

- WebSocket：可以长时间保持的双向通信连接；
- Async Generator（异步生成器）：拿到一块数据就先 `yield` 出去；
- StreamingResponse（流式响应）：服务器不等所有数据完成，而是分块回传；
- PCM：尚未压缩的原始声音采样；
- Web Audio API：浏览器用来创建、排队和播放音频的接口。

### 6. 默认回答模板

以后的技术讲解默认采用：

```text
白话直觉
→ 完整过程
→ 代码对照
→ 设计原因与反面情况
→ 专业术语
```

目标不是让读者记住一堆函数名，而是让他能够画出数据流、找到对应代码，并理解每个设计为什么存在。
