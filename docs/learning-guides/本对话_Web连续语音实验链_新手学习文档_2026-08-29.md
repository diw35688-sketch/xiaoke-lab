## 1. 第一个新手误区：说了一大段，为什么只有“第 1 段口述”

### 1.1 白话解释

“一段口述”不是“一句话”，也不是“一项实验操作”。它是录音系统切出来的一块音频。

如果你一直说，中间没有达到断句条件的停顿，那么即使内容里有十个句号、十个实验动作，录音系统也可能只提交一个音频片段，所以界面只产生一张“第 1 段口述”记录卡。

### 1.2 专业设计

连续通话通常由 VAD（Voice Activity Detection，语音活动检测）决定什么时候开始和结束一个片段：

```text
检测到人声开始
→ 持续收集音频
→ 检测到足够长的静音
→ 封口为一个 WAV 片段
→ 提交 /turn/audio
```

VAD 看的是声音活动，不理解“这句话在语义上已经结束”。因此：

- 内容很长但没有明显停顿：可能仍是一段。
- 内容很短但停顿很长：可能被切成多段。
- 多个实验动作出现在一个音频片段中：结构化理解可以提取多个动作，但界面的“口述段号”仍只增加一次。

### 1.3 RMS 回退是什么

本对话中提到的主路径是 Silero VAD。RMS 是按音量能量判断有没有说话的基础回退方案。

- Silero：利用语音模型判断人声，一般更能区分说话、噪声和短暂停顿。
- RMS：只看声音强弱，环境噪声、风扇声或音量变化都可能影响结果。
- 回退的意义：Silero 模型加载或初始化失败时，系统至少还能提供基础录音能力。
- 回退不代表 RMS 与 Silero 一样好，也不代表测试时应该主动走 RMS。

本对话没有要求增加一套新的并行 VAD 架构；RMS 只应作为失败兜底理解。

### 1.4 鲁棒性测试应该怎么说

不需要一口气念完整篇长文。更友好的方法是把实验过程分成多段，每段只验证一个完整事实，例如：

1. “我检查了离心管和移液枪，器材表面没有明显污染。”
2. “我用移液枪吸取五十微升磷酸盐缓冲液，加入样品离心管。”
3. “加入后轻轻吹打混匀三次，样品基本分散。”
4. “我把离心管放入恒温振荡器，温度三十七摄氏度，转速每分钟二百转。”
5. “样品连续振荡培养二十分钟，仪器运行正常，没有报警。”
6. “培养结束后溶液由透明变成浅黄色，管底有少量沉淀。”
7. “最后把样品放在试管架上，准备下一步检测。”

每段的期待结果应提前写清楚：转写内容、记录卡段号、实体字段、是否产生待确认问题、是否朗读。

## 2. 如何看 `/turn/audio`，以及它能证明什么

### 2.1 新手操作

在浏览器开发者工具中：

1. 打开 `Network`。
2. 搜索或筛选 `turn/audio`。
3. 点击本次音频请求。
4. 查看 SSE 返回事件。
5. 重点找 `turn_result`、`voice_delivery` 和 `done`。

### 2.2 三个事件的含义

```text
turn_result
  说明业务 Turn 已形成；可以看屏幕 Blocks、business、session_ended 等。

voice_delivery
  说明某段文字获得了语音播放资格；不等于扬声器已经实际播放成功。

done
  说明本次 SSE 流正常收尾；前端可以结束等待状态。
```

结束实验时，`turn_result.business` 中应看到：

```json
{
  "session_ended": true
}
```

### 2.3 证据边界

- 看到 `turn_result`：证明服务器产生并返回业务结果。
- 看到 `voice_delivery`：证明服务器授权候选语音进入播放链。
- 听到扬声器完整播放：才证明真实音频播放通过。
- 按钮恢复、麦克风停止：才证明连续通话前端状态真正退出。

只看 Network 不能替代真实听觉和麦克风验收。

## 3. 结束实验为什么最初只显示一句话

### 3.1 现象

最初用户说“结束实验记录”后，系统只显示：

> 本次实验记录已结束。

但没有回显本次实验的步骤数和全部未解决问题。

### 3.2 根因

结束分支只返回了硬编码短句，没有从已恢复的 `ReplyCoordinator` 中读取全部待确认问题，也没有读取 SQLite 中的本次实验步骤数。

### 3.3 修复后的专业设计

结束回复由会话真实状态生成：

```text
SQLite 恢复实验会话
→ ReplyCoordinator.active_clarifications()
→ 过滤掉已解决问题
→ 保留稳定 display_number
→ 标注“待回答”或“已暂缓”
→ 加入 experiment_step_count
→ 形成完整屏幕摘要
```

当前入口可从 [turn_processors.py](../web/turn_processors.py) 中搜索：

- `active_clarifications()`：取得所有仍未解决的问题。
- `SESSION_CLOSING_SUMMARY`：表示结束实验的汇总消息。
- `experiment_step_count`：本次实验保存的步骤数量。

数据库恢复逻辑位于 [turn_store.py](../web/database/turn_store.py) 的 `load_experiment_state()`。它同时返回：

- `next_segment_id`
- `experiment_step_count`
- `reply_coordinator`
- `session_context`

### 3.4 为什么已解决的问题不应再显示

结束汇总的目的不是重放全部历史，而是告诉用户还有什么没有处理。因此只列 `ACTIVE` 和 `DEFERRED`，排除 `RESOLVED`。

这叫“按业务状态投影界面”，不是简单把数据库内容全部打印出来。

## 4. 为什么完整汇总显示了，却没有朗读，连续通话也没退出

### 4.1 表面上像三个问题

- 屏幕有完整文字。
- 扬声器没有读最后回复。
- 连续通话没有退出。

实际上它们来自同一个事件链断点。

### 4.2 因果链

```text
完整结束摘要很长
→ 直接拿整段文字创建 voice_delivery
→ 超过单轮语音长度预算
→ voice_delivery 构造/授权异常
→ SSE 后续 done 被吞掉
→ 前端既没有收尾语音，也没有最终结束信号
→ 连续通话不退出
```

### 4.3 修复原则：屏幕全文和语音摘要分离

屏幕适合承担完整信息：

```text
本次实验记录已结束。
本次共记录 9 个实验步骤。
仍有 2 个待确认问题：
问题 1……
问题 3……
```

语音适合承担短收尾：

> 本次实验记录已结束，仍有 2 个待确认问题，请查看屏幕汇总。

这不是“把内容删掉”，而是按渠道能力分工：完整事实保留在屏幕，语音降低认知负担。

### 4.4 代码对照

- [turn_processors.py](../web/turn_processors.py)：结束时分别构造屏幕全文和短语音。
- [turn.py](../web/api/turn.py)：语音授权异常不能阻止已经提交的 Turn 发送 `done`。
- [phone_call.js](../web/frontend/phone_call.js)：结束时用 `stopCall({preservePlayback: true})`，停止麦克风但保留最后一段播放。

这里体现了一个重要设计原则：

> 已提交的业务结果不能因为后置语音播放失败而变成“请求没有结束”。

专业上可以理解为“持久化提交边界”和“展示副作用边界”分离。

## 5. 待确认问题为什么会出现难懂的英文内部字段

### 5.1 现象

用户回答温度后，界面曾显示：

```text
已将对问题 4 的答复的实体字段 ['action', 'temperature'] 填入。
仍需补充：duration。
```

状态其实是对的，但话术非常不友好。

### 5.2 两套信息不能混用

执行器需要保留调试证据：

```text
supplied_fields = action, temperature
remaining_fields = duration
```

用户只需要知道：

> 已补充问题 4 的温度，仍需补充：加热时间。

前者是机器内部事实，后者是用户界面文案。

### 5.3 为什么多识别出的 `action` 没有破坏状态

回答“加热的温度是 100 摄氏度”时，实体提取器可能同时识别：

- `action = 加热`
- `temperature = 100 摄氏度`

但问题真正缺少的是 `temperature` 和 `duration`。`PendingClarification.supply_fields()` 只会从原有 `missing_fields` 中删除本次确实提供的字段，额外的 `action` 不会让问题错误解决。

对应代码：

- [clarification_executor.py](../src/core/clarification_executor.py)：提取 `supplied_fields`，保留执行原因和剩余字段。
- [pending_clarification.py](../src/core/pending_clarification.py)：计算新的 `remaining_fields`。
- [presentation_copy.py](../src/core/presentation_copy.py)：把字段名翻译成面向用户的中文话术。

### 5.4 专业原则

```text
业务执行结果（structured result）
≠ 调试原因（diagnostic reason）
≠ 屏幕文案（screen copy）
≠ 语音文案（voice copy）
```

它们可以来自同一次业务执行，但用途不同，不能直接互相替代。

## 6. 为什么问题要做成小卡片，而且语音只读问题

### 6.1 用户真正需要什么

用户需要快速看懂三件事：

- 这是第几个问题。
- 现在是什么状态。
- 我具体要回答什么。

因此待确认问题改成结构化卡片：

```text
┌──────────────────────────────┐
│ 待确认问题   问题 2   待回答 │
│ 您说的是移液枪吗？           │
└──────────────────────────────┘
```

### 6.2 为什么不朗读“已创建待确认问题 2”

“已创建”“编号 2”“待回答”是界面管理信息。用户在听觉上真正需要的是问题本身。

因此同一个问题具有两个呈现结果：

```text
屏幕：编号 + 状态 + 问题正文
语音：问题正文
```

### 6.3 代码对照

- [turn_processors.py](../web/turn_processors.py)：创建 `confirmation_card`，并把 `voice_text` 单独设置为问题正文。
- [conversation_block_view.js](../web/frontend/conversation_block_view.js)：把 `confirmation_card` 渲染成“待确认问题”卡片。
- [streaming_chat_v2.js](../web/frontend/streaming_chat_v2.js)：统一渲染文字输入、单次录音和连续通话返回的卡片。
- [phone_call.js](../web/frontend/phone_call.js)：连续通话收到最终 Turn 后调用统一卡片入口。
- [voice_asr.js](../web/frontend/voice_asr.js)：单次录音也调用同一个入口。

自动测试 [test_turn_processors.py](../tests/test_turn_processors.py) 中的
`test_created_clarification_is_a_numbered_card_and_voice_only_reads_question`
明确检查：

- 卡片编号正确。
- 卡片正文正确。
- 状态是“待回答”。
- `voice_text` 只有问题正文。
- `voice_text` 不包含“已创建”。
- 语音来源绑定到可见问题卡片。

### 6.4 为什么语音必须绑定可见卡片

`source_block_id` 表示“这段语音是在朗读屏幕上的哪一块内容”。绑定后可以做追踪、取消、打断和结果反馈。

如果语音来源绑定到一条隐藏的内部提示，而屏幕显示另一张卡片，后续排查会出现“声音和界面不知道是不是同一条消息”的问题。

## 7. 为什么刷新网页、重启 Python 后仍然是“第 2 段口述”

### 7.1 白话解释

刷新网页和重启服务只是重新加载程序，不等于结束实验。

系统把身份和数据放在不同位置：

```text
浏览器存储：我正在进行哪一次实验（lab_session_id）
SQLite：这次实验已经保存了哪些记录
Python 进程：当前正在运行的程序和临时对象
```

重启 Python 只清掉进程内存，不会清除浏览器身份，也不会删除 SQLite 记录。

### 7.2 恢复过程

```text
浏览器刷新或 Python 重启
→ 浏览器继续发送原 lab_session_id
→ 后端查询 SQLite
→ 找到该实验已有第 1 段
→ next_segment_id = MAX(segment_id) + 1
→ 新口述显示为第 2 段
```

### 7.3 代码对照

- [turn_client.js](../web/frontend/turn_client.js)：生成、保存和发送 `lab_session_id`；收到真正的结束结果后调用 `beginNextLabSession()`。本对话发生后，代码又演进为 `LAB_SESSIONS_KEY` 映射，使自由实验和不同方案可以分别持有会话 ID；但“刷新沿用、结束后轮换”的原理没有改变。
- [turn_store.py](../web/database/turn_store.py)：`load_experiment_state()` 根据现有记录计算 `next_segment_id`。

### 7.4 三个操作的业务含义

| 操作 | 是否结束当前实验 | 是否应该从第 1 段重新开始 |
|---|---:|---:|
| 刷新网页 | 否 | 否 |
| 重启 Python 服务 | 否 | 否 |
| 明确执行“结束实验记录” | 是 | 是，下一条实验使用新 ID |

这样设计的目的，是避免实验进行中因为误刷新或服务重启而丢失上下文。

## 8. 本次真实验收应该怎样分级

### 8.1 四种常用证据等级

- `CODED`：代码已经写了。
- `AUTO_OK`：自动测试通过。
- `REAL_OK`：用户在真实浏览器、麦克风、扬声器和服务环境中验收通过。
- `REAL_FAIL`：真实操作已经证明不符合预期。

### 8.2 本对话中的证据

| 项目 | 证据 |
|---|---|
| `session_ended=true` | Network/SSE + 真实操作 |
| 结束命令不新增记录 | SQLite/界面 + 真实操作 |
| 完整未解决问题上屏 | 真实浏览器 |
| 最后回复被朗读 | 真实扬声器 |
| 连续通话退出、麦克风停止 | 真实浏览器与麦克风状态 |
| 下一实验换新 `lab_session_id` | Network/数据库 + 真实操作 |
| 问题卡片与只读正文 | 自动测试 + 用户真实复验 |
| 服务无 `ValueError`/500 | 服务窗口 + Network |

重要边界：这些结果不能自动外推到方案实验、手机端、断网恢复或多标签页隔离。

## 9. Git 为什么不能直接推原分支

### 9.1 当时发生了什么

本地完成了验收提交，但检查远程后发现：

- 本地验收提交有 1 个独有提交。
- 原远程分支已有 115 个本地没有的提交。
- 两边从共同历史处分叉。

直接强推会覆盖远程其他人的大量工作，因此停止推送。

### 9.2 安全做法

```text
检查远程实际哈希
→ fetch 但不合并
→ 比较分叉
→ 保留脏工作区
→ 从已验收提交创建新 feature 分支
→ 按明确文件清单暂存
→ 检查敏感路径和 diff
→ 跑全量测试
→ 普通 push 新分支
→ 对比本地与远程哈希
```

最终发布信息：

```text
分支：feature/unified-web-turns
提交：1889cd0
提交标题：[Web实验链] 接入统一 Turn、会话结束与问题卡片
```

### 9.3 为什么不能 `git add -A`

工作区里同时存在：

- 用户原有修改。
- 真实验收产生的 WAV。
- `web/data/` 运行数据。
- 临时文本和日志。
- 本轮代码、测试和正式文档。

`git add -A` 会把这些不同性质的内容混在一起。正确做法是显式列出要提交的文件，再检查 `git diff --cached`。

### 9.4 本次遵守的提交标准

- 分支采用 `feature/xxx`：`feature/unified-web-turns`。
- 提交信息采用 `[模块] 简述`。
- 没有提交 `.venv/`、`__pycache__/`、`dist/`、`build/`、`web/settings.json`、`web/certs/`、`web/lab_agent.db`、`results/`。
- WAV、`web/data/`、数据库和临时对话文本也没有提交。
- 没有使用 `--force` 覆盖远程。

## 10. 把这次设计浓缩成五条工程原则

### 原则一：业务事实、屏幕文案和语音文案分开

同一个状态可以生成不同渠道的表达。完整屏幕摘要不应原样塞进短语音。

### 原则二：先保存成功，再反馈成功

“已记录”“问题已解决”必须以持久化或状态变更成功为前提，不能提前乐观显示。

### 原则三：后置展示失败不能推翻已提交业务

Turn 已经提交后，即使 TTS 授权失败，也要发出 `done`，不能让客户端永久等待。

### 原则四：恢复会话和开始新会话是不同操作

刷新和重启用于恢复；明确结束命令才创建下一实验身份。

### 原则五：自动测试和真实体验是两种证据

自动测试证明合同，真实验收证明浏览器、麦克风、扬声器和人的体验。两者都需要，但不能互相冒充。

不要一次打开几十个文件。按一条用户可见结果向后追：

### 路线 B：研究“为什么重启后还是第 2 段”

## 12. 自己动手验收清单

### 12.1 多段连续口述

- 每次明显停顿后只产生一次 `/turn/audio`。
- 每个成功片段只生成一张新的实验记录卡。
- 段号在同一实验中连续增加。
- 一次长时间不停顿的口述可能只有一段，这本身不算错误。

### 12.2 待确认问题

- 屏幕显示“待确认问题”小卡片。
- 卡片显示稳定的“问题 N”。
- 卡片显示“待回答”状态和完整问题。
- 扬声器只读问题正文。
- 回答一部分后，只提示仍缺少的内容。
- 完整回答后，问题标记为解决。

### 12.3 结束实验

- 屏幕显示实验已结束、步骤总数和全部未解决问题。
- 扬声器播放短收尾。
- `turn_result.business.session_ended` 为 `true`。
- `voice_delivery` 后最终仍收到 `done`。
- 连续通话按钮退出通话态。
- 麦克风不再提交新片段。
- 结束命令不生成实验记录卡。
- 下一次实验从第 1 段开始，并使用新 `lab_session_id`。

### 12.4 证据记录格式

建议每次写成：

```text
操作：我做了什么
期待：屏幕、声音、Network、数据库分别应该怎样
实际：各自看到了什么
结论：AUTO_OK / REAL_OK / REAL_FAIL / REAL_PENDING
证据：request_id、截图、关键字段、服务日志
```

## 13. 这一小步之外没有证明什么

本文不能证明：

- 方案实验的步骤状态和自由实验完全隔离。
- 手机端拥有同样的卡片与播放体验。
- 多个浏览器标签页不会共享或污染实验身份。
- 断网、浏览器崩溃和磁盘写入失败都能正确恢复。
- RMS 在噪声环境中与 Silero 一样可靠。
- 所有长口述都会自动按语义拆成多段。

这不是缺点清单，而是证据边界。知道“已经证明什么”和“还没有证明什么”，是可靠软件开发的重要能力。
