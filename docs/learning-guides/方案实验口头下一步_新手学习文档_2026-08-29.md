## 先看结论

这次实现让用户在方案实验模式中说“下一步”“进入下一步”或“继续下一步”，系统就能在检查完当前步骤后进入下一步。

它不是“听到三个字就让网页翻页”，而是一条完整的后端业务链：

```text
用户说“下一步”
→ ASR 得到忠实转写
→ 本地精确命令解析
→ 风险策略发放有限权限
→ 统一分派到方案导航
→ 恢复当前步骤、问题和字段状态
→ 确定性导航规则判断能否前进
→ 生成新步骤卡和语音回显
→ 与本次 Turn 一起提交 SQLite
→ 页面显示，扬声器播放
```

真实验收已经通过，包括随后修复的场景：当前步骤没有生成问题，即使还有未记录字段，也能明确说“下一步”继续；旧步骤会保留为 `left_with_pending`，不会被假装成完整完成。

## 一、先用白话理解这个功能

### 1. 用户想要什么

以前用户主要靠按钮进入下一步。现在做实验时双手可能正在拿仪器，因此希望直接说：

```text
下一步
```

系统应当：

1. 听懂这是控制命令，不是实验记录。
2. 检查当前步骤能不能离开。
3. 允许时切到下一步。
4. 不允许时告诉用户原因。
5. 页面、语音和数据库保持一致。

### 2. 为什么不能写成一个简单的 `if`

最简单的写法可能是：

```python
if "下一步" in text:
    current_step += 1
```

但它会产生三个严重问题。

第一，实验叙述会误触发：

```text
等示数稳定后再进行下一步。
```

这句话只是记录实验条件，不是要求系统现在切步。

第二，它绕过业务规则：当前步骤可能还有待回答问题，或者已经是最后一步。

第三，它只改了一个临时变量：页面可能翻了，数据库却没更新；刷新后又回到旧步骤。

所以真正的目标不是“识别三个字”，而是把口头命令安全地接入现有方案状态机和统一 Turn 事务。

## 二、先认识三个核心概念

### 1. Turn：一次完整交互

白话：用户说一句话，到系统完成理解、保存、显示和语音反馈，这一整笔叫一个 Turn。

专业说法：Turn 是一次带身份、模式、输入来源、业务输出和持久化结果的交互事务边界。

本功能中，一个 Turn 包含：

```text
用户原话“下一步”
+ 当前 conversation_id / lab_session_id
+ 输入来源和 ASR 证据
+ 导航判断结果
+ 新步骤卡或拒绝原因
+ 语音播放内容
+ 是否写入新的方案步骤状态
```

代码入口：

- `src/core/turn_input.py`：输入合同 `TurnInput`。
- `web/turn_processors.py`：实验业务准备器 `ExperimentProcessor.prepare()`。
- `web/turn_application_service.py`：统一提交入口。

### 2. 精确命令：代码明确认出的命令

白话：只有用户清楚、独立地说“下一步”，系统才把它当作切步命令。

专业说法：使用 deterministic exact-match fast path，即确定性的本地精确匹配快速路径。

它与 LLM 猜测不同：

| 输入 | 处理结果 |
|---|---|
| “下一步” | 精确控制命令 |
| “进入下一步。” | 精确控制命令 |
| “等稳定后再进行下一步” | 普通实验叙述 |
| “下一步需要加多少水” | 普通问题 |
| “不要进入下一步” | 不能切步 |

### 3. 状态机：决定“允许不允许”的规则

白话：识别出“下一步”只是拿到申请表，状态机才是审批人。

专业说法：`decide_protocol_move()` 是无存储、无 LLM 依赖的确定性领域策略。相同状态和相同输入永远得到相同决策。

## 三、完整实现链路：八个代码关卡

## 关卡 1：语音先变成可信输入

语音首先由 ASR 生成 `ASRResult`：

```python
ASRResult(
    asr_transcript="下一步",
    asr_model_raw_text="下一步",
    audio_path="...",
    audio_duration_seconds=0.8,
    recognition_seconds=0.1,
    model="...",
    language="zh",
)
```

随后装入 `TurnInput`：

```python
TurnInput(
    conversation_id="...",
    request_id="...",
    turn_id="...",
    lab_session_id="...",
    interaction_mode=InteractionMode.EXPERIMENT,
    experiment_context=ExperimentContext.PROTOCOL,
    input_source=InputSource.SINGLE_RECORDING,
    raw_text="下一步",
    asr_result=asr_result,
)
```

### 白话

把“谁说的、在哪个实验会话说的、通过什么方式输入、ASR 真正听成什么”装进一个不能随便改的盒子。

### 专业设计

这是 source-truthful input contract，来源可信输入合同。语音 Turn 要求：

```python
raw_text == asr_result.asr_transcript
```

业务层不能拿一段被大模型润色过的文字冒充原始语音转写。

### 自己检查

如果说“下一步”没反应，先检查：

```text
TurnInput.raw_text
ASRResult.asr_transcript
```

两者是否都是“下一步”。

## 关卡 2：精确解析器识别命令

文件：`src/core/interaction_command.py`

新增内部命令类型：

```python
NEXT_PROTOCOL_STEP = "next_protocol_step"
```

新增允许的口令：

```python
NEXT_PROTOCOL_STEP_COMMANDS = {
    "下一步",
    "进入下一步",
    "继续下一步",
}
```

解析规则：

```python
if normalized in cls.NEXT_PROTOCOL_STEP_COMMANDS:
    return cls._simple_command(
        InteractionCommandType.NEXT_PROTOCOL_STEP,
        raw_text,
        normalized,
    )
```

### 白话

系统先把句尾标点、SenseVoice 情绪符号等确定性噪声清理掉，再检查整句话是不是支持的命令。

### 专业设计

这里用集合完全匹配，而不是子串匹配。命令识别具有：

- 确定性；
- 零网络依赖；
- 零 LLM 调用；
- 可枚举测试；
- 保留原始 `raw_text`。

### 为什么不支持无限多自然说法

因为切步会修改状态。第一版宁可要求用户说清楚，也不能把实验叙述误判成控制命令。

## 关卡 3：风险策略限制执行资格

文件：`src/core/intent_policy.py`

命令策略：

```python
InteractionCommandType.NEXT_PROTOCOL_STEP: IntentPolicy(
    command_type=InteractionCommandType.NEXT_PROTOCOL_STEP,
    risk=IntentRisk.MEDIUM,
    changes_session_state=True,
    requires_clarification_context=False,
    reversible=True,
)
```

### 字段对照

| 字段 | 白话 | 专业含义 |
|---|---|---|
| `MEDIUM` | 切错会影响实验流程 | 中风险状态变更 |
| `changes_session_state=True` | 会改变当前步骤 | 有业务副作用 |
| `requires_clarification_context=False` | 不是在回答问题 | 不依赖当前问题指针 |
| `reversible=True` | 原理上可以回到上一步 | 可逆导航动作 |

又增加了一个关键限制：如果“下一步”只是 LLM 的语义猜测，不允许执行。

```python
if command_type == InteractionCommandType.NEXT_PROTOCOL_STEP:
    disposition = DO_NOT_EXECUTE
```

### 白话

用户明确说“下一步”可以申请切步；模型觉得“用户大概想继续”不可以替用户按按钮。

### 专业设计

把 intent classification 和 execution authorization 分开。分类结果不是执行许可，证据等级决定可获得的权限。

## 关卡 4：统一分派器发放最小权限

文件：`src/core/unified_dispatch.py`

新增目的地：

```python
PROTOCOL_NAVIGATION = "protocol_navigation"
```

新增权限：

```python
EXECUTE_PROTOCOL_NAVIGATION = "execute_protocol_navigation"
```

并固定一一对应：

```python
PROTOCOL_NAVIGATION
→ EXECUTE_PROTOCOL_NAVIGATION
```

### 白话

解析器说“这是下一步命令”，风险策略说“证据够”，分派器才发一张只能去“方案导航窗口”的通行证。

### 专业设计

这是 least privilege，最小权限原则。导航命令不能因为获得权限就顺便：

- 写实验记录；
- 回答待确认问题；
- 结束实验；
- 调用任意工具。

分派器也不直接改状态，因为它不知道当前方案、步骤、问题和数据库 revision。

## 关卡 5：观察结果把动作送到业务层

文件：

- `src/core/unified_acceptance_bypass.py`
- `src/core/unified_observer.py`
- `src/core/clarification_acceptance.py`

当分派目标是方案导航时，输出：

```python
accepted = None
protocol_navigation_action = "next"
```

同时澄清问题动作保持 `NO_ACTION`。

### 白话

“下一步”不是实验事实，也不是对某个问题的回答，所以它不能被塞进实验记录或问题系统。它只携带一个干净的导航动作。

```text
实验事实采用：None
问题状态变更：NO_ACTION
方案导航动作：next
```

这避免了一个控制命令同时污染多套状态。

## 关卡 6：恢复当前方案状态

文件：`web/turn_processors.py`

`ExperimentProcessor.prepare()` 先按联合身份读取状态：

```python
stored = self._store.load_experiment_state(
    turn.conversation_id,
    turn.lab_session_id,
)
```

恢复的内容包括：

- 当前 revision；
- 待确认问题 `reply_coordinator`；
- 会话上下文 `session_context`；
- 当前步骤号；
- 每一步已经记录的事实；
- 每一步的进度状态。

### 白话

系统不能只看页面现在画着第几步。它要先从后端账本恢复“这个对话里的这次实验真正走到哪里”。

### 专业设计

导航判断基于持久化业务状态，而不是 DOM 或浏览器临时变量。状态按 `conversation_id + lab_session_id` 读取，并通过 revision 保护并发写入。

## 关卡 7：确定性导航规则决定能不能前进

文件：`src/core/protocol_navigation.py`

核心函数：

```python
decide_protocol_move(
    state=protocol_execution,
    action="next",
    total_steps=...,
    evaluation=...,
    unresolved=...,
)
```

它返回 `ProtocolMoveDecision`：

```python
ProtocolMoveDecision(
    allowed=True_or_False,
    reason="...",
    state=new_or_old_state,
    from_step_number=1,
    target_step_number=2,
    missing_fields=(...),
    blocking_question_numbers=(...),
    deferred_question_numbers=(...),
)
```

### 当前最终规则表

| 当前情况 | 是否前进 | 离开步骤的状态 | 用户反馈 |
|---|---:|---|---|
| 有 `ACTIVE` 问题 | 否 | 不变 | 请先回答或暂缓 |
| 没有问题、字段完整 | 是 | `completed` | 当前步骤已完成 |
| 没有问题、字段未记全 | 是 | `left_with_pending` | 仍有未记录字段，已前进 |
| 有 `DEFERRED` 问题，缺失字段都被承接 | 是 | `left_with_pending` | 带着暂缓问题前进 |
| 有问题，同时还有未被问题承接的新缺失字段 | 否 | 不变 | 仍有未承接缺失字段 |
| 已经是最后一步 | 否 | 不变 | 已经是最后一步 |

### 为什么状态机不读数据库

状态机只接收输入事实并返回决策，不自己读写数据库，也不调用 LLM。

专业上叫 pure domain policy，纯领域策略。优点是：

- 同样输入必得同样输出；
- 测试不需要启动 Web；
- 规则变化集中在一个位置；
- 按钮和语音可以复用同一规则。

## 关卡 8：生成新步骤卡、语音并一次提交

文件：

- `web/turn_processors.py`
- `web/turn_application_service.py`
- `web/database/turn_store.py`

允许切步后：

```python
protocol_execution = protocol_navigation.state
protocol_domain_state = selected_domain_state.jump_to(
    protocol_execution.current_step_number
)
step = domain.step_view(protocol_domain_state)
```

这里不只是把步骤号改成 2，还重新读取第二步的标题、说明和安全信息。

然后生成：

```text
USER_TEXT：下一步
PROTOCOL_CARD：当前方案
STEP_CARD：新的当前步骤
SAFETY_ALERT：新步骤安全提示
ASSISTANT_TEXT：切步结果
VOICE：语音播放引用
```

成功回显示例：

```text
当前步骤已完成，已进入下一步。当前是第 2 步：设备初始化。
```

有未记录字段但没有问题时：

```text
当前步骤仍有未记录字段，已进入下一步。当前是第 2 步：设备初始化。
```

最后 `TurnApplicationService` 将 Turn、Blocks 和新的 `protocol_step_facts` 一次提交 SQLite。

### 白话

先把整张单据准备好，再一次性入账。不能先告诉用户“成功”，过一会儿才发现数据库没写进去。

### 专业设计

这是 prepare-then-commit 和 transaction boundary：

```text
Processor 只准备结果
→ ApplicationService 统一提交
→ Store 在事务中校验 revision 并写入
```

如果并发请求已经改变 revision，旧请求不能覆盖新状态。

## 四、真实 Bug 复盘：没有问题，为什么仍然进不了下一步

## 1. 用户看到的现象

口头“下一步”已经能识别，但某一步没有生成任何问题卡时，系统仍拒绝进入下一步。

用户陷入死路：

```text
没有问题可以回答
→ 说“下一步”又被拒绝
→ 无法继续实验
```

## 2. 内部真实状态

没有问题不代表字段完整。例如：

```python
missing_fields = ["condition", "observation"]
unresolved_questions = []
```

旧规则计算：

```python
uncovered = missing_fields - deferred_question_fields
```

因为没有暂缓问题，`uncovered` 就等于全部缺失字段。

旧判断：

```python
if uncovered:
    block_next_step()
```

因此产生死路。

## 3. 为什么这是规则 Bug，不是 ASR Bug

复现测试直接调用 `decide_protocol_move()`，输入：

```python
evaluation={"missing_fields": ["condition"]}
unresolved=()
```

测试预期允许前进，但修改前得到 `allowed=False`。

这证明：

- 命令已经识别；
- 没有前端问题；
- 没有 ASR 问题；
- 阻塞发生在导航领域规则。

## 4. 最小修复

文件：`src/core/protocol_navigation.py`

旧代码：

```python
if uncovered:
```

新代码：

```python
if uncovered and scoped:
```

其中：

- `uncovered`：未被暂缓问题承接的缺失字段；
- `scoped`：属于当前方案、当前版本、当前步骤的未解决问题。

新含义是：

> 当前步骤确实存在问题，并且还有额外缺失字段没被这些问题承接时，才阻止前进。

问题列表为空时，明确“下一步”不再被卡死。

## 5. 为什么不直接标记为完成

即使允许前进，字段仍然可能没记全。因此状态写成：

```text
left_with_pending
```

而不是：

```text
completed
```

白话：允许用户继续，但账本诚实地保留“上一页还有空格”。

专业上，这是把 workflow navigation 和 evidence completeness 分离：流程是否允许继续，与证据是否完整不是同一个布尔值。

---

## 五、为什么这次只实现“下一步”

本轮明确限定为一个可独立验收的小能力：

```text
方案模式 + 精确口头命令 + 进入下一步
```

没有同时扩展：

- 口头“上一步”；
- 口头“跳到第几步”；
- 口头“完成本步”；
- 模糊自然语言自动推断；
- 多标签页会话隔离。

这样做的原因不是功能做不出来，而是每一种动作的风险和规则不同。例如“跳到第五步”可能跨过多个未处理步骤，不能直接复制 `next` 规则。

专业上，这是 bounded vertical slice：一次完成一条从输入到持久化、显示和验收的纵向能力，而不是同时铺开多个半成品入口。

- 本功能相关定向测试 70 项通过；
- 全量出现 12 项失败，集中在远端移动端页面、模板/储存模式构造参数和旧测试断言，不属于本功能；
- 因此不能把“合并后全量测试”写成通过。

这体现了证据分层：

| 证据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 纯函数单测 | 导航规则正确 | 浏览器真的会播放 |
| Turn 集成测试 | ASR 合同进入后端后能切步 | 真麦克风一定识别正确 |
| 全量测试 | 当时仓库自动化整体状态 | 用户体验一定好 |
| 真实验收 | 用户现场流程可用 | 多标签页隔离已解决 |

## 七、提交和推送为什么要特别谨慎

提交时工作区还有其他内容：

- 已修改文档；
- 会话导出文本；
- LLM 性能比较脚本；
- 其他开发中的代码。

因此没有使用：

```bash
git add -A
```

而是明确列出本功能的 12 个代码和测试文件。

提交为：

```text
7db6e81 feat: 支持语音命令推进方案步骤
```

刷新远端后发现目标分支领先 22 个提交，而且远端也修改了 `web/turn_processors.py`。处理方式是：

```text
先创建本功能提交
→ 普通 merge 远端
→ Git 自动合并重叠文件
→ 重跑本功能定向测试
→ 普通 push
→ 核对本地 HEAD 与远端哈希一致
```

最终推送的分支头为合并提交：

```text
a2a77c6
```

这里没有 force-push，也没有把无关脏文件混进功能提交。

## 八、自己排查“下一步没反应”的方法

不要一上来猜“大模型没听懂”。按下面的事实链检查。

## 第 1 步：ASR 听到了什么

检查：

```text
ASRResult.asr_transcript
TurnInput.raw_text
```

如果不是“下一步”，问题在麦克风、VAD、ASR 或转写清理。

## 第 2 步：是否命中精确命令

检查：

```python
InteractionCommandParser.parse(raw_text).command_type
```

期望：

```text
NEXT_PROTOCOL_STEP
```

如果得到 `NORMAL`，查看原话是否包含多余叙述，或者口令不在支持集合中。

## 第 3 步：是否获得导航权限

检查：

```text
destination = protocol_navigation
permission = execute_protocol_navigation
```

如果是 `abstention`，说明证据不足或只是 LLM 候选。

## 第 4 步：当前是不是方案模式

检查：

```text
interaction_mode = experiment
experiment_context = protocol
```

free 模式必须拒绝切方案步骤。

## 第 5 步：状态机为什么拒绝

检查 `ProtocolMoveDecision`：

```text
allowed
reason
missing_fields
blocking_question_numbers
deferred_question_numbers
```

这一步能区分：

- 有待回答问题；
- 有未承接缺失字段；
- 已经是最后一步；
- 正常允许前进。

## 第 6 步：新状态是否准备出来

检查：

```python
prepared.session_state[
    "protocol_step_facts"
]["current_step_number"]
```

## 第 7 步：数据库是否提交

检查请求是否走到：

```text
persistence_committed
```

并检查 revision 是否发生冲突。

## 第 8 步：前端是否消费结果

检查最终 Turn 是否包含：

```text
STEP_CARD
ASSISTANT_TEXT
VOICE
voice_delivery
```

如果数据库已经是新步骤但页面没变，问题才属于 SSE、Store 或渲染层。

## 九、这次最值得学的专业设计

### 1. 分类不等于执行授权

白话：门卫认出你是谁，不代表你能打开所有房间。

代码体现：

```text
InteractionCommandParser
→ IntentPolicyEvaluator
→ UnifiedDispatchPlanner
```

### 2. LLM 适合理解，不适合独占确定性控制权

白话：模型可以帮忙理解复杂叙述，但“现在是否切步骤”这种会改状态的动作，要由代码规则把关。

代码体现：精确口令零 LLM；LLM 候选 `DO_NOT_EXECUTE`。

### 3. 导航状态和证据完整性是两个维度

白话：可以离开这一页，不代表这一页所有格子都填满了。

代码体现：

```text
允许导航 + left_with_pending
```

不是只能在“禁止前进”和“完整完成”之间二选一。

### 4. 纯策略与副作用分离

白话：裁判只判结果，不亲自改记分牌和数据库。

代码体现：`decide_protocol_move()` 不读写数据库；`TurnApplicationService` 统一提交。

### 5. 一个用户动作只走一条正式路径

白话：口头下一步和按钮下一步最终遵守同一本规则，不能一边让模型调工具，一边让统一 Turn 改状态。

专业说法：single authoritative execution path，单一权威执行路径。

### 6. 先复现再修 Bug

白话：先用测试把现场重新搭出来，确认抓到同一只虫，再改代码。

代码体现：先添加 `test_missing_fields_without_any_question_can_move_next` 并看到失败，再修改规则使其通过。

### 7. 自动测试与真实验收不能互相冒充

白话：测试证明钥匙尺寸对，真实验收证明现场那扇门真的能打开。

本功能同时具备：

```text
AUTO_OK + 用户真实验收通过
```

但这仍不证明多标签页并发隔离等其他能力。

## 十、读代码的推荐顺序

第一次阅读不要从 12 个文件同时开始。按下面顺序：

1. `tests/test_protocol_navigation.py`
   - 先看规则期待什么行为。
2. `src/core/protocol_navigation.py`
   - 看规则如何得到 `allowed` 和新状态。
3. `tests/test_interaction_command.py`
   - 看哪些话算命令、哪些不算。
4. `src/core/interaction_command.py`
   - 看精确匹配实现。
5. `src/core/intent_policy.py`
   - 看为什么 LLM 猜测不能执行。
6. `src/core/unified_dispatch.py`
   - 看目标和权限如何绑定。
7. `tests/test_turn_processors.py`
   - 看真实 `ASRResult` 如何进入集成测试。
8. `web/turn_processors.py`
   - 看状态恢复、导航、Blocks 和 `session_state` 如何组合。
9. `web/turn_application_service.py`
   - 看准备结果如何统一提交。
10. `web/database/turn_store.py`
    - 看 revision 和事务如何保护状态。

每读一个文件，都问四个问题：

```text
它收到什么？
它只负责什么？
它明确不负责什么？
它把什么交给下一层？
```

## 十一、用一句话记住整套设计

```text
“下一步”先被确定性识别并获得有限权限，再由恢复后的方案事实和问题状态决定能否前进，最后把新步骤、用户反馈和持久化状态作为同一个 Turn 一次提交。
```

而本次 Bug 修复可以记成：

```text
没有问题可回答时不能把用户困住；允许继续，但要诚实保留未完成证据。
```
