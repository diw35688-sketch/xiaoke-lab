## 0. 这份文档只讲什么

这份文档只总结当前对话区发生的事情：从第 19 项“工具入口迁移共享记录服务”开始，到第 29 项“记录流式首反馈”为止。

不包含：

- 第 30 项及之后的 Silero VAD 开发；
- 其他对话区在 2026-08-26～29 完成的功能；
- 与本对话无关的项目历史；
- 还没有真实证据支持的推测。

这段对话的主线不是“加了很多功能”，而是逐渐解决三个问题：

```text
第一，多个入口不能各自保存和回复。
第二，屏幕显示和语音播放不能共用一条无授权旁路。
第三，自动测试通过以后，仍要用真实体验发现录音、追问和等待反馈问题。
```

## 1. 先看全局：这段对话完成了哪条链

### 白话

最开始，网页录音、聊天工具和普通聊天像三个各自做饭的厨房。每个入口都可能自己理解、自己保存、自己回复、自己决定要不要念出来。这样修复一个入口，另一个入口仍可能保留旧问题。

我们逐步把它整理成：

```text
不同入口负责接收用户输入
        ↓
共享记录服务负责理解和保存
        ↓
呈现计划决定哪些内容显示、哪些内容有语音资格
        ↓
播放调度器决定此刻是否允许播放
        ↓
浏览器只执行正式授权
```

随后真实验收又发现：

```text
录音按钮变红不等于真的在录音
语音开关不等于立即静音
模型生成追问不等于追问一定到达页面
服务正在计算不等于用户能及时看到反馈
```

### 专业设计

这条主线涉及五种设计思想：

1. **应用服务**：把一次完整业务用例集中到一个服务中。
2. **适配器**：不同入口只负责把自己的输入转换成共享命令。
3. **关注点分离**：屏幕呈现、内容资格、播放时机、浏览器执行分别负责。
4. **提交后副作用**：保存成功以后才能告诉用户“已记录”或提出挂接于该记录的追问。
5. **证据分级**：自动测试通过与真实浏览器体验通过是不同结论。

### 代码总图

```text
网页录音
web/frontend/voice_asr.js
        ↓ POST /record 或 /record/stream
web/api/record.py
        ↓ RecordCommand
web/record_service.py
        ↓ SharedRecordResult / PresentationIntent
WebRenderer / PresentationDeliveryPlan
        ↓ voice delivery candidate
web/playback_runtime.py
        ↓ READY / DEFERRED / DROP / PREEMPT
web/frontend/voice_delivery_client.js
        ↓
window.enqueueSpeech / stopSpeech / speak
```

聊天工具入口走：

```text
web/agent/core.py
→ web/lab_tools.py
→ web/record_service.py
→ web/tool_presentation.py
→ web/playback_runtime.py
```

## 2. 第 19 项：工具入口迁移共享记录服务

### 一句话结果

聊天工具里的“记录实验”不再自己实现一套抽取和保存，而是与网页 `/record` 共用 `SharedRecordService`。

### 白话理解

网页录音和聊天工具相当于两个前台。以前两个前台都可能自己跑去仓库记账。现在它们只负责填写统一单据，再交给同一个后台处理。

用户在聊天里说：

> 帮我记录，加入五毫升缓冲液。

发生的是：

```text
Agent 判断需要调用 record_observation
→ lab_tools 接到工具参数
→ 构造 RecordCommand
→ SharedRecordService 统一分配段号、理解、评估和保存
→ 工具返回原有五字段结果
```

### 专业设计

`SharedRecordService` 是**应用服务（Application Service）**。它负责“一次实验记录”这个用例的业务顺序。

`/record` 和 `record_observation` 是**入口适配器（Inbound Adapter）**。它们可以接受不同协议，但不应该各自掌握业务规则。

服务通过外部传入保存函数、评估器和抽取器，这叫**依赖注入（Dependency Injection）**。好处是测试时可以使用 Fake，而不用连接真实模型或数据库。

### 代码对照

- 工具入口：`web/lab_tools.py`
- 共享服务：`web/record_service.py`
- 输入合同：`RecordCommand`
- 输出合同：`SharedRecordResult`
- 相关测试：`tests/test_shared_record_service.py`、工具相关测试

阅读代码时先找：

```python
SharedRecordService.record(...)
```

然后检查 `lab_tools.py` 是否还保留了另一套段号、抽取、评估和保存。如果入口仍重复这些步骤，就说明迁移不完整。

### 为什么重要

统一的是业务成功定义，不是所有页面格式。如果两个入口分别保存，以后修复“保存失败不能回复成功”时，很容易只修一个入口。

### 当时的证据

工具专项和相邻记录/呈现回归 `104/104` 通过。该证据证明自动测试覆盖的工具迁移行为，没有证明真实浏览器和真实模型体验。

## 3. 第 20 项：工具结果使用确定性呈现

### 一句话结果

记录工具保存成功后直接使用呈现计划生成回复，不再让大模型第二次自由改写结果。

### 白话理解

后台已经明确知道：

```text
记录是否成功
缺少哪些字段
是否需要追问
追问内容是什么
```

这时如果再让模型“根据工具结果自由回复”，模型可能把一句准确结果改成另一种意思。

新流程是：

```text
共享记录服务产生语义意图
→ PresentationDeliveryPlan 规划呈现
→ WebRenderer 生成固定结构和文案
→ Agent 直接输出
```

### 专业设计

这叫**确定性投影（Deterministic Projection）**：结构化业务结果按照固定规则变成用户界面内容。

其中：

- `PresentationIntent` 表达“系统想告诉用户什么”；
- `PresentationDeliveryPlan` 表达“屏幕和语音各有哪些内容”；
- `WebRenderer` 表达“Web 页面需要什么 JSON 和文案”。

这体现了**关注点分离（Separation of Concerns）**。

### 代码对照

- 工具包装：`web/lab_tools.py`
- 呈现适配：`web/tool_presentation.py`
- Agent 执行：`web/agent/core.py`
- 关键类型：`PresentedToolResult`
- 关键路径：`_run_tool_with_presentation()`

阅读时重点检查：工具成功以后是否又调用一次模型。如果仍存在第二次模型补写，确定性呈现就没有真正闭环。

### 为什么重要

模型适合做语义理解，不适合替代已经确定的保存事实。保存结果必须稳定，否则用户可能听到与数据库事实不一致的话。

### 当时的证据

核心与记录/呈现相邻回归 `111/111`，流事件合同 `7/7`。当时受 Python 环境问题影响，不能把未运行的全量测试写成通过。

## 4. 第 21 项：普通聊天正文只负责上屏

### 一句话结果

普通助手正文改为 `screen_delta`，只更新屏幕，不再隐式获得播放权。

### 白话理解

一段文字出现在页面上，只能说明：

> 这段内容应该让用户看见。

不能自动说明：

> 现在应该从扬声器念出来。

新流程是：

```text
服务端产生普通正文
→ 包装为 screen_delta
→ 浏览器更新 reply.textContent
→ 不检查 TTS 开关
→ 不调用 enqueueSpeech
```

### 专业设计

这是**事件语义单一化**：一个事件只表达一种意思。

也可以用**能力安全（Capability-based Security）**理解：拿到文本数据不代表拿到了操作扬声器的能力。

`screen_delta` 是显示事件，不是播放命令。

### 代码对照

- 事件合同：`web/stream_contract.py`
- SSE 路由：`web/api/chat.py`
- 当前前端：`web/frontend/streaming_chat_v2.js`
- 关键构造器：`agent_chunk_event()`、`screen_delta_event()`

阅读时搜索：

```text
screen_delta
enqueueSpeech
window.speak
```

确认 `screen_delta` 分支内不存在播放调用。

### 为什么重要

如果普通正文可以直接播报，后面的优先级、用户讲话保护和延后队列都会被绕过。

### 当时的证据

组合回归 `124/124`，JavaScript 语法检查通过。未证明真实浏览器 SSE 和扬声器行为。

## 5. 第 23、22、24 项：删除旧旁路，建立新语音事件

### 一句话结果

旧的 `delta` 和 `task_queued` 不能再直接发声；语音内容改由独立 `voice_delivery` 事件承载。

### 为什么顺序是 23 → 22 → 24

本对话中用户先要求第 23 项，所以先删除 `delta → enqueueSpeech` 旁路，再回头完成第 22 项后端事件，最后处理第 24 项 `task_queued` 旁路。

任务编号顺序和实际施工顺序不完全相同，但计划没有错误地把未完成的第 22 项标成完成。

### 白话理解

旧系统像有多条没有门卫的侧门：

```text
普通 delta 能直接念
task_queued 能直接念
某些消息里的 voice_text 也能直接念
```

即使正门已经建立调度规则，侧门仍会让语音绕过检查。

新流程是：

```text
屏幕内容照常显示
→ 可播内容进入 ToolVoiceDeliveryBatch
→ 同轮多个计划先合并
→ 重新计算整轮语音预算
→ 发送 voice_delivery 候选事件
```

### 专业设计

旧路径叫**旁路（Bypass）**或**影子执行路径（Shadow Execution Path）**。

第 22 项还区分了：

- **内容资格（Eligibility）**：这句话适不适合播；
- **运行时授权（Runtime Authorization）**：当前时刻能不能播。

`CONTENT_ELIGIBLE` 只说明内容合格，不等于 `READY`。

同轮计划合并后重新计算预算，是为了防止三个工具各自都认为自己可以播一条问题，最后一轮播三条。

### 代码对照

- 当前前端：`web/frontend/streaming_chat_v2.js`
- 遗留前端：`web/frontend/streaming_chat.js`
- 语音批次：`web/tool_presentation.py`
- Agent 类型化输出：`web/agent/core.py`
- 流事件映射：`web/stream_contract.py`
- SSE 发送：`web/api/chat.py`

建议全局搜索副作用出口：

```powershell
rg "enqueueSpeech|window\.speak|/tts" web
```

不能只检查新入口存在，还要检查旧入口是否仍能产生同样副作用。

### 为什么重要

统一架构最常见的假完成，就是新路径已经有了，旧路径却仍能工作。只有封住旁路，Scheduler 才可能成为真正的唯一权威。

### 当时的证据

- 第 23 项组合回归 `125/125`；
- 第 22 项组合回归 `130/130`；
- 第 24 项针对性 `24/24`、组合回归 `133/133`；
- JavaScript 语法检查通过。

这些证据不能证明真实扬声器已经服从运行时状态。

## 6. 第 25 项：浏览器只执行明确授权

### 一句话结果

浏览器有了唯一语音事件入口，只有 `READY` 或 `PREEMPT` 才会操作 TTS。

### 白话理解

浏览器收到事件以后先当门卫：

```text
检查事件结构
→ 检查 intent_id、kind、priority 和 voice_text
→ 检查用户是否启用语音
→ 根据 authorization 决定
```

具体行为：

```text
CONTENT_ELIGIBLE → 只是候选，不播放
DEFERRED         → 等待，不播放
DROP             → 丢弃，不播放
READY            → enqueueSpeech
PREEMPT          → stopSpeech，再播放替代内容
未知或坏数据     → 拒绝
```

### 专业设计

`voice_delivery_client.js` 是浏览器侧的**执行端口（Execution Port）**和**防腐层（Anti-corruption Layer）**。

它采用**默认拒绝（Deny by Default）**：只有明确允许的状态才产生副作用，未知状态不会“猜测为可以播放”。

这些授权值共同构成一个小型**状态协议（State Protocol）**。

### 代码对照

- 唯一消费入口：`web/frontend/voice_delivery_client.js`
- 加载顺序：`web/app.py`
- 两个流式客户端只委托：`window.consumeVoiceDelivery(data)`
- Node 行为测试：对应 `voice_delivery_client` JavaScript 测试

阅读时不要只看字符串分支，要看真正的副作用调用顺序：

```text
READY 是否只调用 enqueueSpeech？
PREEMPT 是否先 stop，再 speak/enqueue？
候选状态是否零调用？
```

### 为什么重要

执行端是最后一道安全边界。如果它对未知状态也播放，后端一个拼写错误就可能触发扬声器。

### 当时的证据

专项 Python `27/27`、组合回归 `136/136`，Node spy 行为测试通过。

## 7. 第 26 项：三个入口接入同一个播放调度器

### 一句话结果

网页记录、聊天工具和浏览器执行开始共用 `PlaybackScheduler`，但服务器当时仍不知道浏览器真实的讲话和播放状态。

### 白话理解

现在三个入口把播放请求交给同一个调度员：

```text
VoiceDeliveryItem
→ WebPlaybackService
→ PlaybackRequest（带 20 秒 TTL）
→ PlaybackScheduler
→ 浏览器 voice_delivery
```

但是调度员所在服务器当时没有收到：

```text
用户是否正在讲话
音频片段是否还在采集
ASR 是否正在处理
浏览器是否真的正在播放
```

所以生产环境默认快照仍可能是空闲。

### 专业设计

这是**集中式调度（Centralized Scheduling）**与**分布式状态一致性（Distributed State Consistency）**问题。

浏览器拥有设备事实，服务器拥有队列和业务优先级。只有两端通过正式事件同步，服务器的判断才基于现实。

`PlaybackRequest` 的 TTL 是**时效性约束**：过时的提示不能在很久之后突然播放。

### 代码对照

- Web 播放服务：`web/playback_runtime.py`
- 记录路由：`web/api/record.py`
- chat 路由：`web/api/chat.py`
- Agent 工具链：`web/agent/core.py`
- 桌面记录：`web/frontend/voice_asr.js`
- 手机记录：`web/frontend/mobile.js`
- 执行端口：`BrowserPlaybackExecutionPort`

### 为什么重要

“所有请求经过 Scheduler”只能证明路径统一，不能证明 Scheduler 的输入状态是真实的。因此此时不能宣称“不抢话”已经真实完成。

### 当时的证据

纯调度/事件专项 `18/18`、相邻回归 `31/31`、Node 行为测试通过。FastAPI 部分曾受 Python ABI 环境影响，未运行的测试不能算通过。

## 8. 第 27 项：用自动测试冻结架构职责

### 一句话结果

语音链路的重要职责和禁止旁路被写成自动测试，防止以后无意中恢复旧直播代码。

### 白话理解

文档写着“不能从正文直接播报”，但以后维护者可能顺手加回：

```javascript
enqueueSpeech(text)
```

所以需要测试自动检查：

```text
DeliveryPlan 不读取运行状态
Gate 只决定，不播放
/record 和 chat tool 共用播放服务
记录客户端只消费授权事件
正文和 done 不能直接发声
合法后台通知例外仍然保留
```

### 专业设计

这种测试叫**架构适应度函数（Architecture Fitness Function）**。

普通单元测试检查函数结果；架构测试检查：

- 依赖方向；
- 唯一入口；
- 禁止调用；
- 允许的例外。

### 代码对照

- 架构护栏：`tests/test_c5_architecture_freeze.py`
- 被检查前端：`web/frontend/streaming_chat_v2.js`、`streaming_chat.js`
- 相关模块：DeliveryPlan、Coordinator、ContextFactory、Gate、Scheduler

### 为什么重要

大型系统退化经常不是算法算错，而是原本分离的职责重新混合。架构测试能够在真实体验出错以前发现这种退化。

### 当时的证据

冻结专项 `20/20`、C5 组合回归 `190/190`。当时项目全量 discover 出现 17 个导入环境错误，没有被写成业务测试失败，也没有被伪报为全量通过。

## 9. 真实验收第一课：按钮变红不等于录音成功

### 一句话结果

真实体验发现录音按钮能变红但没有开始录音，说明 UI 状态和真实媒体状态没有被同时证明。

### 白话理解

用户点击录音键以后看到红色，只能证明前端执行了样式变化。

完整录音链还需要：

```text
浏览器获得麦克风权限
→ MediaStream 中存在活动音轨
→ 持续产生音频帧
→ 音频被提交给 ASR
→ ASR 返回文字
```

任何一步失败，都可能出现“按钮看起来在录，实际没有数据”。

### 专业设计

按钮颜色属于**表示状态（Presentation State）**，麦克风和媒体流属于**设备状态（Device State）**。

点击后先显示成功状态属于**乐观 UI（Optimistic UI）**。乐观 UI 适合容易成功且可回滚的操作，但设备权限和媒体初始化需要真实确认。

### 代码对照

- 桌面录音：`web/frontend/voice_asr.js`
- 页面与脚本注入：`web/app.py`
- 麦克风 API：浏览器 `getUserMedia` 和相关录音处理
- ASR 路由：`web/api/asr.py` 及其后端调用

### 你应该怎样验收

不要只看按钮颜色，要依次确认：

1. 浏览器权限是否允许；
2. MediaStream 音轨是否 active；
3. 是否产生音频数据；
4. 是否发出 ASR 请求；
5. 是否返回转写结果。

## 10. 真实验收第二课：语音开关不等于立即静音

### 一句话结果

喇叭控件表达的“允许后续播报”和用户期待的“立即停止当前声音”是两个不同能力，当时 UI 没有清楚区分。

### 白话理解

关闭语音开关可能只是告诉系统：

> 从现在起，不要再播放新的语音。

而“立即静音”要求执行：

> 立刻停止当前 Audio/TTS。

前者修改配置，后者执行命令。

### 专业设计

这是**配置状态（Configuration State）**和**运行时命令（Runtime Command）**的区别。

- `tts_enabled=false` 影响未来请求；
- `stopSpeech()` 对当前播放产生即时副作用。

UI 图标是否让用户理解这个区别，属于**可供性/可发现性（Affordance/Discoverability）**。

### 代码对照

- TTS 设置：`web/frontend/tts_settings.js`
- 设置同步：`web/frontend/settings.js`
- 本地播放：`web/frontend/local_tts.js`
- 授权执行：`web/frontend/voice_delivery_client.js`
- 喇叭控件：`web/app.py`

### 为什么重要

代码里存在 `stopSpeech()`，不等于页面已经向用户提供“立即静音”。内部能力和用户可用功能必须分开验收。

## 11. 真实验收第三课：方案模式会追问，不代表自由模式也会

### 一句话结果

方案确认中的追问仍然工作，把问题范围缩小到自由实验，而不是整个 clarification 系统失效。

### 白话理解

实验方案模式有明确步骤，可以用确定性规则问：

> 这一步加热了多长时间？

自由实验没有方案步骤，需要统一理解根据当前口述判断：

> 你说了“加热样品”，但没说时长，所以我要追问。

一个模式正常、另一个模式异常，说明共享的追问显示能力大概率还在，问题更可能发生在模式判断或评估覆盖。

### 专业设计

这种排查叫**差分诊断（Differential Diagnosis）**或**故障域隔离（Fault-domain Isolation）**。

方法是比较正常路径和异常路径，找出最小差异：

```text
相同：保存、clarification、Web 呈现
不同：free/protocol 模式及追问来源
```

### 代码对照

- 模式与评估选择：`web/record_service.py`
- clarification 测试：`tests/test_clarification_acceptance.py`
- 方案评估器：共享服务注入的 protocol evaluator

## 12. 第 28 项：自由实验追问为什么消失，怎样修复

### 一句话结果

统一理解已经生成追问，但 Web 桥没有完整传递，随后自由模式空方案评估覆盖了它；修复后自由模式保留语义追问，方案模式仍保留确定性权威。

### 白话理解

用户说：

> 加热样品。

模型可能已经得到：

```json
{
  "missing_fields": ["duration"],
  "should_ask_follow_up": true,
  "follow_up_question": "样品加热了多长时间？"
}
```

但旧链路发生两个问题：

```text
问题 1：Web 桥只保留实体，没有完整转交追问合同
问题 2：自由模式方案评估返回“无追问”，覆盖模型的语义追问
```

所以页面只剩：

> 已记录。

修复后的链路：

```text
统一理解生成追问
→ llm_bridge 完整透传字段
→ _select_effective_evaluation 判断当前权威来源
→ free + experiment + 非降级 + 合同完整：采用语义追问
→ protocol：继续采用确定性方案评估
→ 保存当前记录
→ 保存成功后生成 clarification
```

### 专业设计一：数据合同保真

上游有字段，下游适配器没有映射，叫**数据合同漂移（Data Contract Drift）**或**信息丢失（Information Loss）**。

排查时不要从最终页面直接猜“模型没生成”，应该沿字段生命周期检查：

```text
在哪里产生
→ 在哪里转换
→ 在哪里覆盖
→ 在哪里保存
→ 在哪里呈现
```

这种只围绕特定字段阅读代码的方法叫**程序切片（Program Slicing）**。

### 专业设计二：权威来源

当模型评估和方案评估冲突时，需要明确**Source of Truth**：

| 条件 | 最终追问权威 |
|---|---|
| 自由实验、正常 experiment、合同完整 | 统一语义追问 |
| 方案模式 | 确定性方案评估 |
| 模型降级 | 原有确定性/默认评估 |
| control/uncertain | 不提升模型追问权限 |

这不是“哪个字段有值就用哪个”，而是正式的**冲突解决规则**。

### 专业设计三：提交后副作用

追问针对的是刚才保存的记录。如果保存失败却已经问：

> 加热了多长时间？

用户回答“10 分钟”时，系统没有可靠的上一条记录可补充。

因此必须：

```text
先 save_record
→ 再构造 RecordObservationResult
→ 再生成 clarification intent
→ 再显示或申请播放
```

这叫**提交后副作用（Post-commit Side Effect）**。

### 代码对照

- 字段桥接：`web/llm_bridge.py::_event_view()`、`extract()`
- 权威选择：`web/record_service.py::_select_effective_evaluation()`
- 保存后结果：`web/record_service.py::_shared_result_after_save()`
- 桥测试：`tests/test_web_llm_bridge.py`
- 自由模式测试：`tests/test_shared_record_service.py::test_free_mode_preserves_unified_follow_up_after_save`
- 方案保护测试：`test_protocol_mode_keeps_deterministic_follow_up_authority`

### 怎样自己读这段代码

先搜索：

```powershell
rg -n "missing_fields|should_ask_follow_up|follow_up_question" web tests
```

然后画出字段表：

| 层 | 输入是否存在 | 输出是否存在 | 是否可能覆盖 |
|---|---:|---:|---:|
| UnifiedUnderstanding | 是 | 是 | 否 |
| llm_bridge | 检查 | 检查 | 映射可能丢失 |
| record_service | 检查 | 检查 | evaluation 可能覆盖 |
| saved record | 检查 | 持久化 | 保存失败中断 |
| presentation | 检查 | clarification | 必须位于保存后 |

### 当时的证据

## 13. 为什么同时保存记录和抽取实体

### 一句话结果

原始记录保存“用户实际说了什么”，实体抽取保存“系统如何理解这句话”，缺失字段和追问保存“还需要补什么”；三者不能互相替代。

### 白话理解

用户说：

> 加热样品。

可以保存三层信息：

```text
原始事实：transcript = 加热样品
结构理解：action = 加热，object = 样品
待补信息：missing_fields = duration
```

后续用户说：

> 10 分钟。

系统才能知道这个“10 分钟”是补充上一条记录的时长。

### 专业设计

这是**原始事实（Raw Fact）**、**派生数据（Derived Data）**和**未完成状态（Pending State）**的分层。

- transcript 是最可信原始证据；
- entities 是可重新计算的推断；
- missing_fields/follow_up 是对话继续所需的状态。

模型失败时不能覆盖或删除原始事实，这属于**证据保真（Evidence Preservation）**。

### 代码对照

- 原始文本和实体保存：`web/record_service.py`
- 统一理解桥：`web/llm_bridge.py`
- 追问结果：`RecordObservationResult`
- 持久化入口：注入到共享服务的 `save_record`

## 14. 为什么第一句回复慢

### 一句话结果

旧 `/record` 在页面第一次更新前串行等待 ASR、统一理解完整 JSON、评估、保存和最终响应，其中近期模型理解约耗时 3.42～4.73 秒。

### 白话理解

旧流程：

```text
录音结束
→ ASR 转写
→ 调用 /record
→ 等模型完整理解
→ 等结构校验
→ 等保存
→ 生成消息
→ HTTP 全部返回
→ 页面第一次变化
```

用户不知道系统是在正常理解，还是按钮失效，所以主观等待比实际时间更难受。

### 专业设计

要区分：

- **端到端延迟（End-to-end Latency）**：从用户结束说话到最终结果；
- **首次反馈延迟（Time to First Feedback）**：到用户第一次看到系统响应。

第 29 项主要降低第二种，不是假装模型计算时间消失。

在优化前先读取 `llm_seconds`，属于**可观测性驱动优化（Observability-driven Optimization）**。

### 代码对照

- 录音前端：`web/frontend/voice_asr.js`
- 记录路由：`web/api/record.py`
- 模型桥：`web/llm_bridge.py`
- 事务编排：`web/record_service.py`
- 耗时字段：`llm_seconds`

## 15. 第 29 项：安全的流式首反馈

### 一句话结果

浏览器在最终分析完成前先看到“正在理解实验内容…”，但“已记录”和追问仍然只在保存成功后出现。

### 白话理解

新流程：

```text
ASR 返回转写
→ 页面显示“正在连接理解服务…”
→ POST /record/stream
→ 服务端先发 record_status
→ 页面显示“正在理解实验内容…”
→ 服务端继续完整理解和保存
→ 成功：record_result
→ 失败：record_error，并结束
```

### 为什么不做模型逐字流式

记录链不是普通聊天，它要得到完整结构：

```text
entities
missing_fields
follow_up_question
evaluation
```

半截 JSON 不能安全进入保存事务。提前流出：

> 已经帮你记录……

随后保存失败，就会制造虚假成功。

所以本项流的是**进度状态**，不是结构化业务结果的 token。

### 专业设计

接口使用 **NDJSON（Newline-delimited JSON）**：每行是一个完整 JSON 事件。

例如：

```json
{"type":"record_status","phase":"understanding","text":"正在理解实验内容…"}
{"type":"record_result","data":{"messages":[]}}
```

浏览器网络读取不保证一次正好得到一行，可能收到：

```text
第一块：{"type":"record_sta
第二块：tus",...}\n
```

所以前端需要：

- `ReadableStream.getReader()` 增量读取；
- `TextDecoder` 解码字节；
- 行缓冲拼接不完整分片；
- 只对完整行执行 JSON 解析。

这叫**消息分帧（Message Framing）**。

`record_status` 是**非承诺型进度事件**；`record_result` 是**提交后最终事件**。

### 代码对照

- 流接口：`web/api/record.py::record_stream()`
- 事件生成：`web/api/record.py::_record_events()`
- 旧兼容接口：`POST /record`
- 桌面读取：`web/frontend/voice_asr.js::streamRecord()`
- 手机读取：`web/frontend/mobile.js::postRecord()`
- 顺序测试：`tests/test_web_record_messages.py`
- 前端合同测试：`tests/test_frontend_screen_delta.py`、手机页相关测试

### 关键失败边界

保存成功：

```text
record_status
→ record_result
```

保存失败：

```text
record_status
→ record_error
→ 结束
```

失败路径绝不能再发送：

```text
record_result
成功回执
播放授权
```

### 当时的证据

- 流式/统一理解专项 `44/44`；
- C5、手机页、record、前端合同复验 `40/40`；
- 当时全量 `1017/1017`；
- 两份 JavaScript 语法检查通过；
- 真实浏览器是否立即显示分块及主观体感仍需用户裁决，因此为 `AUTO_OK`。

## 16. 这段对话教会我们的读代码方法

### 第一步：先写一个可验证问题

不要写：

> 看懂追问系统。

要写：

```text
用户输入：加热样品
预期结果：询问加热时长
实际结果：只显示已记录
追踪字段：missing_fields、follow_up_question
```

这叫建立**可证伪假设（Falsifiable Hypothesis）**。

### 第二步：从用户入口沿调用链阅读

```text
按钮或聊天输入
→ JavaScript 事件处理
→ fetch/SSE URL
→ FastAPI 路由
→ 应用服务
→ 状态或数据库
→ 呈现和副作用
```

不要从文件第一行漫读到最后一行。

### 第三步：每一层只问两个问题

```text
它收到了什么？
它输出了什么？
```

找到“输入仍正确、输出第一次错误”的层。这是**故障域隔离**。

### 第四步：同时追踪数据、状态和副作用

| 类型 | 本项目例子 | 核心问题 |
|---|---|---|
| 数据 | follow_up_question | 在哪里产生和丢失？ |
| 状态 | free/protocol、READY | 谁拥有和更新？ |
| 副作用 | save、enqueueSpeech | 哪一行真正改变外部世界？ |

存在 `voice_text` 不等于已经播放；真正副作用是 `enqueueSpeech()`、`window.speak()` 等调用。

### 第五步：把复杂条件改写成决策表

例如第 28 项：

| 模式 | 模型正常 | 输入类型 | 追问合同 | 采用结果 |
|---|---:|---|---:|---|
| free | 是 | experiment | 完整 | 语义追问 |
| free | 否 | experiment | 任意 | 原评估 |
| protocol | 任意 | experiment | 任意 | 方案评估 |
| 任意 | 任意 | control | 任意 | 不提升追问 |

这叫**决策表（Decision Table）**，比逐行记住多个 `if` 更容易审查。

### 第六步：先读测试的 Arrange–Act–Assert

```text
Arrange：准备了什么冲突条件？
Act：调用哪个公共入口？
Assert：最终哪个来源获胜？
```

第 28 项好测试不是简单断言“有追问”，而是故意构造：

```text
模型说要追问
方案空评估说不用追问
当前是 free
```

然后验证语义追问被保留。

### 第七步：按证据等级写结论

```text
静态检查
→ 单元测试
→ 模块集成
→ 全量回归
→ 真实浏览器/麦克风/扬声器验收
```

低层证据不能自动替代高层证据。
