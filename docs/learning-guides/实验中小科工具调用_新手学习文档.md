# 实验中“小科”工具调用：新手学习文档

> 本文只总结本次对话中设计、实现和验收的内容。目标是同时讲清楚“用户看到什么”“系统为什么这样设计”以及“具体代码在哪里”。

## 1. 最终实现了什么

在“自由实验记录”和“方案实验”中，用户可以用句首“小科”明确发出工具指令：

- “小科，现在几点？”
- “小科，帮我计时10分钟。”
- “小科，还有多久？”
- “小科，现在做到哪一步了？”
- “小科，查一下盐酸的安全性。”
- “小科，查看当前方案详情。”
- “小科，做这个实验前要准备什么？”
- “小科，NaCl的分子量是多少？”
- “小科，把1 M母液稀释成0.1 M，共500 mL。”
- “小科，你现在能做什么？”

这些指令会产生工具卡片和语音回复，但不会写入实验记录。

没有“小科”前缀的普通实验口述继续走原来的记录链。例如：

```text
加入50微升缓冲液，在37℃加热10分钟。
```

这句话仍然作为实验事实保存，不会因为包含“10分钟”就误启动计时器。

## 2. 为什么需要“小科”前缀

### 2.1 白话解释

实验过程中，同一句话可能有两种完全不同的意思：

```text
“加热10分钟”
```

可能表示：

1. 我刚刚完成了加热，需要保存实验事实；
2. 请系统帮我启动一个10分钟计时器。

如果全部交给大模型猜，模型可能选错。一旦选错，就可能漏记实验事实。

所以系统约定：

```text
小科，帮我计时10分钟  → 工具指令
加热10分钟              → 实验记录
```

### 2.2 专业设计

“小科”是一个确定性的意图门控（deterministic intent gate）。它先于模型运行，用明确语法把输入分为两条路径：

```text
实验输入
├─ 句首“小科/小科小科” → 实验工具Agent
└─ 其他输入             → 原统一实验理解链
```

这样做的关键价值是：模型只在用户明确授权工具语义后参与工具选择，不能从普通实验事实中抢走请求。

## 3. 从用户说话到工具执行的完整流程

以“小科，查一下盐酸的安全性”为例：

```text
用户语音或文字
    ↓
获得ASR原文
    ↓
ExperimentToolCommandParser检查句首“小科”
    ↓
提取 command_text = “查一下盐酸的安全性”
    ↓
从工具注册表筛选 experiment_command=True 的工具
    ↓
把指令和允许的工具定义发给模型
    ↓
模型返回 tool_call：check_reagent_safety({"reagent":"盐酸"})
    ↓
后端再次检查该工具是否允许在实验中执行
    ↓
执行真正的Python函数
    ↓
工具结果作为 role=tool 返回模型
    ↓
模型生成简短口语回复
    ↓
后端构造用户文字、工具卡、助手文字和VOICE块
    ↓
页面显示并由TTS朗读
```

这里有一个重要区别：模型只负责“选择工具和填写参数”，真正执行工具的是后端Python代码。

## 4. 第一步：识别“小科”前缀

文件：`src/core/experiment_tool_command.py`

核心类型：

```python
@dataclass(frozen=True)
class ExperimentToolCommand:
    matched: bool
    raw_text: str
    command_text: str | None = None
```

三个字段的含义：

| 字段 | 白话含义 | 专业作用 |
|---|---|---|
| `matched` | 是不是小科工具指令 | 路由判定 |
| `raw_text` | 用户完整原话 | 保留审计证据 |
| `command_text` | 去掉“小科”后的内容 | 交给工具Agent理解 |

解析器只匹配句首，并允许常见标点和空白：

```python
_PREFIX = re.compile(
    r"^\s*(?:小科小科|小科)(?:\s|[，,。.!！?？:：、])*"
)
```

示例：

```text
小科小科，帮我计时10分钟。😔
```

解析结果：

```text
raw_text     = 小科小科，帮我计时10分钟。😔
command_text = 帮我计时10分钟。
```

而下面这句话不会命中：

```text
加入小科试剂10毫升
```

## 5. 第二步：在实验主流程前分流

文件：`web/turn_processors.py`

类：`ExperimentProcessor`

入口逻辑可以简化理解为：

```python
tool_command = ExperimentToolCommandParser.parse(turn.raw_text)

if tool_command.matched:
    return self._prepare_tool_turn(...)

return 原来的实验统一理解流程
```

这里必须在实验事实被保存之前分流，否则“小科，计时10分钟”可能先被记成一条实验事实。

工具路径返回的`PreparedTurn`明确不包含：

```text
lab_record
experiment_events
session_state
segment_id
```

因此工具指令不会污染实验账本，也不会更新追问状态。

## 6. 第三步：工具如何注册

文件：`web/lab_tools.py`

工具通过`@tool(...)`装饰器注册：

```python
@tool(
    "start_timer",
    "启动一个计时器……",
    {
        "type": "object",
        "properties": {
            "duration_seconds": {"type": "integer"},
            "label": {"type": "string"},
        },
        "required": ["duration_seconds"],
        "additionalProperties": False,
    },
    kind="execute",
    title="启动计时器 {label}",
    experiment_command=True,
)
def _start_timer(duration_seconds, label=None):
    ...
```

一次注册同时声明：

| 项目 | 用途 |
|---|---|
| 工具名称 | 模型返回哪个函数名 |
| 工具描述 | 告诉模型什么情况下调用 |
| JSON Schema | 约束参数名称和类型 |
| Python处理函数 | 真正执行查询或操作 |
| `kind/title/present` | 决定工具卡如何展示 |
| `experiment_command` | 决定是否允许在实验中调用 |

## 7. 为什么不再维护第二份白名单

### 7.1 旧设计的问题

第一版除了注册工具，还在`agent/core.py`维护：

```python
EXPERIMENT_TOOL_NAMES = {
    "start_timer",
    "check_timer",
}
```

新增工具需要同时修改两个地方：

```text
lab_tools.py      注册工具
agent/core.py     加入实验白名单
```

如果忘记其中一个，两边就会不同步。

### 7.2 最终设计：单一事实源

现在只在工具定义处声明：

```python
experiment_command=True
```

注册表保存这个字段，然后三个使用方都从同一注册表读取：

```text
experiment_command=True
        ├─ 决定模型能看到哪些工具
        ├─ 决定后端允许执行哪些工具
        └─ 决定能力清单显示哪些工具
```

相关函数：

```python
openai_tools(experiment_commands_only=True)
experiment_command_names()
experiment_command_catalog()
```

这叫单一事实源（single source of truth）。

## 8. 为什么仍然需要两道权限检查

虽然权限只声明一次，但会在两个阶段使用。

### 第一层：模型可见范围

```python
lab_tools.openai_tools(experiment_commands_only=True)
```

未开放的工具不会发送给模型。

### 第二层：执行前检查

```python
if name not in lab_tools.experiment_command_names():
    raise PermissionError(...)
```

即使模型或兼容接口异常返回未授权名称，后端仍然拒绝执行。

这不是两份白名单，而是两个安全检查共用同一份权限事实。

## 9. 第四步：标准Agent工具调用循环

文件：`web/agent/core.py`

函数：`run_experiment_tool_agent(...)`

循环过程是：

```python
messages = [系统规则, 用户指令]

模型请求(messages, tools=实验工具)

if 模型没有返回tool_calls:
    返回模型文字

for 每个tool_call:
    解析名称和参数
    执行工具
    把结果作为role=tool追加到messages

再次请求模型生成最终回答
```

标准协议中的三种关键消息是：

```text
role=user       用户说了什么
role=assistant  模型提出调用哪个工具
role=tool       后端返回真实执行结果
```

模型不能自己启动计时器或读取数据库，只能提出结构化调用请求。

## 10. 工具描述和参数Schema分别解决什么问题

工具描述帮助模型回答：

> 什么时候应该用这个工具？

例如：

```text
用户问“还有多久”“时间到了吗”时调用check_timer。
```

参数Schema帮助程序约束：

> 调用时必须带哪些字段，字段类型是什么？

例如：

```json
{
  "type": "object",
  "properties": {
    "duration_seconds": {"type": "integer"}
  },
  "required": ["duration_seconds"],
  "additionalProperties": false
}
```

它表示：

- 必须提供`duration_seconds`；
- 参数必须是整数；
- 不能随意增加其他字段。

## 11. 计时器如何记住“还有多久”

启动计时器后，工具返回内部`timer_id`。用户不会记住这个ID，所以系统保存当前实验会话最近的计时器：

```python
_latest_experiment_timer[
    (conversation_id, lab_session_id)
] = timer_id
```

当用户说：

```text
小科，还有多久？
```

后端自动查找当前会话最近的计时器，把ID补进`check_timer`参数。

使用`conversation_id + lab_session_id`两个维度，是为了防止不同实验会话串用计时器。

当前边界：这个映射保存在进程内，服务重启后不会恢复。

## 12. 当前方案详情为什么由后端补ID

原始`get_protocol_detail`需要`protocol_id`，但用户只会说：

```text
小科，查看当前方案。
```

模型不应该猜内部ID。

因此，在实验工具环境中，模型看到的是无参数工具：

```json
{
  "properties": {},
  "required": []
}
```

执行时由后端读取当前选择的方案：

```python
state = domain.session()
protocol = state.selection.protocol
safe_args = {"protocol_id": protocol.protocol_id}
```

原则是：模型判断用户想做什么，后端提供当前业务事实。

## 13. “小科，你能做什么”如何实现

工具：`list_experiment_commands`

它不是读取一份手写说明，而是调用：

```python
experiment_command_catalog()
```

从注册表动态列出所有`experiment_command=True`工具。

为了可靠和快速，下面这些明确问法会走本地快速路径：

- 你能做什么
- 你现在能做什么
- 有哪些工具
- 现在有哪些工具
- 支持什么功能
- 现在支持什么功能

本地路径仍然执行清单工具并生成工具卡，只是不额外请求模型。

清单会排除`list_experiment_commands`自己，避免出现无帮助的循环描述。

## 15. 为什么其他工具没有全部开放

新工具默认：

```python
experiment_command=False
```

主要是防止以下能力意外进入现场实验语音：

- 删除方案或配方；
- 修改方案步骤；
- 修改或删除库存；
- 执行终端命令；
- 读取项目源码；
- 自动推进实验步骤。

`record_observation`也没有作为实验工具开放，因为普通实验口述已经由统一实验链强制处理。若再次交给模型决定是否调用，可能出现模型回答成功但实验事实没有保存。

## 16. 工具结果如何变成屏幕和语音

工具Turn包含：

```text
USER_TEXT
TOOL_CARD
ASSISTANT_TEXT
VOICE
```

### 屏幕工具卡

由工具注册时的`present`函数确定，展示详细、结构化、可核对的结果。

例如安全查询卡可显示：

```text
试剂名称
CAS号
是否高危
危险说明
```

### 助手文字和语音

普通工具执行结果会返回模型，由模型生成简短口语回答。随后：

```python
voice_text = outcome.answer
```

因此屏幕卡负责详细证据，语音负责简短结论。

能力清单是例外：它使用后端固定拼接的回答，不依赖第二次模型生成。

## 17. 工具调用后的延迟边界

普通工具当前需要：

```text
第一次模型判断
→ 工具执行
→ 第二次模型总结
→ 提交Turn
→ TTS播放
```

因此工具语音要等完整调用链完成后才开始。目前不是“工具卡刚出现就立刻朗读”，也没有为每个工具全部改成固定语音模板。

如果以后优化延迟，可以让稳定的只读和计算工具使用后端确定性语音，跳过第二次模型请求。但这不在本轮实现范围内。

## 18. 页面模式入口的最终职责

本次还整理了新对话入口：

### 自由聊天

- 用于问答和讨论；
- 不保存实验记录。

### 自由实验记录

- 保存实际操作和测量事实；
- 不绑定方案；
- 支持“小科”工具指令。

### 方案实验

- 无论当前状态如何，都先打开方案页；
- 用户查看或选择方案后再开始实验；
- 不自动沿用或猜测方案。

### AI制作方案/配方

- 留在对话区；
- 通过对话创建或修改实验方案、试剂配方；
- 可以读取文本类上传；
- PDF或图片目前应到方案页导入。

### 制作储存库

- 进入储存库相关工作区。

“方案实验”和“AI制作方案/配方”的区别是：前者选择并执行已有方案，后者创建或修改方案资产。

## 19. PDF和图片上传的真实边界

对话上传接口可以保存文件，`read_uploaded_file`可以读取文本文件的部分内容。

但对于PDF、图片、Word和Excel，它当前只返回提示：

```text
这是二进制/文档文件，建议调用MinerU/OCR接口识别内容。
```

真正的PDF/图片识别链目前接在方案页面：

```text
方案页选择文件
→ /protocols/upload-file
→ MinerU/OCR
→ 生成方案草稿
→ 用户确认保存
```

所以界面文案改为：

```text
通过对话创建或修改实验方案、试剂配方；
可上传文本文件，PDF或图片请到方案页导入。
```

文案只承诺真实已打通的功能。

## 20. 如何新增一个实验工具

以后新增工具只需要在`web/lab_tools.py`定义一次：

```python
@tool(
    "new_tool",
    "说明什么时候使用",
    {
        "type": "object",
        "properties": {},
        "additionalProperties": False,
    },
    kind="read",
    title="新工具",
    experiment_command=True,
)
def _new_tool():
    return {"result": "..."}
```

注册完成后会自动：

1. 出现在模型可见工具列表；
2. 通过后端实验权限检查；
3. 出现在“小科，你能做什么”的动态清单；
4. 复用统一工具卡和工具调用循环。

不需要再修改语音路由中的名称名单。

## 24. 当前已知边界

1. 普通工具语音需要等待“模型选择 → 工具执行 → 模型总结”完成；
2. 计时器最近引用是进程内状态，服务重启后丢失；
3. PDF和图片在对话上传后不会自动OCR，需要到方案页导入；
4. 安全查询不能替代实验室MSDS和负责人判断；
5. 配液计算依赖用户提供的浓度、体积、纯度等参数；
6. 多浏览器标签页和多设备的完整业务隔离需要单独做真实验收；
7. 自动测试通过不等于麦克风、页面和扬声器真实体验通过。

## 25. 推荐代码阅读路线

按下面顺序阅读最容易理解：

1. `src/core/experiment_tool_command.py`：如何识别“小科”；
2. `web/turn_processors.py`中的`ExperimentProcessor.prepare()`：如何分流；
3. `web/lab_tools.py`中的`tool()`：工具如何注册；
4. `web/lab_tools.py`中的权限和目录函数：如何自动发现；
5. `web/agent/core.py`中的`_experiment_tools()`：模型能看到什么；
6. `web/agent/core.py`中的`_execute_experiment_tool()`：后端如何校验和执行；
7. `web/agent/core.py`中的`run_experiment_tool_agent()`：标准工具调用循环；
8. `web/turn_processors.py`中的`_prepare_tool_turn()`：卡片和语音如何形成；
9. `tests/test_experiment_tool_command.py`：每条安全边界如何被测试保护。

## 26. 一句话总结

这套实现不是让大模型接管实验，而是：

> 用“小科”明确授权工具语义，用注册表统一管理工具和权限，让模型负责自然语言理解，让后端负责真实执行、状态隔离、工具卡和语音交付，同时保留原实验记录链作为事实入口。
