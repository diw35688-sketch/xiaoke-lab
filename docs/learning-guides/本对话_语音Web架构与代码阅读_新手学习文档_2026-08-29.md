# 本对话学习文档：语音 Web 架构与代码阅读

> 范围说明：本文只总结这个对话区里讨论过的内容，不补写其他对话、后续功能或整个项目历史。
>
> 阅读目标：你不只知道“改了什么”，还能够自己沿代码判断 Agent 有没有走偏。

## 1. 一句话理解本对话在做什么

我们不是单独修一个“语音抢话”按钮，而是在建立一条受控链路：系统先分清用户是否还在讲话，再由服务器统一决定某段语音应该立即播放、延后、丢弃还是抢占。

完整主线是：

```text
麦克风产生音频帧
→ VAD 判断讲话边界
→ ASR 把完整音频段转成文字
→ Coordinator 更新服务器运行状态
→ Gate 根据请求和状态作决定
→ Scheduler 执行入队、丢弃或播放
→ TTS 报告真实开始、结束或失败
```

这条链解决两个不同问题：

- **输入理解**：用户什么时候开始说、是在停顿还是已经说完；
- **输出控制**：系统现在是否可以出声。

二者有关，但不是同一件事。

## 2. VAD、ASR 和“用户停顿”到底怎样区分

### 白话理解

用户说：

> “加入……五毫升缓冲液。”

省略号处可能只是用户在想下一句话，并不代表已经说完。

- 麦克风只负责不断交出声音数据；
- VAD 像门卫，只判断有没有人声以及一段话是否结束；
- ASR 像书记员，只把已经封好的音频段写成文字。

所以“暂时没有声音”和“这句话结束了”必须是两个不同事件。

### 专业设计

这叫 **Voice Activity Detection（语音活动检测）**和 **Endpoint Detection（端点检测）**。

本对话把 VAD 事实拆为四类：

```text
讲话开始
短暂停顿
继续讲话
断句完成
```

其中：

```text
短暂停顿 ≠ 音频段完成
用户没出声 ≠ 现在允许 TTS 播放
```

因为短暂停顿期间，当前音频段可能仍在采集，ASR 也可能尚未处理。

### 代码对照

- VAD 稳定合同：`src/core/silero_vad_contract.py`
- 浏览器 Silero 适配：`web/frontend/call_silero_vad.js`
- 连续通话入口：`web/frontend/phone_call.js`
- 音频段组装：`src/audio/vad_segmenter.py`
- 合同测试：`tests/test_silero_vad_contract.py`
- 浏览器行为测试：`tests/js/test_call_silero_vad.js`
- 固定模型样本：`tests/test_vad_real_model_regression.py`

### 你自己怎么检查

看到 VAD 回调后，先检查它产生的是 `PAUSED` 还是 `FINALIZED`，再检查有没有代码直接从“静音”跳到 TTS 播放。如果有，这条链很可能把思考停顿误当成说完。

## 3. 为什么服务器必须知道用户正在讲话

### 白话理解

如果浏览器检测到你开始说话，却只在本地停掉旧声音，没有通知服务器，那么：

```text
浏览器认为：用户正在讲话
服务器认为：现在是空闲
```

服务器随后仍可能批准另一条语音播放。因此，浏览器“听见了你”不等于整个系统“知道你正在讲话”。

### 专业设计

这涉及两个概念：

1. **Single Source of Truth（单一事实来源）**：播放判断必须读取同一份权威状态；
2. **Single Writer（单一写入者）**：所有 VAD、ASR、TTS 事件都由一个 Coordinator 更新状态。

设备或页面不能各自随意修改几个布尔值，否则不同模块会看到互相矛盾的状态。

### 代码对照

- 运行状态与事件归约：`src/core/voice_runtime_state.py`
- 状态测试：`tests/test_voice_runtime_state.py`
- 播放快照工厂：`src/core/playback_context_factory.py`
- 快照测试：`tests/test_playback_context_factory.py`

关键思路是：

```text
旧状态 + 新事件 → 校验 → 生成完整新状态 → 一次性替换
```

这叫 **Reducer（归约器）**和 **Atomic State Transition（原子状态转换）**。

### 你自己怎么检查

搜索谁在修改 `user_speaking`、`segment_capturing`、`asr_processing`、`tts_playing`。正常设计应当让调用方提交事件，而不是到处直接设置这些字段。

## 4. 为什么要把播放拆成 Request、Context、Decision

### 白话理解

播放系统要回答三个不同问题：

1. 想播放什么？
2. 现在现场是什么状态？
3. 最终应该怎么办？

把三个问题混在一个函数里，后面就很难判断“是请求有问题，还是现场状态不允许”。

### 专业设计

#### PlaybackRequest：想播放什么

包含语音内容的身份、重要性、创建时间、有效期和替代键。

代码：`src/core/playback_request.py`

#### PlaybackContext：现在发生什么

包含用户讲话、语音输入忙、TTS 播放和会话阶段等事实。

代码：`src/core/playback_context.py`

#### PlaybackDecision：应该怎么办

```text
READY     立即播放
DEFERRED  现在不播，稍后重评
DROP      永久丢弃
PREEMPT   需要先停止当前播放
```

代码：`src/core/playback_decision.py`

这种拆法叫 **Policy/Execution Separation（策略与执行分离）**。规则只计算决定，不直接碰播放器。

### 你自己怎么检查

打开一个判断函数，问五个问题：

```text
谁调用它？
输入是什么？
输出是什么？
它有没有修改状态？
它有没有产生外部动作？
```

`PlaybackGate` 理想答案是：输入 Request 和 Context，输出 Decision，不改状态，不调用 TTS。

## 5. Gate、Queue、Scheduler 和 TTS 分别负责什么

### 白话理解

可以把它们想成车站：

- Gate 是检票员，只判断能不能走；
- Queue 是候车室，保存现在不能走但稍后可能走的请求；
- Scheduler 是调度员，根据决定安排候车、取消或发车；
- TTS 是列车，只执行播放和停止，并报告真实状态。

### 专业设计与代码对照

| 模块 | 专业职责 | 代码 |
|---|---|---|
| PlaybackGate | 无副作用策略判断 | `src/core/playback_gate.py` |
| DeferredPlaybackQueue | 保存延后请求 | `src/core/deferred_playback_queue.py` |
| Reevaluation | 状态变化后重新判断 | `src/core/playback_reevaluation.py` |
| Expiry | 过期后不再补播 | `src/core/playback_expiry.py` |
| Supersession | 新追问替代旧追问 | `src/core/playback_supersession.py` |
| SessionCancel | 会话结束清理剩余请求 | `src/core/playback_session_cancel.py` |
| PlaybackScheduler | 决定到副作用的唯一编排者 | `src/core/playback_scheduler.py` |
| TTSAdapter | `play/stop` 和执行事件 | `src/core/tts_adapter.py` |
| FailureBoundary | 区分失败类型和重试边界 | `src/core/tts_failure_boundary.py` |

### 为什么 TTS 命令和事件要分开

调用 `stop()` 只代表“要求停止”，不代表声音已经停下。必须收到 `STOPPED` 事件，服务器才能把 `tts_playing` 改成假。

这叫 **Command–Event Separation（命令—事件分离）**。

反面情况是：代码执行 `stop(); play(new)` 两行就认为抢占完成。真实播放器可能还没有停稳，新旧声音就会重叠。

### 你自己怎么检查

沿 `PlaybackScheduler.schedule()` 看四个决定是否只进入一个分支。然后检查 PREEMPT 是否等待匹配的停止事件、重新读取状态并再次经过 Gate，而不是沿用几百毫秒前的旧决定。

## 6. 为什么 `/record`、Tool 和 Chat 必须共用业务核心

### 白话理解

录音入口、Agent 工具和聊天入口像三个前台。它们可以使用不同表单，但“怎样保存记录、什么时候算成功、什么时候可以追问”必须由同一个后厨决定。

### 专业设计

这叫 **Multiple Adapters, One Use Case（多入口、单用例）**。

```text
不同入口
→ SharedRecordService
→ 保存成功
→ 生成呈现意图
→ 形成播放请求
→ 统一 PlaybackScheduler
```

其中保存是 **Transaction Commit Point（事务提交点）**。只有保存成功后，系统才能显示“已记录”或生成追问。

### 代码对照

- 共享记录服务：`web/record_service.py`
- `/record` 入口：`web/api/record.py`
- 工具入口：`web/lab_tools.py`
- 工具结果呈现：`web/tool_presentation.py`
- Chat 入口：`web/api/chat.py`
- Web 播放运行时：`web/playback_runtime.py`
- 共享服务测试：`tests/test_shared_record_service.py`
- 架构冻结测试：`tests/test_c5_architecture_freeze.py`

### 你自己怎么检查

从每个入口向后追，检查它是否只是解析协议并调用共享服务。如果入口自己重新实现保存顺序、追问条件或播放判断，就出现了第二套业务逻辑。

## 7. 为什么屏幕文字不能直接变成语音

### 白话理解

屏幕上出现一句话，只代表“这句话可以看见”，不代表“这句话现在可以念出来”。任务状态、模型增量文字和正式语音是三种不同事件。

### 专业设计

```text
screen_delta   只更新屏幕
task_queued    只报告任务状态
voice_delivery 才携带正式语音授权
```

这叫 **Channel Separation（渠道分离）**和 **Capability Authorization（能力授权）**。

如果前端收到每个 delta 就 `enqueueSpeech`，它会绕过服务器的 PlaybackGate。即使服务器知道用户正在讲话，浏览器仍能自行出声。

### 代码对照

- 流事件合同：`web/stream_contract.py`
- Chat SSE：`web/api/chat.py`
- 屏幕增量消费者：`web/frontend/streaming_chat.js`、`web/frontend/streaming_chat_v2.js`
- 正式语音消费者：`web/frontend/voice_delivery_client.js`
- 语音交付对象：`src/core/voice_delivery.py`

### 你自己怎么检查

搜索所有 `enqueueSpeech`、`window.speak` 或 `/tts` 调用。每一条都要能回答：它是否来自正式 `voice_delivery`？如果不能，就是可能绕开后端许可的旁路。

## 8. 为什么追问字段不能在中间层丢失

### 白话理解

统一理解已经知道“缺少体积”并准备问用户，但 Web 桥接只传了“记录成功”，用户最终就只看到“已记录”，不知道下一步该补什么。

### 专业设计

关键字段要沿整条链保留：

```text
missing_fields
should_ask_follow_up
follow_up_question
```

这叫 **Semantic Preservation（语义保真）**和 **Data Lineage（数据血缘）**：一个信息从哪里产生、经过哪些对象、在哪里保存、最后由谁使用，都应该能够追踪。

并且：

```text
先成功保存
→ 再投影 CLARIFICATION
```

这叫 **Post-commit Projection（提交后投影）**。

### 代码对照

- LLM Web 桥接相关实现
- `web/record_service.py`
- 共享服务和桥接对应测试

### 你自己怎么检查

选一个字段，例如 `follow_up_question`，逐层搜索它。不要只确认“源头有这个字段”，还要检查每一个构造函数、字典映射、序列化和保存对象是否完整传递。

## 9. `/record/stream` 的“流式”到底是什么

### 白话理解

用户提交录音后，不必一直面对空白页面。服务器先说“正在理解”，完成保存后再给最终结果。

```text
record_status / understanding
→ 执行共享记录事务
→ record_result
```

失败时只发 `record_error`。

### 专业设计

这是 **Progressive Feedback（渐进反馈）**和 **NDJSON Streaming（逐行 JSON 流）**。

它只缩短第一次可见反馈时间，不等于：

- ASR 正在逐字输出；
- LLM JSON 正在逐字段输出；
- TTS 已经内容级流式播放。

### 代码对照

- `web/api/record.py`
- 桌面录音前端的 `ReadableStream` 消费代码
- 手机录音入口的 `ReadableStream` 消费代码

### 你自己怎么检查

先列出流中的正式事件，再看每个事件在什么业务事实之后发送。特别检查 `record_result` 是否严格位于保存成功之后。

## 10. 我们如何正确理解测试证据

### 白话理解

测试像不同级别的考试：单元题通过，不代表真实教室、真实麦克风和真实用户体验都通过。

### 专业分级

```text
单元测试
→ 模块集成测试
→ 固定真实模型样本
→ 真实浏览器功能验收
→ 用户体验确认
```

- `AUTO_OK`：自动化覆盖范围内通过；
- `REAL_OK`：记录过的真实环境功能通过；
- `UX_CONFIRMED`：用户确认实际体验清楚、自然、不打扰。

固定 WAV 得到正确音频段，只能证明该文件和参数；不能证明真实房间中的回声、远场讲话和外放自激都没有问题。

### 测试为什么不必每轮全量

这叫 **Risk-based Testing（风险分层测试）**：

- 局部纯规则：专项测试加相邻回归；
- 共享合同、Web 接线、存储、主流程、阶段收口：运行全量；
- 没跑全量时，只报告实际测试，不能写“全量通过”。

### `.venv` 纠错

受限环境出现“拒绝访问”或“无法创建进程”，只证明当前执行边界阻止了启动，不证明 `.venv` 损坏。

专业上叫 **Fault Attribution（故障归因）**。必须先在获准环境用相同项目命令重试，再根据真实解释器、导入或断言错误下结论。

项目规则位置：`CLAUDE.md` 的“项目 `.venv` 与沙箱误判禁止规则”。

## 11. 你自己读代码的六站法

这是本对话最后形成的核心学习方法：

```text
用户入口
→ 核心数据
→ 状态写入者
→ 决策者
→ 副作用执行者
→ 测试证据
```

### 第一步：先写一句预期行为

例如：

> 用户讲话期间，普通提示不能播放；讲话结束后，未过期的延后提示可以恢复。

这句话是你读代码时的尺子。

### 第二步：从用户入口开始

不要先读整个仓库。搜索按钮、URL 或事件名：

```powershell
git grep -n "record/stream"
git grep -n "voice_delivery"
git grep -n "USER_SPEECH"
```

### 第三步：每个函数只问五个问题

```text
谁调用它？
输入是什么？
输出是什么？
它修改什么状态？
它产生什么外部动作？
```

### 第四步：沿数据对象追字段

播放链可以这样追：

```text
PlaybackRequest
→ PlaybackContext
→ PlaybackDecision
→ voice_delivery
→ TTS event
```

检查字段在哪里新增、保留、覆盖或丢失。

### 第五步：找唯一所有者和旧旁路

| 问题 | 应当由谁说了算 |
|---|---|
| 用户是否讲话 | VAD 事件 + VoiceStateCoordinator |
| 当前运行状态 | VoiceRuntimeState |
| 是否允许播放 | PlaybackGate |
| 谁执行决定 | PlaybackScheduler |
| 谁接触播放器 | TTSAdapter |
| 谁定义记录成功 | SharedRecordService |

如果同一问题有两个所有者，或者前端可以绕过后端决定，就要警惕。

### 第六步：反向看测试和失败路径

先读测试名称，再看 Arrange–Act–Assert：

```text
Arrange：准备状态和请求
Act：调用公共接口
Assert：检查唯一主要结果
```

最后专门检查：空输入、字段缺失、保存失败、VAD 失败、TTS 失败、会话结束。

## 12. 你怎样帮助 Agent 不走偏

以后每完成一项，你可以用这十个问题核查：

1. 这一项解决的用户问题是什么？
2. 用户操作从哪个文件进入？
3. 核心数据对象是什么？
4. 谁修改状态？
5. 谁作决定？
6. 谁执行副作用？
7. 有没有旧旁路绕过新设计？
8. 测试覆盖了哪些正常、边界和失败路径？
9. 当前证据不能证明什么？
10. 这一轮是否只完成了一个小而完整的能力？

如果回答只列模块，却没有从用户操作追到最终副作用，说明解释还不完整。

## 13. 本文的证据边界

本文能帮助你：

- 看懂本对话为什么这样拆语音架构；
- 找到第 1～32 项相关的核心代码；
- 自己沿入口、数据、状态、决定和副作用检查实现；
- 区分自动测试、真实验收和体验确认。

本文不能证明：

- 当前工作区后来新增的功能都遵守这些边界；
- 真实浏览器、真实麦克风、房间回声和外放环境已经全部验收；
- 所有可能的 TTS 旁路在后续修改中仍然不存在。

这些结论必须重新读取当前代码并进行与风险相称的测试或真实验收。
