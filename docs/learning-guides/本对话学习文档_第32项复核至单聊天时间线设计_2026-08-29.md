# 本对话学习文档：从第 32 项复核到单聊天时间线设计

> 范围：只整理本对话中讨论、纠偏和形成的设计，不扩写项目更早的历史。  
> 适合：第一次接触语音交互、状态机和前后端消息合同的新手。  
> 阅读方法：先读“白话”，理解用户实际看到什么；再读“专业设计”；最后沿“代码对照”亲自查证。

## 1. 一句话理解我们在做什么

这个系统不只是“把文字变成声音”。它必须同时解决三件事：

1. 用户说话时，助手不能抢话；用户停下后，原本延后的声音要在合适时恢复。
2. 普通聊天、自由实验记录、方案实验记录可以有不同的回答规则，但都应走同一套消息和播放基础设施。
3. 页面只能有一条主要对话时间线，方案、步骤、安全、记录和工具结果都作为聊天中的不同卡片出现，不能聊天框一套、右侧区域再维护一套运行状态。

可以把它想成一家餐厅：

- **Turn/Block** 是统一餐盘和小碟子；
- **Chat、自由实验、方案实验** 是三种不同菜单；
- **PlaybackScheduler** 是出餐口，判断现在能不能播声音；
- **ConversationTurnStore** 是唯一账本；
- 聊天时间线只是把这本账画给用户看。

统一的是“餐盘、账本和出餐规则”，不是强迫三种菜单说同样的话。

## 2. 本对话中最重要的纠正

### 2.1 “一小步”不是“一小段代码”

过去容易把“新增一个事件”“补一个函数”叫作一小步。但从用户角度看，如果功能还不能独立复核，这只是半步。

以后的一小步应当是：**一项边界清楚、从入口到可观察结果完整接通、可以独立验证的能力。**

每次交付应回答：

1. 本轮只解决什么；
2. 修改前真实缺口是什么；
3. 入口文件和入口函数在哪里；
4. 消息带哪些字段；
5. 服务端经过哪些函数；
6. 最终状态在哪里改变；
7. 用户可以运行什么检查；
8. 测试实际输出是什么；
9. 还有哪一段没接通；
10. 唯一下一步是什么。

这也是本文的组织原则：不只给结论，还给一条可以自己走通的复核路线。

## 3. 第 32 项到底解决了什么

### 3.1 白话场景

助手准备说话时，用户又开始讲话。系统不应该把声音硬播出来，而应先延后。用户停止讲话、识别工作也结束后，系统再重新判断：

- 还适合播：`READY`；
- 现在仍不适合：`DEFERRED`；
- 已经过时或不应再播：`DROP`。

而且 A 对话中用户说话，只能影响 A 对话，不能把 B 对话的声音也压住。

### 3.2 32c–32f 的能力拆分

| 小项 | 白话作用 | 专业概念 |
|---|---|---|
| 32c | 同一段话中停顿后又继续说，系统知道“用户又说起来了” | VAD 事件、状态迁移 |
| 32d | 一段语音正式结束后，系统知道识别何时开始、结束或失败 | 异步生命周期、事件驱动 |
| 32e | 每个对话分别保存“用户是否在说、ASR 是否忙”等播放状态 | conversation-scoped state、隔离性 |
| 32f | 浏览器把 TTS 开始、结束、失败反馈给服务端；延后项可重新判定 | 反馈闭环、延迟队列、重新调度 |

### 3.3 专业状态机

一条待播内容不是简单的“播放/不播放”，而要经过：

```text
产生语音候选
    ↓ authorize
READY ─────────────→ 浏览器播放
  │                      ↓
  │                 TTS started/ended/failed
  │
  └→ DEFERRED → 等用户/ASR状态变化 → reevaluate
                                      ├→ READY
                                      ├→ DEFERRED
                                      └→ DROP
```

这里的关键不是事件名字，而是事件确实改变了某个对话专属状态，随后调度器又读取这个状态作出决定。

### 3.4 第 32 项代码对照

| 一跳 | 文件 / 关键函数 | 主要字段或状态 | 你在检查什么 |
|---|---|---|---|
| 浏览器产生语音事件 | `web/frontend/phone_call.js`：`queueVoiceRuntimeEvent` | `user_speech_resumed`、`segment_finalized`、`asr_processing_started/finished/failed` | 浏览器是否真的发出生命周期事件 |
| 服务端接收事件 | `web/api/voice_runtime.py`：`consume_voice_runtime_event` | `conversation_id`、事件类型 | 事件是否按会话进入服务端 |
| 会话运行态入口 | `web/voice_runtime_sessions.py`：`consume`、`coordinator` | 每个 conversation 的运行态 | A、B 会话是否隔离 |
| 播放授权与反馈 | `web/playback_runtime.py`：`authorize`、`reevaluate`、`handle_tts_event` | READY / DEFERRED / DROP、TTS 生命周期 | 延后项是否会重新判断 |
| 调度核心 | `src/core/playback_scheduler.py`：`reevaluate` | 延后队列 | 状态变化是否真正影响候选 |
| 浏览器实际播放反馈 | `web/frontend/voice_delivery_client.js` | started / ended / failed | 浏览器是否把结果反馈回来 |

## 4. 为什么“喇叭开着但没有声音”成为关键发现

### 4.1 当时看到的现象

- 通话已经开启；
- 浏览器喇叭开关已经开启；
- 语音识别成功；
- 聊天区出现了文字回复；
- 但是没有声音。

服务端当时能看到 `/asr/transcribe` 和 `/chat/stream`，却没有进入 `/tts`，也没有 TTS 生命周期事件。

### 4.2 白话结论

这不是“音箱坏了”，而是普通 Chat 回复根本没有生成一张“请播放这段内容”的语音单据。播放调度器即使工作正常，也没有东西可以调度。

### 4.3 专业结论

自动测试此前证明的是：**当 `voice_delivery` 已存在时，系统如何授权、延后、恢复和丢弃。**

它没有证明：**每一种回答生产者都会创建 `voice_delivery`。**

这体现了两个不同的证据层级：

- 组件闭环：已经有候选时，播放策略正确；
- 生产链闭环：Chat、Record、Tool 都真的会产生可播放候选，并与屏幕上的来源 Block 对应。

当时把普通回复临时映射成 `ASSISTANT_REPLY` 是有价值的诊断桥梁，但它复用了实验模式的短句约束，不能直接当作最终 Chat 策略。

## 5. 为什么要“统一外壳，分开策略”

用户最终明确了三种需求：

| 模式 | 用户期望 | 内容策略 |
|---|---|---|
| 自由聊天 Chat | 可以自然交流，回答可完整，仍希望能出声 | 不自动写实验记录；采用自然回答和适合朗读的分句 |
| 自由实验记录 | 保存真实观察，也允许正常追问 | 先保存原始事实；成功后最多追问一个最关键的语义缺口 |
| 方案实验记录 | 严格跟踪方案、步骤、偏差和安全 | 按方案规则判断必填项、偏差、风险和下一动作 |

专业上，这叫作：

- **统一数据合同**：所有输出都成为 Turn/Block；
- **策略模式**：不同交互模式选择不同内容政策；
- **统一投递机制**：语音都经过同一播放调度和浏览器反馈；
- **关注点分离**：回答“说什么”与“什么时候播放”是两件事。

因此，Chat 不需要被实验记录的严格话术绑住，但它的屏幕输出、语音身份、播放授权和反馈仍可以统一。

## 6. 模式与输入方式不能混为一谈

### 6.1 两个正交维度

**交互模式**决定“系统如何理解和处理内容”：

- `chat + none`
- `experiment + free`
- `experiment + protocol`

**输入来源**只说明“用户怎么把内容送进来”：

- `text`
- `single_recording`
- `continuous_call`

所以“用麦克风说话”不等于“正在记实验”；Chat 也可以录音并出声，实验模式也可以打字。

### 6.2 为什么每次提交都要冻结模式快照

一次请求发出后，用户可能马上切换模式。如果旧请求完成时读取的是“现在的模式”，它可能被错误地按新模式处理。

因此请求提交时要冻结：

```json
{
  "interaction_mode": "experiment",
  "experiment_context": "free",
  "mode_version": 3,
  "input_source": "text"
}
```

专业上这是用**不可变请求快照**避免异步竞态；`mode_version` 用于发现同一个请求身份被不同模式版本重复提交的冲突。

当前前端入口可从 `web/frontend/interaction_mode_state.js` 的 `select` / `capture` 开始查看；服务端字段校验可查看 `web/mode_snapshot.py`。

## 7. 为什么聊天框和右侧区域不能各维护一套

### 7.1 白话问题

如果聊天区显示一次 Tool 调用，右侧运行区又显示一次，用户会不知道：

- 两边是不是同一个东西；
- 哪边是最新状态；
- 一边失败、另一边成功时应该信谁；
- 切换页面回来后状态是否还能对应。

### 7.2 专业问题

这叫**双写状态**或**多事实源**。同一个运行事实同时写入两个独立 UI 状态，必然增加顺序错乱、重复渲染和恢复不一致的风险。

最终设计是：

```text
Chat / Record / Tool / Protocol / Safety 生产事件
                       ↓
              ConversationTurnStore
                       ↓
                单一聊天时间线
```

方案库、安全库、记录库仍可保留独立管理页面，用于完整浏览和编辑；但一次对话正在发生的运行状态只投影到聊天时间线，不在右侧再复制一份。

## 8. Turn/Block 专业设计

### 8.1 Turn 是一轮总信封

`ConversationTurn` 表示从一次用户提交到本轮系统输出的完整回合，核心字段包括：

```text
conversation_id
request_id
turn_id
interaction_mode
experiment_context
mode_version
input_source
blocks
```

### 8.2 Block 是时间线中的一种消息块

典型类型包括：

```text
user_text          用户文字
assistant_text     助手正文
protocol_card      方案卡
step_card          步骤卡
safety_alert       安全提醒
record_card        实验记录卡
tool_card          工具调用卡
confirmation_card  确认卡
system_status      系统状态
voice              语音投递描述
```

语音 Block 不应复制一份屏幕正文，而应使用 `source_block_id` 指向“它在朗读哪张可见 Block”。这样用户看到的内容、调度器播的内容和测试检查的内容具有同一个身份。

### 8.3 幂等与冲突

`(conversation_id, request_id)` 是请求身份：

- 完全相同的请求重放：保留已有结果，不重复制造 Block；
- 同一身份但 `mode_version` 变化：明确报告模式版本冲突；
- 同一身份但其他内容变化：报告请求内容冲突。

核心合同位于 `src/core/conversation_turn.py`：

- `ConversationBlock`
- `ConversationTurn`
- `decide_turn_replay`
- `to_wire`

浏览器唯一状态入口位于 `web/frontend/conversation_turn_store.js`：

- `createConversationTurnStore`
- `beginTurn`
- `upsertBlock`
- `subscribe`
- `getSnapshot`

## 9. 当前统一请求链怎么走

下面是一条适合新手复核的主路线。当前代码已经比对话早期的临时 `/chat/stream` 分支继续演进，统一 Turn 入口可从 `/turn` 查看。

```text
用户在唯一 Composer 提交文字/录音
    ↓
interaction_mode_state.capture() 冻结模式快照
    ↓
web/frontend/turn_client.js 组装请求
    ↓ POST /turn
web/api/turn.py 校验身份、模式和输入字段
    ↓
web/turn_application_service.py 选择处理策略
    ↓
web/turn_processors.py 生成 ConversationTurn + Blocks
    ↓
响应回到浏览器
    ↓
ConversationTurnStore 写入唯一状态
    ↓
聊天时间线渲染可见 Block
    ↓
voice Block / voice_delivery 进入播放调度与浏览器 TTS
```

注意：这条图同时包含“当前已接入的统一 Turn 主链”和“仍需 33g 真机证明的实际播放效果”。有代码路径不等于已经有人耳验收。

## 10. Chat、Record、Tool 如何互不打架

它们不是三套系统，而是三个**生产者**：

- Chat 生产 `assistant_text`；
- Record 生产 `record_card`、追问或方案反馈；
- Tool 生产 `tool_card` 和结果。

三个生产者都要满足同一组外壳规则：

1. 先有屏幕来源 Block；
2. 需要朗读时，Voice 通过 `source_block_id` 引用它；
3. 同一请求重放不能重复生产；
4. 播放许可都经过同一调度器；
5. A 会话的状态不能影响 B；
6. Tool 是能力，不是第四种交互模式；有副作用的 Tool 以后还要经过确认和权限策略。

## 13. 真实验收时该怎么操作、说什么

33g 不是再看代码，而是用人能听见的结果验证三类生产者。建议每次只测一个对话和一个场景，并同时观察聊天时间线、网络请求和实际声音。

### Chat

说或输入：

> 请用两三句话解释为什么冰会浮在水面上。

检查：屏幕出现完整自然回答；声音与这张回答 Block 对应；不是实验式的 25 字短句；没有写入实验记录。

### 自由实验记录

说：

> 我观察到溶液从无色变成浅蓝色。

检查：原始事实先保存；若缺少关键语义，最多追问一个问题；保存结果和追问都在同一聊天时间线。

### 方案实验记录

说：

> 我已经完成当前步骤，但温度比方案要求高了五度。

检查：系统识别当前方案和步骤，记录偏差并给出必要的安全/下一步反馈。

### 抢话与恢复

在助手开始播报后立即说：

> 等一下，我补充一个条件。

检查：助手停止或不继续抢话；新语音识别结束后，旧内容依据时效被恢复或丢弃；不能无条件把过期内容全部补播。

## 14. 本文能证明与不能证明的边界

本文能证明：

- 本对话形成了怎样的产品判断和技术设计；
- 当前代码中相应合同、模式状态、统一 Store 和处理入口在哪里；
- 正式计划把 33a–33f 标为 `AUTO_OK`、33g 标为 `TODO`。

本文不能证明：

- 当前本地服务正在运行；
- 当前浏览器已经加载最新前端资源；
- 麦克风权限、扬声器、TTS 网络和浏览器自动播放策略都正常；
- 用户已经完成 33g 的真人听感确认。

## 15. 接下来为什么应该做 33g

33a–33f 已经回答了“数据结构、唯一状态、界面收敛、模式快照、分策略和三生产者组合是否在自动测试里闭环”。现在最缺的不是再加一个抽象，而是把这套链放进真实浏览器：

1. Chat 回答是否自然且真的出声；
2. 自由/方案记录是否按各自策略出声；
3. Tool 是否引用正确的屏幕卡片；
4. 用户抢话时是否延后；
5. 用户说完后是否只恢复仍然有效的内容；
6. A、B 会话是否互不影响。

所以唯一下一步是：**按 33g 的三生产者验收表启动服务并做真实播放验收，记录屏幕 Block、请求字段、TTS 生命周期和人耳结果。**

## 16. 给新手的自测题
