# 统一对话区与语音链路：从白话到代码

> 文档范围：只总结本对话中讨论、设计、编码和真实排查过的内容。  
> 不包含：项目其他功能、后续新增的实验 Tool 细节、未在本对话中确认的产品结论。  
> 阅读目标：先看懂“用户说一句话后系统到底经历什么”，再学会用专业概念和代码定位问题。

## 1. 先用一句白话说清整个系统

这个项目想做的不是“左边聊天、右边再放一个实验面板”，而是：

> 用户始终面对一个输入框和一条聊天时间线；系统根据当前模式，把本轮产生的文字、记录、步骤、方案、安全提示和工具状态，组合成不同类型的卡片，并从其中一张明确可见的卡片生成语音。

这里有三个不能混淆的问题：

1. **本轮产生了什么内容？**——由 Turn 和 Block 表达；
2. **当前正在录音、识别还是播放？**——由语音运行状态表达；
3. **某段文字现在是否允许朗读？**——由播放调度表达。

它们分别是“内容账本”“现场状态”“播出许可”，不能由一个布尔变量全部代替。

## 2. 为什么最后只保留一个聊天区

### 2.1 修改前的直观问题

同一条实验记录曾同时出现在：

- 主聊天区的 Block；
- 右侧“实验方案/安全/记录”面板。

用户看到两份相同内容，很自然会怀疑保存了两次，也不知道应该在哪一边继续操作。

### 2.2 产品结论

- 只有一个 Composer（输入框）；
- 只有一条聊天时间线；
- `chat`、`experiment/free`、`experiment/protocol` 是明确模式；
- 文字、单次录音、连续通话只是 `input_source`，不是业务模式；
- 方案、步骤、安全、记录、工具等内容都作为不同 Block 出现在同一时间线；
- 方案管理、记录管理等页面可以整页打开，但不与主聊天同时重复展示同一回合。

### 2.3 专业概念

这叫 **Single Conversation Surface（单一对话表面）** 和 **Single Source of Truth（单一事实来源）**。

它不是要求所有内容长得一样，而是要求所有内容进入同一个可追溯时间线。不同 Block 可以有不同视觉样式和交互能力。

## 3. 什么是一个完整回合

### 3.1 白话理解

用户按下发送键或完成一次有效录音，就像新建一只文件夹：

- 文件夹叫 Turn；
- 文件夹里每张纸叫 Block；
- 用户原话是一张纸；
- 助手回答是一张纸；
- 保存结果、方案、步骤、安全提示、工具状态也各是一张纸；
- 要朗读时，语音只引用其中一张看得见的纸。

一次用户输入只能产生一个主要 Turn，不能因为系统内部又保存、又调用模型、又生成语音，就偷偷变成几个互不关联的回合。

### 3.2 不超过五个节点的数据流

```text
用户提交一次输入
→ 冻结本次模式与输入来源
→ 建立一个 ConversationTurn
→ 各业务模块追加 ConversationBlock
→ 前端按同一 Turn 顺序显示
```

### 3.3 关键身份字段

| 字段 | 白话含义 | 为什么需要 |
|---|---|---|
| `conversation_id` | 属于哪段长期对话 | 防止不同聊天串线 |
| `turn_id` | 属于哪一次用户输入 | 把一轮内的所有结果装在一起 |
| `block_id` | 本轮中具体哪张卡片 | 更新、引用和去重都靠它 |
| `interaction_mode` | 提交时是聊天还是实验 | 决定业务解释方式 |
| `experiment_context` | 自由实验还是方案实验 | 决定是否有方案约束 |
| `mode_version` | 提交时模式的版本号 | 防止异步返回时模式已经切换 |
| `input_source` | 打字、单次录音或连续通话 | 描述输入渠道，不改变业务含义 |

代码入口：

- `src/core/conversation_turn.py::ConversationTurn`
- `src/core/conversation_turn.py::ConversationBlock`
- `src/core/conversation_turn.py::decide_turn_replay()`
- `web/mode_snapshot.py::ModeSnapshotFields`
- `web/frontend/conversation_turn_store.js::createConversationTurnStore()`

## 4. 为什么模式必须在提交瞬间冻结

### 4.1 白话理解

假设用户在“自由实验记录”模式说了一句话，模型还没返回时又切换到 Chat。如果系统读取的是“当前按钮状态”，旧请求可能被错误当成 Chat；反过来也可能把 Chat 内容自动保存成实验事实。

因此，每个请求都要带走一张“提交时快照”：

```text
interaction_mode + experiment_context + mode_version
```

后面不论 ASR、LLM 或保存用了多久，都按这张快照处理。

### 4.2 专业概念

这叫 **Request Snapshot（请求快照）**、**Optimistic Versioning（乐观版本校验）** 和 **Race-condition Prevention（竞态预防）**。

### 4.3 三种模式的业务边界

| 模式 | 用户输入默认含义 | 关键限制 |
|---|---|---|
| `chat` | 普通交流 | 像实验事实的话也不能自动保存 |
| `experiment/free` | 默认是待保存的原始实验事实 | 先保存，再最多追问一个关键缺口 |
| `experiment/protocol` | 方案约束下的现场事实 | 必须已有用户选择且服务端确认的活动方案 |

代码对照：

- `web/frontend/interaction_mode_state.js::createInteractionModeState()`：前端模式状态；
- `web/frontend/composer.js::selectComposerMode()`：用户选择模式；
- `web/output_policy.py::select_output_policy()`：服务端选择输出策略；
- `web/api/chat.py::_require_chat_policy()`：Chat 入口守卫；
- `web/api/record.py::_submitted_experiment_context()`：实验上下文校验。

## 5. Block 为什么很多，但语音 Block 只要一个

### 5.1 业务 Block 的种类

统一合同允许这些内容出现在同一 Turn：

| Block 类型 | 表达什么 |
|---|---|
| `user_text` | 用户原话或 ASR 最终文字 |
| `assistant_text` | 助手可见回答 |
| `protocol_card` | 当前实验方案 |
| `step_card` | 当前步骤 |
| `safety_alert` | 安全资料或提示 |
| `record_card` | 保存成功的实验事实 |
| `tool_card` | Tool 的请求、结果或状态 |
| `confirmation_card` | 需要用户补充或确认的内容 |
| `system_status` | 加载、识别、失败等系统状态 |

多个 Block 并不等于重复。它们分别维护不同业务状态。例如，记录已经保存，但追问仍待回答，这两个状态不能硬塞进同一张卡片。

### 5.2 为什么自动语音统一为一个可见 Block

最初讨论过“每个有语音资格的 Block 分别朗读”，但这样会出现：

- 一轮连续播好几段；
- 保存回执、追问和解释重复说；
- 用户不知道屏幕哪一段对应当前声音；
- 打断和重读很难精确定位。

最终决定：

> 一个完整 Turn 可以有多个业务 Block，但自动语音最多引用一个独立、可见的朗读 Block。

语音项目自身不再保存另一份正文，只保存：

| 字段 | 含义 |
|---|---|
| `source_block_id` | 屏幕上哪张 Block 是朗读原稿 |
| `intent_id` | 这次朗读的稳定身份 |
| `priority` | 调度时的重要程度 |

`voice_text` 必须逐字等于 `source_block_id` 指向 Block 的可见正文。

### 5.3 专业概念

- **Reference Integrity**：语音引用必须指向真实存在的 Block；
- **Single Source of Truth**：屏幕正文是唯一稿件；
- **Derived Data**：语音正文从可见 Block 派生，不维护第二份容易漂移的副本；
- **Fail before publication**：超长时先要求上游重写，不能显示后再截断。

代码对照：

- `src/core/spoken_output.py::select_spoken_output_policy()`
- `src/core/spoken_output.py::build_spoken_block_plan()`
- `web/api/chat.py::_build_chat_spoken_delivery()`
- `web/frontend/voice_delivery_client.js::validItems()`

## 6. Chat 的屏幕与语音合同

### 6.1 已讨论并实现的默认规则

- 普通 Chat 默认生成一段简短但完整的回答；
- 当前纯合同按最多 50 个中文字符估算约 10 秒；
- 不允许屏幕显示长文、语音只读开头；
- 不允许在播放到 10 秒时硬切；
- 用户明确说“继续说”时，未来应建立新的详细回合，不沿用默认短答限制；
- 用户打断后不自动恢复旧音频；
- 用户明确要求重读时，应从历史可见 Block 原文重新合成，而不是重新调用模型改写。

### 6.2 数据流

```text
DeepSeek生成完整短答
→ 后端在发布前检查预算
→ 建立 assistant_text(role=spoken)
→ Scheduler授权引用该Block的voice item
→ 浏览器用同一正文请求TTS
```

### 6.3 代码对照

- `web/agent/core.py`：模型提示策略；
- `web/api/chat.py::chat_stream()`：SSE 主入口；
- `web/api/chat.py::_prepare_chat_spoken_delivery()`：生成前/发布前的语音合同桥接；
- `web/frontend/streaming_chat_v2.js`：把 `screen_delta` 写入当前 Turn；
- `web/frontend/voice_delivery_client.js::consumeVoiceDelivery()`：只有 `READY/PREEMPT` 才能进入播放；
- `web/frontend/local_tts.js::addToQueue()`：进入实际 TTS 队列。

## 7. 两种 Experiment 的输出合同

### 7.1 共同原则

- 用户原话显示，但不回读；
- 保存成功的 `record_card` 只显示“已保存”，不朗读；
- 一个 Experiment Turn 的自动语音总计目标约 15 秒；
- 多个业务 Block 最多合成为一个可见语音汇总 Block；
- 一般 `safety_alert` 只显示不读；
- “取溶液”之类普通操作不能仅凭词面冒充危险；
- 本对话期间并没有完成真正的 `danger_intervention` 判断能力。

### 7.2 `experiment/free`

正确顺序是：

```text
原始口述事实
→ 先保存原文
→ 显示静默 record_card
→ 若存在关键语义缺口，最多产生一个追问
→ 需要说的内容合成唯一可见朗读 Block
```

“加入缓冲液”即使缺少用量，也应该先保存原始事实，再问“加入多少缓冲液？”，不能因为缺字段就丢掉事实。

### 7.3 `experiment/protocol`

- 必须先选择并确认活动方案；
- `protocol_card` 只在进入方案、切换方案或方案版本变化时显示；
- `step_card` 只在进入步骤、切换步骤或步骤版本变化时显示；
- 不能每记录一句话就重复方案卡和步骤卡；
- 新偏差、现场必测缺口或确认问题可以各自维护 Block；
- 真正需要朗读的内容仍汇总成一个可见语音 Block。

这里对应 **Entity Lifecycle（实体生命周期）**：方案卡属于方案版本，步骤卡属于步骤版本，而不是属于每一次 Turn。

## 8. 连续通话不是另一种业务模式

### 8.1 白话理解

单次录音和连续通话都只是“怎样把声音送进系统”：

- 单次录音：点一下开始，再点一下结束；
- 连续通话：开始时点一次，之后由 VAD 自动切分每句话；
- 两者最终都应该得到 `user_text`，再走同一 Chat/Experiment 业务链。

### 8.2 连续通话数据流

```text
麦克风音频帧
→ Silero VAD判断开始/停顿/结束
→ 音频片段提交 /asr/transcribe
→ ASR文字交给唯一Composer发送
→ 当前模式生成同一时间线Blocks
```

### 8.3 代码对照

- `web/frontend/composer.js::send()`：唯一发送入口；
- `web/frontend/phone_call.js::startCall()`：连续通话启动；
- `web/frontend/phone_call.js::handleSileroEvent()`：接收 VAD 事件；
- `web/frontend/phone_call.js::processQueue()`：ASR 队列；
- `web/frontend/call_silero_vad.js::createCallSileroVad()`：浏览器 Silero VAD；
- `/asr/status`、`/asr/warmup`、`/asr/transcribe`：模型状态、预热和转写接口。

## 9. VAD、ASR、LLM、TTS 分别是什么

| 层 | 白话 | 失败时的典型现象 |
|---|---|---|
| VAD | 判断“有没有人在说话、什么时候说完” | 误触、过早切段、一直不结束 |
| ASR | 把音频变成文字 | 显示加载失败、没有转写、错字多 |
| LLM | 根据文字生成回答或理解结果 | 模型连接失败、回复为空、超出合同 |
| TTS | 把指定可见正文变成声音 | 有文字无声音、合成失败、播放被中止 |

用户说“没有语音”时，不能直接归咎于 TTS。必须沿链路检查：

```text
有没有VAD片段
→ 有没有ASR文字
→ 有没有LLM/业务Block
→ 有没有voice_delivery授权
→ 有没有/tts请求和浏览器播放
```

## 10. 打断为什么是状态机问题

### 10.1 需要记录的运行事实

`VoiceRuntimeState` 主要记录：

- `user_speaking`
- `segment_capturing`
- `asr_processing`
- `tts_playing`
- `active_tts_priority`

这些是“现在发生了什么”，不是聊天内容，也不是永久业务记录。

### 10.2 真实发现的 500

真实浏览器曾产生：

```text
user_speech_started
→ user_speech_paused
→ user_speech_started
```

核心状态机认为一个片段仍打开，因此第三个事件应该叫 `USER_SPEECH_RESUMED`，曾抛出：

```text
片段已在采集；请使用 USER_SPEECH_RESUMED。
```

修复方式不是放松所有状态规则，而是在会话边界根据当前状态把第二次 `started` 归一化为 `resumed`。

这叫 **Boundary Normalization（边界归一化）**：外部设备可以有不同事件命名，内部核心状态机仍保持严格。

代码对照：

- `web/api/voice_runtime.py::consume_voice_runtime_event()`：HTTP 事件入口；
- `web/voice_runtime_sessions.py::VoiceRuntimeSessionRegistry.consume()`：按 conversation 隔离并归一化；
- `src/core/voice_runtime_state.py::VoiceStateCoordinator._reduce()`：唯一状态转换入口。

### 10.3 为什么修掉 500 后仍可能没有声音

因为“事件被接受”只证明输入状态链没有崩，后面还有：

- 新回复是否生成语音候选；
- Scheduler 是否给 `READY`；
- 前端是否发现来源 Block；
- 朗读开关是否允许；
- 新语音是否真正入队；
- `/tts` 是否发出；
- 浏览器 Audio 是否播放。

本对话末尾的真实日志显示：

- 第二轮 ASR 成功；
- 第二轮 DeepSeek 成功；
- 第二轮之后没有 `/tts`；
- 因而故障已缩小到“模型之后、TTS请求之前”；
- 当时尚未取得足够证据断言最终根因已经修复。

## 11. PlaybackScheduler 到底做什么

### 11.1 白话理解

它像广播室值班员：拿到“可以朗读的稿子”后，还要看现场是否适合播放。

- 用户正在说话：通常延后；
- ASR 正在处理：通常延后；
- 有更重要的声音正在播放：根据优先级决定等待、抢占或丢弃；
- 条件满足：发出 `READY`；
- 内容已经失去上下文：`DROP`。

### 11.2 专业分层

```text
VoiceDeliveryItem：内容具有语音资格
PlaybackRequest：带时效和身份的播放请求
PlaybackContext：某一瞬间的现场快照
PlaybackGate：纯规则判断
PlaybackScheduler：排队、重评估、抢占和执行交接
BrowserPlaybackExecutionPort：把最终许可交给浏览器
```

代码对照：

- `src/core/playback_scheduler.py::PlaybackScheduler.schedule()`
- `src/core/playback_scheduler.py::PlaybackScheduler.reevaluate()`
- `src/core/playback_scheduler.py::PlaybackScheduler.handle_tts_event()`
- `web/playback_runtime.py::WebPlaybackService.authorize()`
- `web/playback_runtime.py::ConversationPlaybackRegistry`
- `web/frontend/voice_delivery_client.js::consumeVoiceDelivery()`

## 12. 浏览器实际怎样播放

### 12.1 数据流

```text
收到 READY voice_delivery
→ 校验 source_block_id 和朗读开关
→ local_tts加入队列
→ 请求 /tts
→ 浏览器解码并播放音频
```

### 12.2 打断机制

`web/frontend/local_tts.js::stopSpeech()` 会：

- 递增 `jobId`，使旧任务失效；
- 清空旧队列；
- 中止正在进行的网络请求；
- 停止当前音频源；
- 上报 `tts_stopped`。

新回复必须使用最新 `jobId` 重新进入队列。否则就会出现“旧声音停了，但以后永远不再说”的竞态问题。

这属于 **Cancellation Token / Generation ID（取消代号/代际编号）** 模式。

## 13. 连续误触保护的产品决定

本对话中决定：

- 连续第 1、2 次误触：屏幕显示反馈，也可以朗读反馈；
- 第 3 次及以后：仅停止语音反馈，连续监听仍保持；
- 一旦形成有效 `user_text` Block，计数清零；
- 误触不能保存实验事实；
- 被误触暂停的旧回答不自动恢复；
- 用户明确指定某一段时，可以从历史 Block 原文重新合成。

这是 **Circuit Breaker（熔断保护）** 的轻量形式：不是关闭全部功能，而是暂时关闭最容易形成自激循环的语音反馈。

注意：这部分在本对话中主要是产品合同讨论，不能仅凭讨论记录宣称所有生产代码已经完整实现。

| `voice_delivery_client.js` | 浏览器播出许可门 | 校验后端授权、来源Block和开关 |

前端改动以后必须用“文件 → 功能 → 用户看到什么”来报告，不能只说“改了 JS”。

## 15. 服务端每个文件对应什么功能

| 文件 | 主要职责 |

## 16. 怎样读一条真实 Chat 语音链路

推荐按下面顺序打开代码，不要从 CSS 或某个按钮开始乱翻：

1. `composer.js::send()`：输入是什么、携带什么 mode/input_source；
2. `api/chat.py::chat_stream()`：请求进入服务端后生成哪些 SSE 事件；
3. `spoken_output.py::build_spoken_block_plan()`：可见正文和语音引用怎样绑定；
4. `streaming_chat_v2.js`：Block 何时写入 Store；
5. `voice_delivery_client.js::consumeVoiceDelivery()`：为什么允许或拒绝播放；
6. `local_tts.js::processQueue()`：是否真正请求并播放音频。

每读一层都回答四个问题：

```text
输入是什么？
输出是什么？
状态在哪里改变？
失败后用户看到什么？
```

## 17. 怎样排查“没有声音”而不乱改

### 17.1 检查表

| 观察证据 | 可以得出的结论 |
|---|---|
| 没有 VAD 事件 | 先查麦克风/VAD，不查模型 |
| 有音频但 `/asr/transcribe` 失败 | 查 ASR 加载或音频格式 |
| 有 ASR 文字但无 `/chat/stream` | 查 Composer 提交链 |
| DeepSeek 成功但无 `voice_delivery` | 查输出合同/调度 |
| `READY` 但无 `/tts` | 查前端来源Block、开关和取消竞态 |
| `/tts` 200 但听不到 | 查浏览器播放、音量和Audio错误 |

### 17.2 证据等级

- 静态检查：只能证明代码结构或语法；
- 单元测试：只能证明函数在测试输入下工作；
- 集成测试：只能证明模拟模块能连通；
- 真实 API 探针：能证明模型或 TTS 服务响应；
- 真实浏览器 + 麦克风 + 人耳：才证明这一现场交互真正可用。

“全量测试通过”不能替代“用户打断后确实听到了下一轮回复”。

## 18. 本对话中的重要失败与学到的方法

### 18.1 把 25 字策略复用到 Chat

问题：实验模式的首句/25字策略曾被临时复用到普通 Chat，造成回答不到 5 秒。

教训：不同业务策略可以共享 Turn/Block 和 Scheduler，但不能共享错误的内容策略。

### 18.2 两个界面同时消费同一事实

问题：聊天时间线和右侧实验面板都渲染记录、方案和追问。

教训：一个事实可以有多个数据消费者，但产品主界面必须明确唯一权威投影。

### 18.3 把“通话”误当成模式

问题：通话按钮、单次录音和 Chat/Experiment 的关系不清楚。

教训：业务模式与输入设备是两个正交维度，应分别建模。

### 18.4 只修状态机异常却提前宣布修好

问题：`started/resumed` 的 500 被修复后，真实浏览器仍不朗读。

教训：修复一个确定断点，只能证明这个断点消失；必须继续追踪到最终用户可见效果。

## 19. 当前结论：哪些完成，哪些不能冒充完成

### 已有明确设计或代码基础

- 单 Composer、单聊天时间线方向；
- 显式 `chat / experiment/free / experiment/protocol`；
- Turn/Block 纯合同；
- 请求提交时冻结模式、上下文和版本；
- 语音通过 `source_block_id` 引用可见 Block；
- Chat 默认约 10 秒、Experiment 整轮约 15 秒的合同方向；
- Experiment 一轮最多一个自动语音汇总 Block；
- 连续通话的 VAD→ASR→Composer 基础链；
- `started → paused → started` 的后端事件归一化。

### 本对话结束时仍不能宣称完成

- 打断后下一轮必然重新朗读；
- VAD 误触保护全部生产接通；
- 用户指定历史重读；
- Chat continuation 的完整生产状态；
- `danger_intervention` 危险动作识别；
- Protocol/Step 生命周期在所有真实场景都不重复；
- 所有 Experiment 输出都已遵守唯一语音 Block 与 15 秒合同。

## 20. 给新手的最终架构图

```text
                    ┌──────────────────────────┐
文字 / 单次录音 / 连续通话 ─→ 唯一 Composer     │
                    └────────────┬─────────────┘
                                 │ 冻结 mode/context/version
                                 ▼
                    ┌──────────────────────────┐
                    │ 一个 ConversationTurn   │
                    │ 多个业务 Blocks         │
                    └───────┬──────────┬───────┘
                            │屏幕      │唯一可见朗读Block
                            ▼          ▼
                    Conversation   VoiceDeliveryItem
                    TurnStore          │
                                       ▼
                               PlaybackScheduler
                                       │ READY
                                       ▼
                              浏览器校验 source_block
                                       │
                                       ▼
                                  TTS与播放
```

真正的统一不是“所有代码合成一个文件”，而是：

- 内容统一进 Turn/Block；
- 模式在请求边界冻结；
- 屏幕和语音共享同一正文；
- 运行状态由唯一状态机维护；
- 是否播放由统一 Scheduler 决定；
- 最终必须用真实浏览器体验闭环验证。

## 21. 唯一建议的下一步

基于本对话最后的证据，下一步只做一件事：

> 用浏览器播放结果回传和服务端授权日志，完整复现一次“打断后第二轮不朗读”，确定它究竟停在 `voice_delivery` 授权、前端 Block 校验、播放开关、TTS 入队还是请求取消，然后只修这个确定断点并做真实复验。

在这个闭环完成前，不同时调整 VAD 阈值、不扩展 Experiment 新 Block、不实现历史重读，避免多个变量再次混在一起。
