# 导师问答:通过这个项目,我学到了什么

> 用途:应对导师 / 评委的提问,回答"通过做这个项目你学到了什么"。
> 口径:白话 + 能对应到代码 + 有专业术语 + 有反面例子。每条结论都能回到「小科」语音交互主线的具体文件。
> 状态:2026-08-30 整理,聚焦"咱们负责的部分"(语音交互主线 + 架构梳理)。

---

## 一、一句话版(导师只给 30 秒)

> 我最大的收获不是"会调大模型 API",而是理解了一个真实系统里,数据是怎么从用户的一句话,
> 变成一条可靠、可追溯的实验记录的;以及为了"可靠",哪些事必须交给写死的规则、哪些事才能交给大模型。
> 这个过程让我把"分层架构、依赖注入、测试、证据边界"这些课本上的词,在真实代码里对上了号。

关键:不吹"用了多少技术",而是点出**理解了"可靠性"这个真正难的地方**。

## 二、展开版:真正学到的 6 件事

每条按「白话 → 专业术语 → 项目里在哪 → 反面例子」展开,可单独深挖。

### ① 一条数据流,能从用户点击追到数据库(端到端可追溯)

- **白话**:页面上有个"语音记录"按钮,只能证明"有扇门",不能证明门后的路修通了。方法是:不凭按钮和 README 下结论,顺着数据一层层追,直到追到它落进数据库、并且有测试和真实验收兜底。
- **专业术语**:端到端可追溯性(End-to-End Traceability)、调用链追踪(Call Chain Tracing)。
- **项目里在哪**(完整主链):

```text
voice_asr.js / mobile.js / phone_call.js   ← 三个录音入口
→ turn_client.submitAudio()                ← 统一提交
→ POST /turn/audio                          ← 后端接口
→ TurnApplicationService.submit_audio()     ← 应用服务调度
→ ASRApplicationService.recognize_upload()  ← 语音识别
→ ExperimentProcessor.prepare()             ← 语义理解 / 追问 / 方案核对
→ TurnStore.commit()                        ← 写 SQLite
```

- **反面例子**:不这么追,容易把"半成品"写成"已完成"。项目踩过坑:聊天区输入实验口述,agent 口头说"已记录",但数据库里没记录;靠追到 `TurnStore.commit()` 的 SQL 才坐实真假。

### ② 把"算数"和"做事"分开(分层 + 纯逻辑)

- **白话**:代码分两类——"动脑子算对错"的(判断字段缺不缺、这步算不算完成)和"动手干活"的(写文件、连网络、开麦克风)。把"动脑子"的部分单独拎出来,不碰文件网络,变成能反复测试的"干净积木"。
- **专业术语**:分层架构(Layered Architecture)、纯逻辑与副作用分离(Pure Logic vs Side Effects)、领域层与基础设施层(Domain Layer vs Infrastructure Layer)。
- **项目里在哪**:`src/core/` 是纯领域逻辑(判断规则全在这),`src/asr/`、`src/llm/`、`src/storage/` 是干活的适配器。"这步方案算不算完成"写在 `src/core/protocol_completion_policy.py`,是纯函数,不联网、不读文件。
- **反面例子**:把"判断规则"和"读写文件"搅在一起,测一条规则就得真启动麦克风、真连模型,测试没法自动跑,规则没人敢改、没人敢信。

### ③ 面向接口编程,不绑死具体实现(依赖注入)

- **白话**:只认"约定"(接口),不认"具体哪个牌子"(具体实现)。依赖一个"能干识别这件事"的接口,而不是 FunASR 这个具体库;换模型、做测试都只换一个零件,不动主逻辑。
- **专业术语**:接口隔离(Protocol)、依赖注入(Dependency Injection)、工厂模式(Factory)、测试替身(Test Double / Fake)。
- **项目里在哪**:`ASRBackend`、`LLMClient` 是接口(Protocol),运行时由工厂(`src/asr/factory.py`)把 `SenseVoiceBackend`、`OpenAICompatibleLLMClient` 装进去。测试时塞进"假的"处理器(Fake),不用真连 DeepSeek 也能测业务逻辑。
- **反面例子**:业务代码里直接 `import funasr`、`import deepseek`,换模型要到处改业务代码,测试还得真烧钱联网——这项目就没法用 1300+ 自动化测试守住。

### ④ 大模型只负责"听懂",不负责"拍板"(确定性 vs 幻觉)——最深的一课

- **白话**:大模型会一本正经地胡说(幻觉)。"这句话是什么意思"可以交给它;"要不要追问、这步算不算完成、计算对不对"这种必须可靠的事,写死成规则。模型只干它擅长的"听懂人话",拍板永远用代码。
- **专业术语**:幻觉(Hallucination)、确定性规则(Deterministic Rule)、函数/工具调用(Function Calling)、"模型当分类器、不当执行者"(LLM as classifier, not executor)。
- **项目里在哪**(整套架构的魂):
  - 精确命令("结束实验记录")走**零 LLM** 词表匹配,不浪费也不冒幻觉风险;
  - "这步方案完没完成"用 `resolve_protocol_completion` 这种**确定性函数**判,不用模型猜;
  - 专业计算(分子量、C1V1=C2V2)走**工具计算**,结果只引用工具返回值,不信模型记忆;
  - 连"说什么话术"都是后端 copy 层写死的,**语音受控靠确定性格式化器,而不是靠 prompt 求模型好好说话**。
- **反面例子**:项目踩坑——让模型"判断并声称已记录",结果口头说"记好了",数据库啥也没有。这导向一个反复用到的判断:**涉及"数据是否真实落盘、步骤是否真实完成"的,一律确定性代码,模型只做理解那一环。**

### ⑤ 数据安全优先,失败要降级、不崩溃

- **白话**:模型挂了、网断了,也不能丢实验数据。原则是**先存原始证据,再做聪明推断**;聪明的部分失败就降级成"只保存原文",而不是崩溃。
- **专业术语**:优雅降级(Graceful Degradation)、原始数据优先(Evidence-first)、原子性/两阶段提交(Atomicity / Two-phase Commit)。
- **项目里在哪**:ASR 原文先落 JSONL,LLM 结构化结果后写——原始事实永远可回溯;LLM 失败降级成 NOTE 事件("原始记录已保存,结构化处理暂时不可用"),不抛异常中断实验;确认类操作用"先 prepare 拿版本号 → 落盘成功 → 再 commit"的两阶段提交,防并发改乱状态。
- **反面例子**:实验人员戴着湿手套做实验,系统一崩就把刚说的话丢了——这不是"功能缺失",是"数据事故"。"失败降级"是硬要求,不是加分项。

### ⑥ 测试分等级,证据要诚实(能证明 / 不能证明)

- **白话**:测试分四级,过了低级不等于过高级。诚实区分:自动测试通过 ≠ 真实环境能用 ≠ 用户觉得好用。说结论必须讲清"这条证据到底能证明到哪一步"。
- **专业术语**:测试金字塔(Testing Pyramid)、单元/集成/端到端(Unit / Integration / E2E)、证据边界(Evidence Boundary)。
- **项目里在哪**:验收状态分三档——`AUTO_OK`(自动测试过)、`REAL_OK`(真实麦克风/浏览器/模型跑通)、`UX_CONFIRMED`(真实用户确认体验好),三者不能互相替代。测试从"用 Fake 的单元测试"到"真连模型的真实验收"层层递进,全量 1300+ 项。
- **反面例子**:把"AUTO_OK 自动测试过了"说成"真实验收通过"是撒谎——自动测试证明"逻辑对",证明不了"真麦真模型下用户用着顺不顺"。

## 三、口播建议

给导师讲,重点是"**一个结论 + 一个项目例子**",别背术语。套模板:

> 我学会了「XX」——比如项目里「某个具体功能/文件」就是这么做的,如果不这么做,会「出什么错」。

三个最值得主动抛出的"高光结论":

1. **"我理解了为什么大模型不能直接当业务逻辑用"** —— 体现不是"套壳党",而是有工程判断。
2. **"我能从一行前端代码,追到它最终写进数据库的那条 SQL"** —— 体现读得懂真实系统,不是只会跑 demo。
3. **"我学会了诚实区分'能证明'和'不能证明'"** —— 体现工程师的严谨,不夸大。

## 四、导师可能追问的 5 个问题

| 导师可能问 | 回应方向 |
|---|---|
| "你具体负责哪部分?" | 如实说:语音交互主线的理解与梳理 + 具体协作的功能(把真实写的部分说清,别揽全功也别藏) |
| "大模型在这个系统里到底是什么角色?" | 只有"理解自然语言"这一环交给它;判断、计算、落盘、话术全用确定性代码,因为它会幻觉 |
| "为什么不用现成的?" | 现成的通用对话/转写做不到"可靠记录 + 多轮追问 + 方案核对 + 可追溯",这四件事才是难点 |
| "你怎么证明它可靠?" | 分层测试:单元(Fake)→集成→真实验收,并诚实标注三档状态 AUTO_OK/REAL_OK/UX_CONFIRMED |
| "最难的 bug / 最难的设计取舍是什么?" | 任选:①非阻塞录音(说完继续说,不卡);②删除旧代码时保证能力不丢(迁移对照表);③"确认+补充字段"的复合意图不能丢字段 |

## 五、诚实边界(重要)

- 本文口径是"**我理解了 / 我能追踪 / 我参与了**",不是"我独立实现了整个系统"。大二学生能透彻讲清一个复杂系统的数据流和设计取舍,本身就是强信号,不需要夸大工作量。
- 具体负责的代码边界以你实际写的为准;如与"语音交互主线 + 架构梳理"有出入,按事实调整「一、二」中的对应举例。
