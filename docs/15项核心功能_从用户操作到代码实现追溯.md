# 15 项核心功能：从用户操作到代码实现的追溯手册

> 本文不是作品简介，而是给项目成员学习代码用的「寻路图」。
> 阅读时始终问：用户做了什么？前端发了什么？后端谁执行？数据写到哪？现有证据能证明到哪一层？

## 0. 先学会一套通用追溯方法

对任何一项功能，都按下列顺序查：

```text
用户操作
  → 前端事件处理函数
  → fetch() / turnClient 网络请求
  → FastAPI @router 路由
  → 应用服务或业务处理器
  → 领域规则 / 工具 / 外部模型
  → SQLite / JSON 文件 / 远程服务
  → 界面反馈
```

三个最常用的寻路动作：

1. 看到 `fetch('/xxx')`，就搜后端的 `prefix="/xxx"` 和 `@router`。
2. 看到 `service.some_method()`，就搜 `def some_method`。
3. 看到 `from module import Name`，就进入 `module.py` 搜 `Name`。

证据分四层：

| 证据层 | 能说明什么 |
|---|---|
| 页面 / API 入口 | 用户有这个入口 |
| 生产调用链 | 入口后确实有业务代码 |
| 写入点 + 测试 | 数据闭环可被自动检查 |
| 真实环境验收 | 麦克风、浏览器、模型或远程服务真正跑过 |

`tests/` 中有文件只能说「有这类测试」；没有在当前轮实际执行，不能称为「当前已通过」。

## 1. 单次录音、手机录音与连续通话

### 用户做什么

用户可以点击桌面端录音按钮、使用手机录音，或进入连续通话模式。

### 怎么找到代码

先搜共同调用词 `submitAudio`：

```text
web/frontend/voice_asr.js:176   桌面单次录音
web/frontend/mobile.js:218      手机录音
web/frontend/phone_call.js:379  连续通话
```

三者都进入 `web/frontend/turn_client.js::submitAudio()`，它使用 `FormData` 同时提交 WAV 音频和模式元数据：

```javascript
form.append('audio', blob, options.filename || 'segment.wav');
form.append('metadata', JSON.stringify(info));
fetch('/turn/audio', {method: 'POST', body: form});
```

后端入口是 `web/api/turn.py::turn_audio()`，然后调用 `TurnApplicationService.submit_audio()`。

### 代码实际做了什么

- 录音开始时冻结当前模式快照；
- 录音结束后产生 WAV `Blob`；
- 为请求生成 `request_id` 和 `turn_id`；
- 通过 SSE 陆续接收「已接受、正在识别、正在理解、正在保存、最终结果」。

### 边界

代码证明三种输入均接到统一客户端；不等于所有手机、浏览器、麦克风和噪声环境都已稳定通过。

相关测试入口：`tests/test_turn_api.py`、`tests/test_web_mobile_page.py`、`tests/test_explicit_mode_switch.py`、`tests/js/test_phone_call_silero_fallback.js`。

## 2. 交互模式隔离

### 用户做什么

用户选择自由聊天、自由实验、方案实验、方案管理或储存管理。

### 从哪里追

`web/frontend/interaction_mode_state.js` 定义模式映射：

```javascript
chat     -> interaction_mode=chat,       experiment_context=none
free     -> interaction_mode=experiment, experiment_context=free
protocol -> interaction_mode=experiment, experiment_context=protocol
template -> interaction_mode=experiment, experiment_context=template
storage  -> interaction_mode=experiment, experiment_context=storage
```

元数据进入 `/turn/text` 或 `/turn/audio`。`web/turn_application_service.py::_execute_prepared()` 根据模式分派：

```python
CHAT     -> ChatProcessor
TEMPLATE -> TemplateProcessor
STORAGE  -> StorageProcessor
else     -> ExperimentProcessor
```

### 为什么它是真正功能

模式不是仅改页面标题，而是决定后端调用哪个处理器。`web/agent/core.py` 还明确禁止聊天模式调用 `record_observation`。

### 边界

模式分派代码存在，但多标签页会话隔离是另一个验收问题，不能仅凭单请求测试推断。

相关测试：`tests/test_explicit_mode_switch.py`、`tests/test_mode_output_policies.py`、`tests/test_turn_application_service.py`。

## 3. 原始语音证据与结构化实验记录

### 生产调用链

```text
/turn/audio
  -> TurnApplicationService._execute_audio()
  -> ASRApplicationService.recognize_upload()
  -> 构造 TurnInput(asr_transcript, ASRResult)
  -> ExperimentProcessor.prepare()
  -> TurnStore.commit()
```

`web/asr_application_service.py::recognize_upload()` 负责 WAV 校验、音频落盘、ASR 调用和证据封装。`src/asr/sensevoice_backend.py` 通过 FunASR `AutoModel` 加载 SenseVoiceSmall。

`web/turn_processors.py::ExperimentProcessor.prepare()` 把原始文本送入统一实验理解链，并构造实验事件、记录、消息和会话状态。

`web/database/turn_store.py::commit()` 在同一 SQLite 事务中写入：

- `asr_evidence`：音频路径、SHA256、字节数和 ASR 证据；
- Turn 最终结果；
- 实验事件与实验记录；
- 会话与方案执行状态；
- 用户可见消息。

### 关键理解

这不是「模型回答已记录」，而是有真实事务提交。只有 `commit()` 成功后，前端才收到已提交 Turn。

### 边界

代码能证明保存设计，不能单独证明 ASR 在所有专业词、口音和噪声中都准确。

相关测试：`tests/test_asr_application_service.py`、`tests/test_asr_evidence_contract.py`、`tests/test_turn_store.py`、`tests/test_turn_application_service.py`。

## 4. 主动追问与多轮字段补全

### 用户行为

用户先说「加入缓冲液并加热」，系统发现仍缺用量、温度或时长；后续用户可能只回答「五毫升」。

### 怎么追

在 `web/turn_processors.py` 搜：

```text
missing_fields
follow_up_required
follow_up_question
ClarificationExecutor
ReplyCoordinator
```

`ExperimentProcessor.prepare()` 先从 `TurnStore.load_experiment_state()` 恢复 `ReplyCoordinator` 和 `SessionContext`，而不是只靠当前一句话。

`src/core/reply_coordinator.py` 管理待回答问题；`src/core/clarification_executor.py` 处理回答、确认、暂缓等动作；更新后的 `remaining_fields` 会再次写回会话状态。

### 这项功能的核心

不是「模型会问问题」，而是：

```text
问题有身份
→ 记录了待补字段
→ 后续回答能指向对应问题
→ 补全后重新计算剩余字段
```

### 边界

多问题并存、含糊回答和跨标签页会话仍需分别验收，不能只用「一问一答」证明。

相关测试：`tests/test_targeted_clarification.py`、`tests/test_clarification_executor.py`、`tests/test_protocol_missing_fields.py`、`tests/test_protocol_missing_fields_new_semantics.py`。

## 5. 方案实验执行跟踪与确定性完成判定

### 用户做什么

选择一份实验方案，进入某一步，口述真实操作和参数。

### 生产链

`web/api/protocols.py::start()` 调用 `domain.start_session()` 选中方案。实验 Turn 进入 `ExperimentProcessor.prepare()` 后：

1. 从 `domain.session()` 取当前方案与步骤；
2. 从 SQLite 恢复 `ProtocolExecutionState`；
3. 将本次实体值合并进当前步骤事实；
4. 调用 `resolve_protocol_completion()`；
5. 产生缺失字段、参数冲突、偏差和下一动作。

核心文件：

- `src/core/protocol_execution_state.py`：每步已记录的事实和状态；
- `src/core/protocol_completion_policy.py`：能否完成、是否追问；
- `src/core/protocol_navigation.py`：上一步、下一步、跳转；
- `src/core/protocol_deviations.py`：实际值与方案值偏差。

### 关键边界

大模型可以提取语义，但「步骤是否完成」最终走确定性策略。这不等于系统通过传感器真正看到了实验动作；当前事实主要来自用户口述。

相关测试：`tests/test_protocol_completion_policy.py`、`tests/test_experiment_state_snapshot.py`、`tests/test_protocol_navigation.py`、`tests/test_protocol_deviations.py`。

## 6. 实验过程控制命令

### 用户可以表达什么

查看问题、回答问题、确认、暂缓、结束实验记录，或控制方案步骤。

### 实现路径

`ExperimentProcessor.prepare()` 首先调用 `ExperimentToolCommandParser.parse(turn.raw_text)`。明确的工具命令可直接进入 `_prepare_tool_turn()`；普通实验语句则进入 `UnifiedObserver` 和统一理解路由。

与「记录一条实验事实」不同，控制命令会修改 `ReplyCoordinator`、`SessionContext` 或 `ProtocolExecutionState`。

### 边界

精确命令可以由规则直达；自然、含糊的表达可能需要 LLM 理解或确认，不应宣称任意说法都能稳定命中。

相关测试：`tests/test_experiment_tool_command.py`、`tests/test_end_session_commands.py`、`tests/test_clarification_command_handler.py`。

## 7. 实验方案库、AI 草拟与步骤编辑

### 从页面追到后端

`web/frontend/protocol_editor.js` 调用 `/protocols/step`；`web/frontend/views.js` 调用 `/protocols/upload-file`；方案列表和选择使用 `/protocols` 与 `/protocols/session`。

`web/api/protocols.py` 包含四类路径：

1. **查询**：列表、详情、当前会话、步骤和进度；
2. **AI 草稿**：`llm_bridge.generate_protocol_draft()` 和 `generate_protocol_edit_draft()`；
3. **用户确认保存**：`domain.add_protocol()` 或 `update_protocol_from_draft()`；
4. **编辑**：添加、修改、删除步骤并更新版本。

存储链是：

```text
api/protocols.py
  -> web/domain.py
  -> src/storage/protocol_store.py
  -> 方案 JSON 文件
```

PDF/图片上传另走 `ocr_bridge.ocr_pdf()` / `ocr_image()`，再拆成结构化草稿。

### 边界

AI 生成接口明确只返回「草稿」，不自动落盘；保存是另一个确认操作。OCR 准确性和真实 PDF 兼容性需另行真实验收。

相关测试：`tests/test_protocol.py`、`tests/test_protocol_store.py`、`tests/test_protocol_store_new_schema.py`、`tests/test_protocol_session.py`。

## 8. 试剂配置方案管理

### 用户路径

`web/frontend/reagent_prep.js` 负责列表、编辑、删除和导入，调用 `/reagent-prep/*`。

### 后端路径

`web/api/reagent_prep.py` 提供：

- `GET /reagent-prep`：列表；
- `GET /reagent-prep/{id}`：详情；

### 边界

这里是「试剂配置方案库」，不是自动控制称量仪器或液体工作站。

## 9. 分子量、溶液配制和稀释计算

### 从 API 往下追

`web/api/calculator.py` 暴露三个端点：

```text
POST /calculator/molecular-weight
POST /calculator/solution-prep
POST /calculator/dilution
```

路由不让 LLM 直接算，而是从 `lab_tools._REGISTRY` 取对应 handler：

```text
calculate_molecular_weight
calculate_solution_prep
calculate_dilution
```

分子量优先使用开源库 `molmass`，失败时才走项目内置解析器；配液使用物质的量浓度公式；稀释使用 `C1V1=C2V2`。Pydantic 在 API 层限制浓度、体积、纯度和单位的合法范围。

`web/agent/core.py` 的系统规则还规定：用户问分子量、称多少克或稀释体积时，必须先调用计算工具，不得先凭模型记忆给数字。

### 边界

计算程序能保证使用明确公式，但输入的化学式、纯度、密度和实际试剂信息仍需用户确认。

相关测试：`tests/test_calculator_tools.py`、`tests/test_molecular_weight.py`、`tests/test_experiment_tool_command.py`。

## 10. 大模型 Function Calling 与真实工具执行

### 大模型调用从哪里进

`web/agent/core.py::_client()` 创建 OpenAI 兼容客户端：

```python
OpenAI(api_key=settings.api_key, base_url=settings.base_url, ...)
```

`run_agent()` / `stream_agent()` 调用：

```python
client.chat.completions.create(
    model=settings.model_name,
    messages=messages,
    tools=_tools_for_mode(interaction_mode),
)
```

### 工具怎么进入模型

`web/lab_tools.py` 中的 `@tool(...)` 同时登记：

- 工具名；
- 给模型看的用途说明；
- JSON Schema 参数合同；
- 真正的 Python handler；
- 给用户看的调用卡片和结果卡片。

`openai_tools()` 把注册表导出为 OpenAI Function Calling 格式。模型返回 `tool_calls` 后，`_execute_tool()` 调用真实 handler，再把结果作为 `role=tool` 放回模型上下文。

### 为什么不只是「大模型聊天」

对于记录、配液计算、方案编辑、储存管理等任务，最终动作由 Python 函数和存储层完成，不是模型只生成「已完成」三个字。

### 边界

Function Calling 能建立工具执行链，不代表模型每次都会选对工具或参数；所以仍需参数校验、模式权限和确认门。

相关测试：`tests/test_agent_tool_presentation.py`、`tests/test_lab_tool_record_service.py`、`tests/test_tool_presentation.py`、`tests/test_experiment_tool_command.py`。

## 12. 实验排期、仪器冲突与确认创建

### 手动页面路径

`web/frontend/experiment_confirmation.js` 向 `POST /experiments` 提交实验；`experiment_status.js` 更新状态；`history_panel.js` 查看或删除历史。

`web/api/experiments.py::add_experiment()` 在写入前先调用 `planner.conflicts.find_conflicts()`。如果时间或仪器冲突，返回 HTTP 409，不写入 SQLite。

### 智能体路径

`web/tools/experiment_tools.py` 实现两阶段创建：

```text
propose_experiment()
  -> 查冲突
  -> 放入 PENDING_EXPERIMENTS
  -> 要求用户确认

confirm_pending_experiment()
  -> 再次查冲突
  -> create_experiment()
  -> 写入 SQLite
```

### 边界

`PENDING_EXPERIMENTS` 是进程内字典，服务重启后待确认提案会失效。这是为了防止重启后误创建，但也说明它不是持久化审批流。

相关测试：`tests/test_agent_tool_presentation.py` 覆盖提案与确认工具的部分行为；排期 API 和真实页面流程仍需单独核查。

## 13. 确认后保存的长期信息

### 保存链

Agent 在识别到设备数量、固定规则或用户偏好等长期信息时，调用：

```text
propose_memory()
  -> PENDING_MEMORIES[conversation_id]
  -> 询问用户是否保存

confirm_pending_memory()
  -> database.crud.save_memory()
  -> SQLite
```

`web/agent/core.py::_memory_context()` 在后续请求中读取已确认记忆，加入模型上下文。`web/frontend/memory_panel.js` 通过 `/memories` 查看和删除。

### 边界

- 待确认内容同样保存在进程内字典，重启后失效；
- 当前是「结构化长期信息」，不是向量检索、RAG 或 SOP 知识库。

相关测试：`tests/test_agent_tool_presentation.py`。

## 14. 本地实验社区与远程社区代理

### 必须先分清两条路

#### 本地社区

`web/api/community.py` 使用 SQLite `community_entries`：

- 浏览和搜索；
- 发布 `protocol` 或 `reagent_prep`；
- 查看详情；
- 将社区内容导入个人方案库；
- 删除条目。

导入时会生成新 ID，避免覆盖本地已有方案或配方。

#### 远程社区代理

`web/api/community_proxy.py` 把 `/community-proxy/*` 转发到 `settings_store.current().community_base_url`，使用 `httpx.AsyncClient`，并处理超时和连接失败。

### 边界

- 本地社区是真实的 SQLite 功能；
- 远程社区是可配置的 HTTP 代理，是否真正可用取决于远程服务与网络；
- 本地删除目前注释明确说尚未增加作者/管理员鉴权，因此不应宣称已具备完整社区权限体系。

目前未从测试文件名中找到专门社区 API 端到端测试，需后续继续核查。

## 15. 流式 TTS、播放调度与语音打断

### 语音是如何产生的

`web/api/tts.py` 提供：

- `/tts/providers`：供应商、音色和当前配置；
- `/tts/models`：查询可用合成模型；
- `/tts`：非流式合成；
- `/tts/stream`：火山引擎 WebSocket 流式 PCM；
- `/tts/warmup`：第一句之前预建连接；
- `/tts/test`：真实合成测试及耗时。

`web/frontend/local_tts.js` 读取 `/tts/stream` 的 PCM 块并边收边播。

### 为什么还需「播放调度」

实验系统可能同时产生欢迎语、记录回执、关键追问、错误和结束摘要。`web/playback_runtime.py` 和 `src/core/*playback*` 按优先级决定播放、暂缓、丢弃或中断。

`web/api/voice_runtime.py` 接收：

```text
开始/结束说话
ASR 开始/结束/失败
TTS 开始/结束/停止/失败
```

这些事件更新 `VoiceRuntimeState`，并触发已暂缓语音的重新评估。浏览器最终是否播放成功，会通过 `/voice-runtime/client-result` 回报。

### 边界

代码与自动测试能证明状态机、优先级和中断调用；不能代替真实外放、耳机、麦克风自激、噪声和听感验收。

相关测试：`tests/test_web_tts_stream.py`、`tests/test_volcano_streaming_tts.py`、`tests/test_voice_runtime_state.py`、`tests/test_web_voice_runtime_event.py`、`tests/js/test_local_tts_barge_in.js`、`tests/js/test_voice_delivery_client.js`。

## 16. 这 15 项之间的真实关系

它们不是 15 个并排的页面，而是四层系统：

```text
交互层
  单次录音 / 手机 / 连续通话 / TTS

实验主线
  模式隔离 / 证据记录 / 主动追问 / 方案核对 / 控制命令

实验工具层
  方案库 / 配方库 / 专业计算 / Function Calling / 储存 / 排期

沉淀与协作层
  长期信息 / 本地社区 / 远程社区代理
```

最有作品辨识度的不是「功能数量有 15 项」，而是主线能否形成：

```text
用户口述
→ 保留原始证据
→ 理解实验事实
→ 写入结构化记录
→ 发现缺失或偏差
→ 主动追问
→ 将后续回答补回正确记录
→ 依方案规则判定进度
→ 屏幕和语音反馈
```

方案、计算、储存、排期、记忆和社区是为这条主线提供实验前后支撑，而不是与主线争抢定位。
