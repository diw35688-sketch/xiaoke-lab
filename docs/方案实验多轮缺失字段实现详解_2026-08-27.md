## 1. 本轮目标

本轮要完成的能力不是简单替换追问文字，而是：

> 在方案实验（protocol）模式下，允许用户分多次自然口述当前步骤的现场字段；系统累计已经记录的字段，再对照当前步骤的 `must_record`，确定还缺什么、是否追问以及追问什么。

同时保留以下边界：

- 聊天模式不参与实验字段判断。
- 自由实验（free）的初始追问仍由 LLM 决定。
- free 已有的部分补充状态要正确显示，不再出现“内部只剩一个字段，界面仍显示原来两个字段”的情况。
- protocol 的追问决定由确定性评价负责，LLM 只负责提取本轮实验实体。
- `ClarificationExecutor`、`ReplyCoordinator`、保存、卡片和语音仍走统一主链，不建立旁路。

## 2. 原来的问题

原来的处理顺序大致是：

```text
LLM observe()
→ LLM 同时给出 entities 和追问决定
→ 立即执行 observation.pending_action
→ 后面才 materialize analysis
→ 后面才聚合 entities
```

这导致两个问题。

### 2.1 protocol 无法成为确定性权威

执行追问动作时，程序还没有拿到完整实体，因此不能先对照 `must_record` 再决定动作。

例如：

```text
LLM：不需要追问
must_record：实际还缺 condition
```

原链路会直接执行 LLM 的 `NO_ACTION`。

反方向也一样：

```text
LLM：需要追问
must_record：实际已经完整
```

原链路仍可能创建问题。

### 2.2 每轮只看本轮实体

假设当前步骤要求：

```python
must_record = ("observation", "condition")
```

第一轮用户说：

```text
倒转混匀，溶液透明。
```

LLM 提取：

```python
{"observation": "溶液透明"}
```

第二轮用户自然继续说：

```text
室温保存。
```

LLM 提取：

```python
{"condition": "室温保存"}
```

如果第二轮只评价本轮实体，系统会错误地认为 `observation` 又缺失，从而重复追问已经说过的内容。

## 3. 调整后的主链

现在顺序调整为：

```text
读取会话状态
→ 统一理解
→ 物化正常结构化实验分析
→ 聚合本轮实体
→ 合并当前方案步骤的累计实体
→ 对照 must_record 做确定性评价
→ 生成 final_action
→ ClarificationExecutor 执行 final_action
→ 构造回复、卡片和实验记录
→ 在一个事务中保存记录、问题状态和累计状态
```

主入口仍是：

```text
web/turn_processors.py::ExperimentProcessor.prepare()
```

没有新增一条绕过统一理解、Executor 或 Store 的方案实验旁路。

## 4. 新增的累计状态模型

新增文件：

```text
src/core/protocol_completion_policy.py
```

### 4.1 ObservedFieldValue：保存值及其来源

```python
@dataclass(frozen=True)
class ObservedFieldValue:
    value: str
    request_id: str
    segment_id: int
```

它不只保存字段值，还保存来源。

例如：

```json
{
  "value": "溶液透明",
  "request_id": "r-protocol-1",
  "segment_id": 1
}
```

这样以后可以回答：

- 这个字段值是什么；
- 来自哪次请求；
- 来自第几段口述。

`frozen=True` 表示对象不能原地修改。状态变化必须生成新对象，避免其他模块突然看到被暗中修改的状态。

### 4.2 ProtocolStepFactState：当前步骤累计事实

```python
@dataclass(frozen=True)
class ProtocolStepFactState:
    protocol_id: str
    protocol_version: str
    step_number: int
    values: Mapping[str, ObservedFieldValue]
    clarification_id: str | None = None
```

它表示：

```text
当前是哪个方案
+ 方案版本
+ 当前步骤号
+ 当前步骤已经记录的字段和值
+ 当前步骤对应的追问 ID
```

一个实际快照可能是：

```json
{
  "protocol_id": "p1",
  "protocol_version": "1.0",
  "step_number": 1,
  "values": {
    "observation": {
      "value": "溶液透明",
      "request_id": "r-protocol-1",
      "segment_id": 1
    }
  },
  "clarification_id": "unified-1"
}
```

`clarification_id` 用来保证后续补充更新的是同一个问题，而不是每轮创建一个新问题。

## 5. 步骤和会话隔离

恢复累计状态时，会比较：

```python
protocol_id
protocol_version
step_number
```

核心代码：

```python
if not snapshot or (
    snapshot.get("protocol_id") != protocol_id
    or snapshot.get("protocol_version") != protocol_version
    or snapshot.get("step_number") != step_number
):
    return cls.empty(...)
```

因此：

- 切换方案后不继承旧方案字段；
- 方案版本变化后不继承旧版本字段；
- 切换步骤后不继承上一步字段；
- 数据库存储又以 `(conversation_id, lab_session_id)` 为会话身份，不同实验会话不会共用同一份累计快照。

当前只保证新步骤不继承旧字段。旧步骤尚未解决的问题还没有自动变成 `EXPIRED`，这是后续边界。

## 6. 字段合并规则

合并逻辑位于：

```text
ProtocolStepFactState.merge()
```

核心代码：

```python
for name, raw_value in contribution.items():
    value = raw_value.strip() if isinstance(raw_value, str) else ""
    if not value:
        continue

    previous = merged.get(name)

    if previous is None:
        merged[name] = ObservedFieldValue(
            value,
            request_id,
            segment_id,
        )
    elif previous.value != value:
        conflicts.append(name)
```

### 6.1 原来没有值：填入

第一轮：

```python
{"observation": "溶液透明"}
```

第二轮：

```python
{"condition": "室温保存"}
```

累计后：

```python
{
    "observation": "溶液透明",
    "condition": "室温保存",
}
```

### 6.2 重复相同值：保持不变

```text
第一轮：温度 25℃
第二轮：温度仍是 25℃
```

不会重复写入，也不会产生冲突。

### 6.3 新旧值不同：不静默覆盖

```text
第一轮：温度 25℃
第二轮：温度 28℃
```

当前行为：

```python
values["temperature"] == "25℃"
conflicting_fields == ("temperature",)
```

这样不会把用户改口、ASR 错误或真实修正混在一起。

当前只检测冲突并保护旧值，还没有创建“是否改成 28℃”的确认问题。

文件：

```text
web/turn_processors.py
```

### 7.1 读取状态

```python
stored = self._store.load_experiment_state(
    turn.conversation_id,

coordinator = ReplyCoordinator.from_snapshot(
```

三种状态各司其职：

|---|---|
| `ReplyCoordinator` | 问题编号、剩余字段、ACTIVE/RESOLVED/DEFERRED |
| `SessionContext` | 最近语义上下文 |
| `ProtocolStepFactState` | 当前方案步骤累计字段和值 |

### 7.2 只在 protocol 下恢复累计事实

```python
if turn.experiment_context == ExperimentContext.PROTOCOL:
    protocol_state = ProtocolStepFactState.from_snapshot(...)
```

free 不进入这里，所以 free 不使用 `ProtocolCompletionPolicy`。

### 7.3 统一理解保持不变

```python
observation = self._observer().observe(...)
```

LLM 仍然可以产生：

```text
events
entities
should_ask_follow_up
missing_fields
follow_up_question
pending_action
```

差别在于：

- free 最终仍采用 LLM 追问决定；
- protocol 只采用正常结构化实体，追问决定随后重新计算。

### 7.4 先物化分析，再聚合本轮实体

```python
analysis = observation.accepted_analysis.materialize_analysis()

for event in analysis.events:
    for name, value in vars(event.entities).items():
        if value and name not in entities:
            entities[name] = value
```

例如本轮得到：

```python
entities = {
    "condition": "室温保存"
}
```

这还是本轮事实，不是累计结果。

### 7.5 只有正常 protocol 实验进入累计

```python
if (
    turn.experiment_context == ExperimentContext.PROTOCOL
    and observation.accepted_analysis.kind
    == ExperimentAcceptanceKind.STRUCTURED_EXPERIMENT
):
```

因此：

- free 不进入；
- `DEGRADED_EVIDENCE_NOTE` 不进入；
- 正常结构化 protocol 实验才会累计字段。

接着执行：

```python
protocol_state, conflicting_fields = protocol_state.merge(
    entities,
    request_id=turn.request_id,
    segment_id=segment_id,
)
```

### 7.6 用累计实体做确定性评价

```python
evaluation = domain.evaluate_for_state(
    protocol_domain_state,
    protocol_state.entity_values(),
)
```

第二轮送入评价的不是：

```python
{"condition": "室温保存"}
```

而是：

```python
{
    "observation": "溶液透明",
    "condition": "室温保存",
}
```

这就是“第二轮不会重新追问 observation”的根本原因。

`evaluate_for_state()` 接收本 Turn 开始时捕获的同一份方案状态快照，避免显示步骤时读一次全局状态、评价时又读到另一个步骤。

### 7.7 得到 protocol 最终动作

```python
protocol_completion = resolve_protocol_completion(...)
final_action = protocol_completion.action
```

在进入 protocol policy 前：

```python
final_action = observation.pending_action
```

这只是 LLM 候选动作。

进入 protocol policy 后：

```python
final_action = protocol_completion.action
```

这才是最终权威动作。

没有修改原始 LLM analysis，因此记录中仍能看见 LLM 原本如何判断；只是执行层不再把它当 protocol 最终决定。

## 8. ProtocolCompletionPolicy 如何决定动作

核心函数：

```text
resolve_protocol_completion()
```

### 8.1 已有问题，累计事实补了字段

```python
newly_completed = tuple(
    field
    for field in existing.missing_fields
    if field not in missing
)
```

例如：

```python
existing.missing_fields = ("condition",)
missing = ()
```

得到：

```python
newly_completed = ("condition",)
```

Policy 生成：

```python
ClarificationAction(
    action_type=ClarificationActionType.ANSWER,
    target_clarification_id=existing.clarification_id,
    supplied_entity_fields=("condition",),
)
```

因此，即使 LLM 把“室温保存”识别为一条新实验记录，系统仍然会发现它补齐了旧问题的 condition，并更新原问题。

### 8.2 没有旧问题，但还缺字段

```python
ClarificationAction(
    action_type=ClarificationActionType.CREATE,
    question=question,
    missing_fields=missing,
)
```

例如：

```python
missing = ("condition",)
question = "请补充保存条件。"
```

### 8.3 不缺字段

```python
action = None
```

即使 LLM 判断需要追问，protocol 也不会创建问题。

### 8.4 已有问题但本轮没有补充有效字段

不会重复 `CREATE`。

Policy 保持原问题，回复层仍可显示确定性评价给出的当前问题文本。

## 9. 统一 Executor：为什么这不是旁路

真正执行动作的位置仍然是：

```python
if final_action is not None:
    execution = ClarificationExecutor(...).execute(final_action)
```

两种模式的区别只是 `final_action` 从哪里来：

```text
free：LLM pending_action
protocol：ProtocolCompletionPolicy action
```

两者继续共用：

- `ClarificationAction`
- `ClarificationExecutor`
- `ReplyCoordinator`
- TurnStore
- ConversationBlock
- VoiceDeliveryItem

所以 protocol 没有自己维护另一套问题编号、问题状态、保存逻辑或展示链。

## 10. 如何保证不重复创建问题

第一次 `CREATE` 执行成功后，Executor 返回：

```python
execution.affected_clarification_id
```

代码将它写回步骤累计状态：

```python
protocol_state = replace(
    protocol_state,
    clarification_id=execution.affected_clarification_id,
)
```

下一轮恢复状态后：

```python
existing = coordinator.find_clarification(
    protocol_state.clarification_id
)
```

于是后续补充会更新原问题，而不是创建新问题。

## 11. free 模式改了什么

free 没有使用 protocol 累计状态，也没有改变 LLM 初始追问权。

free 原来已经会更新内部剩余字段：

```python
missing_fields = ("temperature", "duration")
```

用户补充温度后：

```python
missing_fields = ("duration",)
```

问题在于原 `question` 文本仍然是：

```text
请补充温度和时间。
```

现在回复层读取更新后的问题状态：

```python
updated = coordinator.find_clarification(
    execution.affected_clarification_id
)
```

根据真实剩余字段生成：

```text
还需要补充：时间。
```

同时卡片保留：

```python
"original_question": updated.question
```

因此可以同时审计：

```text
原始问题：请补充温度和时间。
当前状态：还需要补充时间。
```

## 12. evaluation 的模式边界

构造 `lab_record` 时，protocol 使用：

```python
evaluation = {
    "missing_fields": protocol_completion.missing_fields,
    "follow_up_required": protocol_completion.follow_up_required,
    "follow_up_question": protocol_completion.follow_up_question,
    "deviations": protocol_completion.deviations,
    "conflicting_fields": protocol_completion.conflicting_fields,
}
```

free 仍使用：

```python
evaluation = {
    "missing_fields": observation.missing_fields,
    "follow_up_required": observation.follow_up_required,
    "follow_up_question": analysis.follow_up_question,
    "deviations": [],
}
```

结论：

```text
free 初始追问 → LLM 权威
protocol 初始追问 → must_record 确定性权威
```

## 13. 数据库如何持久化累计状态

表 `experiment_session_state` 新增：

```sql
protocol_step_facts_json TEXT NOT NULL DEFAULT '{}'
```

数据库初始化使用 `_ensure_column()`：

```python
_ensure_column(
    connection,
    "experiment_session_state",
    "protocol_step_facts_json",
    "TEXT NOT NULL DEFAULT '{}'",
)
```

因此：

- 新数据库直接具有该列；
- 旧数据库启动时自动增加该列；
- 不需要删除原数据库。

TurnStore 在同一个事务中保存：

```text
lab_record
reply_coordinator_json
session_context_json
protocol_step_facts_json
turn_requests committed 状态
```

这样可以避免：

```text
累计字段保存成功，但问题状态没保存
```

或：

```text
问题已经 resolved，但累计事实仍显示字段缺失
```

保存中途失败时，事务整体回滚。

## 22. 方案切步：允许带着暂缓欠账继续

这一阶段把方案切步从“修改全局游标”改为“修改指定实验会话的持久化步骤状态”。
核心规则是：

```text
ACTIVE 问题    → 阻止进入下一步
DEFERRED 问题  → 允许带着欠账进入下一步
没有缺失字段   → 完成当前步骤并进入下一步
```

### 22.1 为什么暂缓现在有实际作用

```text
步骤 1 缺 amount_value
→ 创建问题 1（ACTIVE，属于步骤 1）
→ 用户说“问题 1 暂缓”
→ 问题 1 变为 DEFERRED
→ 点击下一步
→ 步骤 1 标为 LEFT_WITH_PENDING
→ 当前步骤变为步骤 2
```

问题没有消失，也没有伪装成已完成。以后恢复问题 1 并回答时，答案写回步骤 1；
所有欠账解决后，步骤 1 才变成 `COMPLETED`。

### 22.2 新的会话级方案执行状态

新增 `src/core/protocol_execution_state.py`：

```text
ProtocolExecutionState
├─ protocol_id
├─ protocol_version
├─ current_step_number
├─ steps[step_number]       每一步自己的累计事实
└─ statuses[step_number]    每一步自己的进度状态
```

步骤状态为：

```text
NOT_STARTED
IN_PROGRESS
LEFT_WITH_PENDING
COMPLETED
```

旧版单步骤 `protocol_step_facts_json` 可以读取；首次保存后会转换成多步骤结构，数据库
不需要增加新列。

### 22.3 问题如何绑定原步骤

`PendingClarification` 新增：

```text

protocol_version
protocol_step_number
```

三者必须同时存在或同时为空：protocol 问题有完整归属，free 问题继续全部为空。
问题编号仍按整个 `lab_session_id` 连续递增，不按步骤重新从 1 开始。

### 22.4 确定性切步规则

新增 `src/core/protocol_navigation.py`。它是纯规则模块，不读数据库、不调用 LLM。

`NEXT` 的判断顺序：

```text

→ 当前步骤有 ACTIVE 问题：拒绝，提示先回答或暂缓
→ 缺失字段没有被 DEFERRED 问题完整承接：拒绝
→ 所有缺失字段均由 DEFERRED 问题承接：允许，LEFT_WITH_PENDING
```

`PREV` 和向后 `JUMP` 允许；向前只能进入紧邻下一步，不能直接跨过尚未依次处理的步骤。

## 23. 待设计：追问后的自然短回答与字段漂移

### 23.1 问题现象

系统上一轮提出单一问题后，用户下一句可能是：

```text
问题 3：终点时溶液颜色是什么？
用户：粉红色
```

这句话既不像完整实验记录，也没有显式携带“问题 3”。当前统一理解可能把它判为
`uncertain`，要求用户改说“溶液颜色为粉红色”。如果强制用户每次携带问题编号，
又不符合自然口述习惯。

另一个风险是字段漂移。同一个回答可能在不同轮次被模型标为不同字段：

```text
“室温” → temperature 或 condition
“粉红色” → observation、condition 或其他描述字段
```

因此不能只使用 `extracted_field == missing_field` 判断本句是否回答了当前问题。

### 23.2 短期建议策略

采用“当前问题锁定目标槽位，模型只提取回答值”的受限吸收策略：

```text
当前存在唯一 ACTIVE 问题
→ 问题自身提供目标 missing_field
→ 从下一句提取值候选
→ 用字段兼容规则检查该值是否适合目标字段
→ 兼容：写入问题指定的目标字段
→ 不兼容但构成完整实验事件：作为新实验记录，原问题保持 ACTIVE
→ 同时包含回答值和新操作：两边都处理
→ 两边都无法确定：才向用户请求消歧
```

例如当前问题目标字段是 `condition`，用户回答“室温”时，目标仍由问题确定为
`condition`；模型给出的 `temperature` 只能作为值的辅助解释，不能擅自改变写入槽位。

需要建立基础字段兼容规则，例如：

```text
temperature  ← 室温、80℃、冰浴
duration     ← 5分钟、半小时、过夜
observation  ← 粉红色、透明、有沉淀、产生气泡
condition    ← 室温保存、避光、冷藏、密封
amount       ← 2毫升、5克、三滴
```

该策略不要求日常回答携带问题编号；编号只作为多问题并存或语义歧义时的显式消歧手段。

### 23.3 长期字段模型方向

当前扁平字段 `temperature`、`condition`、`observation` 的语义存在重叠。长期应考虑
把累计事实和 `must_record` 改成带实验上下文的路径：

```text
storage.temperature
storage.light_condition
reaction.temperature
reaction.duration
endpoint.observation.color
```

原始用户证据与字段投影需要分开保存：

```json
{
  "target_field": "condition",
  "value": "室温",
  "source_text": "室温",
  "interpreted_as": "temperature"
}
```

这样可以保留用户原话，同时避免模型字段标签变化导致同一个问题时而补成功、时而失败。

### 23.4 当前状态

本节仅登记设计问题，尚未实现：

- 单一当前问题的自然短回答吸收策略。

### 24.2 页面现在展示什么

## 25. 给“待确认账”增加补充答案投影

“实验口述”只展示会生成实验记录的事实 Turn；回答问题属于问题生命周期 Turn，不会生成
一条假的 `lab_record`。因此用户此前能看到“问题已解决”，却看不到自己具体回答了什么。

本轮没有改变保存模型，而是在统一账本读取时增加一层可追溯投影：

```text
PendingClarification.clarification_id
            ↑
回答 Turn 的 confirmation_card.clarification_id
            ↓
turn_requests.raw_text                 → 用户答了什么
turn_requests.request_id
            ↓
ProtocolStepFactState.values[*].request_id
            ↓
字段名 + 最终累计值                       → 最终写入了什么
```

### 25.1 为什么不只用 last_updated_segment_id

`last_updated_segment_id` 能说明问题在哪个逻辑段落被更新，但控制类回答不一定新增
`lab_record`，多个控制 Turn 也可能看到相同的 next segment id。仅靠这个数字反查会有把
答案挂错问题的风险。

当前实现采用更强的主关联：回答 Turn 的 `confirmation_card` 直接保存
`clarification_id`；`last_updated_segment_id` 保留为问题状态的辅助时间线证据。只有旧
Turn 缺少问题身份时才无法投影，并且系统不会根据问题文本或答案文本猜测归属。

### 25.2 页面展示规则

每个有回答证据的问题下新增“补充答案”：

```text
补充答案
  用户答了：室温保存
  最终写入：实验条件=室温
```

一个问题分多轮补齐时，每个回答 Turn 单独显示一项；每项只列出由该 Turn 的
`request_id` 首次写入步骤累计事实的字段。这样“原文”和“结构化结果”不会混为一谈。

### 25.3 证据边界

- 方案实验的步骤累计事实为字段保存了 `value/request_id/segment_id`，所以字段值关联是
  可验证的确定性连接。
- 历史 Turn 若有问题卡片身份，就能恢复回答原文。
- 旧 Turn 若没有 `clarification_id`，系统不做文本猜测，因此不会错误挂账。
- free 模式目前没有 `ProtocolStepFactState` 这类步骤累计字段账；可展示能关联的问题回答
  原文，但不会伪造“最终写入字段”，页面会明确显示未找到可验证关联。

## 26. 通用偏差等价比较与“期望/实际”展示

旧偏差规则直接执行 `actual_value != protocol_value`。实体抽取成功只说明系统知道用户
说了什么，并不代表字符串和方案目标逐字相同，因此会把“称取/称量”“克/g”等等价表达
误报为偏差。

本轮把偏差判断拆成两层：

```text
实际实体原文
→ 通用、保守的字段归一化
→ 当前方案步骤声明的局部别名
→ 与 protocol_values 比较
→ 仍不等价才生成 ProtocolDeviation
```

### 26.1 通用规则与局部规则的职责

通用规则位于 `src/core/protocol_value_equivalence.py`，第一版只处理低歧义表达：

- 动作：`称取/称重 → 称量`
- 单位：`克 → g`、`毫升 → ml` 等
- 数值字符串：`3.50 → 3.5`
- 温度写法：`60摄氏度 → 60℃`

专业对象简称不能进入全局表。步骤可以声明可选 `value_aliases`：

```json
"protocol_values": {
  "object": "磷酸二氢盐和磷酸氢二盐"
},
"value_aliases": {
  "object": ["磷酸盐"]
}
```

这条别名只对当前方案的当前步骤生效。另一个步骤或另一个实验即使也出现“磷酸盐”，
没有自己的声明就不会自动判等。

### 26.2 “验证过才生效”的技术含义

`ProtocolStore` 仍采用严格字段白名单。`value_aliases` 出现时必须满足：

- 是字段到字符串数组的映射；
- 字段已经存在于本步骤 `protocol_values`；
- 每个别名非空且不重复；
- 整份方案仍通过版本、步骤连续性和其他合同校验。

只有成功加载成不可变 `ProtocolStep` 的局部别名会进入比较器。系统不会从 LLM 输出、
用户自由口述或其他实验中自动学习别名。这里的“通过验证”是程序合同验证；专业内容是否
科学合理，仍由方案维护者在把别名写入正式方案前确认。

### 26.3 截图案例的新结果

方案步骤 1 的期望与实际为：

```text
action:       称量 / 称取       → 通用规则判等
object:       完整盐名称 / 磷酸盐 → 本步骤局部别名判等
amount_unit:  g / 克             → 通用规则判等
amount_value: 3.58 / 3.5         → 不相等，保留真实偏差
```

所以最终只有一条：

```text
偏差：体积或质量数值
期望：3.58 · 实际：3.5
```

### 26.4 历史记录为什么需要展示投影

旧实验段已经把严格字符串比较产生的四条偏差保存进 `lab_records.evaluation`。修改比较器
不会自动重写数据库。统一账本读取时会根据记录自身保存的
`protocol_id + protocol_version + step_number` 找到同版本方案并重新生成展示用偏差：

```text
数据库原 evaluation.deviations → 保留为 stored_deviations
当前规则重新评价              → 页面使用 deviations
deviation_rule_version         → 2
```

只有方案 ID、版本和步骤都准确匹配才重新投影；版本不同则原样展示历史结果，避免拿新版方案
解释旧版实验。数据库原记录没有被修改。

### 26.5 代码位置

- `src/core/protocol_value_equivalence.py`：通用归一化和统一等价入口。
- `src/core/protocol.py`：步骤局部别名合同，以及字段来源判定复用同一等价规则。
- `src/core/protocol_deviations.py`：偏差检测复用同一等价规则。

## 27. 待实现设计：指代消解、字段归类与固定写入合同

### 27.1 要解决的三个表象问题

当前暴露出的三个问题看似不同：

1. 用户省略实验对象时，LLM 可能输出泛称 `object=样品`，而没有落到具体的
   `object=磷酸盐`；
2. “管壁均匀”有时可能被归入 `condition`，有时被归入 `observation`；
3. 回答同一个问题时，“最终写入”会随着本轮抽取出的实体数量变化，并非固定字段集合。

三者的共同根因是：当前链路在若干位置把“LLM 或规则抽取器提出了什么”直接当成了
“步骤事实最终写入什么”，缺少独立、确定性的落账准入层。

目标链路应改为：

```text
用户原话
→ LLM/规则抽取器提出候选实体
→ 指代消解：候选具体指向什么
→ 字段归类：该事实属于哪个字段
→ 问题写入合同：本轮允许补哪些字段
→ 确定性落账：只写入有证据且被合同允许的字段
```

LLM 只提出候选，不拥有最终落账权限。

### 27.2 问题必须保存不可变的写入合同

当前 `PendingClarification.missing_fields` 同时承担“问题最初要什么”和“现在还缺什么”两种
含义；问题解决后它会变成空数组，历史上就无法再判断该问题原来允许写入哪些字段。

应拆为：

```json
{
  "requested_fields": ["amount_value", "observation"],
  "remaining_fields": ["amount_value", "observation"]
}
```

- `requested_fields`：创建问题时固定，问题整个生命周期内不可变；
- `remaining_fields`：多轮回答后逐步减少；
- 旧快照兼容：没有 `requested_fields` 时，用创建时可恢复的字段初始化；如果证据不足，
  不猜测历史合同。

每轮最终允许写入的集合必须是：

```text
requested_fields
∩ remaining_fields
∩ 本轮具有可靠证据的已解析候选字段
```

因此不能继续把完整的 `answer_values` 直接交给：

```python
protocol_state.merge(answer_values)
```

应先生成受限贡献：

```python
allowed_fields = set(question.remaining_fields)
accepted_values = {
    field: value
    for field, value in resolved_candidates.items()
    if field in allowed_fields
}
protocol_state.merge(accepted_values)
```

即使抽取器额外识别出 `action/object/instrument/amount_unit`，只要它们不在当前问题合同内，
就不能作为本轮问题回答写入。

### 27.3 指代消解：泛称不是最终实体值

“样品、溶液、它、该试剂”等词可以作为指代候选，但不应直接作为标准化 `object` 值。

示例：

```text
步骤 1：称取磷酸盐
步骤 2：加入烧杯溶解
```

正确解析过程：

```text
本轮对象被省略，或 LLM 候选为“样品”
→ 当前步骤 protocol_values.object = 磷酸盐
→ 前一步累计 object = 磷酸盐
→ 两份证据一致，且不存在第二候选对象
→ 解析为 object=磷酸盐
```

应保留来源证据：

```json
{
  "field": "object",
  "value": "磷酸盐",
  "source": "context_resolution",
  "raw_candidate": "样品",
  "evidence": {
    "protocol_step_number": 2,
    "protocol_value": "磷酸盐",
    "previous_step_value": "磷酸盐"
  }
}
```

确定性准入规则：

1. 本轮明确说出具体对象时，以本轮有原文证据的对象为候选；
2. 本轮使用泛称或省略对象时，才允许进入上下文解析；
3. 当前步骤方案对象与累计上下文一致，并且候选唯一时，可解析成标准对象；
4. 有多个候选、前后冲突或跨步骤关系不明确时，不自动解析；
5. 无法唯一解析时保留空值，必要时进入追问，而不是写入“样品”。

### 27.4 condition 与 observation 的字段边界

通用字段语义固定为：

| 字段 | 含义 | 示例 |
|---|---|---|
| `observation` | 用户现场看到、听到或读到的结果和状态 | 管壁均匀、溶液澄清、出现浅红色 |
| `condition` | 实验过程、环境或保存所处的条件 | 室温保存、避光、冷藏、pH 7.4 |

判定不能只靠开放式 LLM 分类，而要按以下顺序收窄：

```text
字段是否有原文证据
→ 当前问题 requested_fields 允许哪些字段
→ 当前步骤 must_record 需要哪些字段
→ 通用字段语义是否匹配
→ 唯一匹配才写入
```

例如当前问题只允许 `observation`，用户回答“管壁均匀”：

```text
当前允许字段：observation
文本语义：可观察状态
→ observation=管壁均匀
```

即使 LLM 候选为 `condition=管壁均匀`，也不能直接写进 condition。若问题同时允许
`condition` 和 `observation`，而一句话无法可靠拆分，则保留不确定，不强行落账。

### 27.5 润洗步骤的数据合同需要同步修正

当前润洗步骤只声明：

```json
"must_record": ["observation"],
"field_prompts": {
  "observation": "滴定管实际润洗了几次？润洗后管壁看起来是否均匀？"
}
```

这里一个字段同时承载“次数”和“观察现象”，导致问题合同本身不稳定。应改为：

```json
{
  "protocol_values": {
    "action": "润洗",
    "object": "氢氧化钠标准溶液",
    "instrument": "碱式滴定管",
    "amount_unit": "次"
  },
  "must_record": [
    "amount_value",
    "observation"
  ],
  "field_prompts": {
    "amount_value": "滴定管实际润洗了几次？",
    "observation": "润洗后管壁看起来是否均匀？"
  }
}
```

回答：

```text
润洗了2次，管壁均匀
```

固定接受：

```text
amount_value=2
observation=管壁均匀
```

不作为本轮用户回答写入：

```text
amount_unit=次       # 方案已知值
action=润洗          # 不在当前问题合同内
object=滴定管        # 字段归类错误且不在问题合同内
```

### 27.6 步骤累计事实需要按来源分层

当前单一 `values` 容易把方案默认、用户明说和上下文解析混成同一种事实。目标模型至少区分：

```json
{
  "protocol_defaults": {
    "action": "润洗",
    "object": "氢氧化钠标准溶液",
    "instrument": "碱式滴定管",
    "amount_unit": "次"
  },
  "observed_values": {
    "amount_value": {
      "value": "2",
      "request_id": "回答Turn",
      "source": "literal_answer"
    },
    "observation": {
      "value": "管壁均匀",
      "request_id": "回答Turn",
      "source": "literal_answer"
    }
  },
  "resolved_context": {
    "object": {
      "value": "磷酸盐",
      "source": "protocol_and_previous_step"
    }
  }
}
```

这里的核心不是必须立刻拆成三个数据库列，而是领域快照和投影必须保留来源类型，不能再让
“方案给定”“用户回答”“上下文推断”在界面中都显示为“最终写入”。

### 27.7 回答贡献需要成为一等证据

建议为每个回答 Turn 保存不可变贡献记录：

```json
{
  "clarification_id": "问题身份",
  "request_id": "回答Turn身份",
  "raw_text": "润洗了2次，管壁均匀",
  "requested_fields": ["amount_value", "observation"],
  "candidate_values": {
    "amount_value": "2",
    "amount_unit": "次",
    "observation": "管壁均匀"
  },
  "accepted_values": {
    "amount_value": "2",
    "observation": "管壁均匀"
  },
  "rejected_candidates": {
    "amount_unit": {
      "value": "次",
      "reason": "不在当前问题 remaining_fields 中"
    }
  }
}
```

这样“最终写入”直接读取 `accepted_values`，不再事后根据当前累计状态和 request_id 反推，
从而保证同一已提交回答的投影稳定。

### 27.8 页面展示目标

待确认账应把不同证据类型分开：

```text
问题 1：实际润洗次数和管壁状态？

用户回答

本次接受写入
实际次数=2
观察现象=管壁均匀

单位=次
操作=润洗
仪器=碱式滴定管
```

指代解析可显示：

```text
上下文解析
“样品” → 磷酸盐

依据
当前步骤对象=磷酸盐
前一步累计对象=磷酸盐
```

默认界面可以只显示“用户回答”和“本次接受写入”；依据和拒绝候选放在可展开详情中，避免
普通用户被审计信息淹没。

### 27.9 protocol 与 free 的边界

方案实验可以使用强合同：

```text
protocol_values + must_record + requested_fields + remaining_fields
```

因此最终写入可以完全确定。free 模式没有方案步骤合同，但已经由某个追问创建的问题仍应
保存自己的 `requested_fields`；回答该问题时同样只能写入问题允许字段。free 模式的自然
实验口述仍可由语义抽取产生新的记录事实，不与“回答问题的受限写入”混为一条路径。

### 27.10 推荐实施顺序

### 27.11 验收标准

- 同一已提交回答无论刷新多少次，“本次接受写入”字段和值都不变化；
- 回答问题时，额外抽取字段不能越过 `remaining_fields` 写入；
- “润洗2次，管壁均匀”固定写入 `amount_value=2` 和
  `observation=管壁均匀`；
- `amount_unit=次`显示为方案已知值，不显示为用户补充；
- “加入烧杯溶解”在候选唯一时解析为 `object=磷酸盐`，不落账为“样品”；
- 多候选或上下文冲突时不擅自解析；
- “管壁均匀”不会写入 condition，“室温保存”不会写入 observation；
- protocol 与 free 的问题回答都遵守各自问题的不可变写入合同；
- 旧问题快照可以加载，无法恢复的历史合同明确降级而不猜测。
