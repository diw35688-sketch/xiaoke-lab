## 1. 第 19 项：工具入口改用共享记录服务

### 一句话结果

现在聊天工具里的“记录实验”与网页 `/record` 使用同一套记录业务逻辑，但这一项暂时没有处理工具结果怎样显示和播报。

### 用户操作发生了什么

用户在聊天中要求记录实验
→ Agent 调用 `record_observation` 工具
→ 工具构造统一的 `RecordCommand`
→ `SharedRecordService` 分配段号、抽取实体、评估并保存
→ 工具把原有五个字段返回给 Agent
→ 这一阶段尚未消费共享服务生成的呈现意图

### 代码位置

- 工具入口：`web/lab_tools.py`
- 共享记录服务：`web/record_service.py`
- 记录命令：`RecordCommand`
- 共享结果：`SharedRecordResult`
- 当前保留的工具结果字段：`transcript / entities / missing_fields / follow_up_question / deviations`

### 为什么重要

如果网页记录和聊天工具各自维护一套抽取、评估和保存流程，修复一个入口后另一个入口仍可能保留旧问题。统一服务以后，核心记录规则只有一份。

### 对应的专业知识

这叫**应用服务（Application Service）**和**入口适配器（Adapter）**分离。`SharedRecordService` 负责一次“记录实验”用例的完整业务编排；`/record` 和 `record_observation` 只是不同适配器。它也使用了**依赖注入（Dependency Injection）**：保存函数、评估器和实体抽取器由外部传入，所以服务可以在测试中替换依赖，而不必连接真实数据库或模型。

### 当时唯一下一步

只处理工具结果的确定性呈现，不同时改聊天流事件和语音播放。

## 2. 第 20 项：工具结果不再交给模型二次改写

### 一句话结果

记录工具成功后，系统能够直接使用统一呈现计划生成屏幕回复，不再让模型对保存结果进行第二次自由改写。

### 用户操作发生了什么

用户要求记录实验
→ Agent 调用记录工具
→ 共享记录服务完成保存并产生语义意图
→ `PresentationDeliveryPlan` 把意图转成确定性文案
→ `WebRenderer` 生成屏幕内容
→ Agent 直接返回这段文案
→ 不再调用第二次模型补写“已记录”或追问

### 代码位置

- 工具适配：`web/lab_tools.py`
- 工具呈现：`web/tool_presentation.py`
- Agent 工具执行：`web/agent/core.py`
- 呈现计划：`PresentationDeliveryPlan`
- Web 渲染：`WebRenderer.render_plan()`

### 为什么重要

模型二次改写会让相同的保存结果产生不同文案，也可能丢掉追问、擅自承诺成功或增加未保存的信息。确定性呈现让“保存结果”和“用户看到的回复”保持一致。

### 对应的专业知识

这里使用的是**确定性投影（Deterministic Projection）**：把结构化业务结果按照固定规则投影成屏幕文案和语音候选，而不是再次调用概率模型。`PresentationIntent → PresentationDeliveryPlan → WebRenderer` 也体现了**关注点分离（Separation of Concerns）**：业务层表达“想告诉用户什么”，呈现层决定“用什么文案表达”。

### 当时唯一下一步

只把聊天正文改成纯屏幕事件，不同时接入语音授权事件。

## 3. 第 21 项：普通聊天正文只负责上屏

### 一句话结果

普通助手正文现在通过 `screen_delta` 只更新屏幕，不再同时隐式决定是否播报。

### 用户操作发生了什么

用户发送聊天消息
→ 服务端流式生成普通助手正文
→ 后端把正文包装成 `screen_delta`
→ 浏览器累积文字并更新回复区域
→ 浏览器不读取 TTS 开关
→ 浏览器不从这条正文直接调用语音播放

### 代码位置

- 流事件合同：`web/stream_contract.py`
- 聊天流路由：`web/api/chat.py`
- 当前桌面流式客户端：`web/frontend/streaming_chat_v2.js`
- 事件构造器：`agent_chunk_event()`
- 屏幕事件：`screen_delta_event()`

### 为什么重要

同一段文字如果既代表“显示内容”又代表“允许播放”，任何普通回复都可能绕过播放时机、抢占和用户讲话状态。拆开以后，文字能显示不等于它获得了播放许可。

### 对应的专业知识

这是**命令与事件语义分离**。`screen_delta` 是展示事件，只描述屏幕增量；播放需要另一条带授权语义的事件。也可以把它理解为**能力安全（Capability-based Security）**：拿到文本不等于拿到操作扬声器的能力，只有正式播放授权才授予这个能力。

### 当时唯一下一步

定义后端正式的 `voice_delivery` 候选事件。

## 4. 第 23 项先行：删除 `delta` 直接播报旁路

### 一句话结果

旧 `delta` 事件仍可兼容显示文字和控制标记，但不能再直接调用 `enqueueSpeech()` 播放正文。

### 用户操作发生了什么

旧客户端收到 `delta`
→ 继续识别 `LABTHINK` 和 `LABCARD` 控制标记
→ 兼容文字仍可显示
→ 不再检查 `shouldSpeak()`
→ 不再拆分完成句子
→ 不再把正文送入 `enqueueSpeech()`

### 代码位置

- 当前客户端：`web/frontend/streaming_chat_v2.js`
- 遗留客户端：`web/frontend/streaming_chat.js`
- 被删除的旧路径：`delta → shouldSpeak → takeCompletedSentences → enqueueSpeech`

### 为什么重要

只要旧旁路存在，将来即使建立了正式播放调度，正文仍可能从另一条路直接发声，造成重复播报或在用户讲话时抢话。

### 对应的专业知识

这类旧路径叫**旁路（Bypass）**或**影子执行路径（Shadow Execution Path）**。系统表面上有统一调度器，但旧代码仍能直接产生副作用，就会形成**双重写入/双重执行**风险。删除旁路的重点不是删函数，而是保证所有播放副作用只能经过一个可信边界。

### 当时唯一下一步

回到尚未完成的第 22 项，只建立后端语音候选事件。

## 5. 第 22 项：后端产生独立语音候选事件

### 一句话结果

后端现在能够把适合播报的内容放进独立 `voice_delivery` 事件，但此时它只是内容候选，不是最终播放许可。

### 用户操作发生了什么

记录工具保存成功
→ 呈现计划产生屏幕内容和可能的语音内容
→ 同轮多个工具的计划先合并
→ 重新计算整轮语音预算
→ 后端先发送屏幕文字
→ 只有存在语音项时才发送 `voice_delivery`
→ 事件授权状态暂时是 `CONTENT_ELIGIBLE`

### 代码位置

- 工具语音批次：`web/tool_presentation.py`
- Agent 输出：`web/agent/core.py`
- 流事件映射：`web/stream_contract.py`
- SSE 路由：`web/api/chat.py`
- 关键对象：`ToolVoiceDeliveryBatch`
- 关键字段：`intent_id / kind / priority / voice_text / authorization`

### 为什么重要

内容适合播报只回答“能不能读”，没有回答“现在是否应该读”。只有把候选内容独立出来，后续调度器才能结合用户讲话、当前播放和优先级决定 `READY / DEFERRED / DROP / PREEMPT`。

### 对应的专业知识

这里区分了**资格判断（Eligibility）**和**运行时许可（Runtime Authorization）**。前者是内容策略，例如追问适合播报；后者是调度策略，例如用户正在讲话，所以现在不能播。`CONTENT_ELIGIBLE` 是事实声明，不是执行命令。这种分层可以避免静态内容规则偷读动态设备状态。

### 当时唯一下一步

只删除 `task_queued` 事件的直接播报旁路。

## 6. 第 24 项：删除 `task_queued` 直接播报旁路

### 一句话结果

后台任务进入队列时仍会显示状态并刷新任务面板，但不会再从 `task_queued` 事件直接发声。

### 用户操作发生了什么

用户发起后台任务
→ 服务端发送 `task_queued`
→ 浏览器显示排队文案
→ 保存 `conversation_id`
→ 更新头像和任务面板
→ 不再执行 `enqueueSpeech(answer)`

### 代码位置

- 当前客户端：`web/frontend/streaming_chat_v2.js`
- 遗留客户端：`web/frontend/streaming_chat.js`
- 独立后台完成通知：`web/frontend/task_panel.js`

### 为什么重要

如果排队事件能够直接播报，它就绕开正式播放授权。删除这条旁路又不能误删后台任务完成/失败通知，因为后者是另一条明确的产品通知路径。

### 对应的专业知识

这里体现的是**事件类型的单一语义（Single Semantic Meaning）**：`task_queued` 表示任务状态变化，不应该顺便承担播放命令。保留 `task_panel` 的完成通知则体现了**范围控制（Scope Control）**：修复一条旁路时，通过反向测试保护不属于本轮的合法通知路径。

### 当时唯一下一步

建立浏览器唯一的语音授权事件执行入口。

## 7. 第 25 项：浏览器只执行正式播放授权

### 一句话结果

浏览器新增唯一的 `voice_delivery` 消费入口，只有收到 `READY` 或 `PREEMPT` 才真正操作 TTS。

### 用户操作发生了什么

浏览器收到 `voice_delivery`
→ 校验事件结构、意图字段和 `voice_text`
→ 检查用户是否启用语音
→ `CONTENT_ELIGIBLE` 只记为候选，不播放
→ `DEFERRED / DROP / 未知状态` 不播放
→ `READY` 才调用 `enqueueSpeech`
→ `PREEMPT` 才先停止旧语音，再播放新内容

### 代码位置

- 唯一消费适配器：`web/frontend/voice_delivery_client.js`
- 脚本加载顺序：`web/app.py`
- 当前流式客户端委托：`web/frontend/streaming_chat_v2.js`
- 遗留流式客户端委托：`web/frontend/streaming_chat.js`
- 统一入口：`window.consumeVoiceDelivery(data)`

### 为什么重要

这把“显示什么”和“什么时候发声”彻底分离。页面其他模块不能因为拿到一段文字就自行播报，必须拿到运行时授权。

### 对应的专业知识

`voice_delivery_client.js` 是浏览器侧的**执行端口（Execution Port）**和**防腐层（Anti-corruption Layer）**。它把服务端领域状态翻译成浏览器 TTS 操作，并拒绝坏 payload、未知状态和不完整能力。`READY`、`DEFERRED`、`DROP`、`PREEMPT` 可以看作一个小型**状态协议（State Protocol）**，而不是几条随意的字符串分支。

### 当时唯一下一步

把 `/record`、chat tool 和浏览器执行端接到同一个播放调度服务。

## 8. 第 26 项：三个入口共用播放调度

### 一句话结果

网页录音记录、聊天工具记录和浏览器语音执行开始共用同一个 `PlaybackScheduler`，但服务器当时还不知道浏览器真实的 VAD/TTS 状态。

### 用户操作发生了什么

用户通过 `/record` 或 chat tool 产生可播报内容
→ 内容先成为 `VoiceDeliveryItem`
→ `WebPlaybackService` 创建带 TTL 的 `PlaybackRequest`
→ 统一 `PlaybackScheduler` 根据服务器快照决定状态
→ 结果作为 `voice_delivery_events` 或 SSE 事件交给浏览器
→ 桌面与手机只调用 `consumeVoiceDelivery()`
→ 浏览器根据授权决定是否执行 TTS

### 代码位置

- Web 播放服务：`web/playback_runtime.py`
- `/record` 路由：`web/api/record.py`
- chat 路由：`web/api/chat.py`
- Agent 工具链：`web/agent/core.py`
- 桌面录音客户端：`web/frontend/voice_asr.js`
- 手机客户端：`web/frontend/mobile.js`
- 浏览器执行端口：`BrowserPlaybackExecutionPort`

### 为什么重要

统一调度解决了多个入口分别决定播放的问题，但这一阶段服务器默认看到的是“空闲快照”。如果浏览器已经检测到用户讲话却没有上报，服务器仍可能错误地认为可以播放。

### 对应的专业知识

这是**集中式调度（Centralized Scheduling）**与**分布式状态一致性（Distributed State Consistency）**问题。浏览器掌握麦克风和扬声器的真实状态，服务器掌握播放队列和业务优先级；两端状态没有同步时，服务器只能根据过期或默认快照决定。`PlaybackRequest` 的 TTL 则是**时效性约束**，防止过时语音在很久以后突然播放。

### 当时唯一下一步

先用自动验收冻结各层职责和禁止旁路，不立即实现 Silero 实时状态上报。

## 10. 真实验收：录音键变红但没有开始录音

### 一句话结果

真实验收暴露出“按钮状态改变”不等于“麦克风采集和录音链路已经成功启动”，当时不能仅凭红色按钮判断录音可用。

### 用户操作发生了什么

用户点击录音键
→ 页面把按钮切成红色
→ 用户预期浏览器开始采集声音
→ 实际没有出现正常录音和识别结果
→ 说明视觉状态与真实媒体状态不一致，或者后续采集/识别链没有启动

### 代码位置

- 桌面录音入口：`web/frontend/voice_asr.js`
- 麦克风权限与媒体采集：浏览器 `getUserMedia` 相关处理
- ASR 后端接口：`web/api/asr.py` 及其调用链
- 页面按钮和状态绑定：`web/app.py` 生成的桌面页面及对应前端脚本

### 为什么重要

按钮变红只是 UI 状态，不能证明麦克风权限、音频帧采集、上传和 ASR 都成功。真实验收必须观察整条链，而不能把颜色变化当作完成证据。

### 对应的专业知识

这是**表示状态（Presentation State）**与**领域/设备状态（Domain or Device State）**不一致。按钮颜色只是前端视图状态；真正的录音状态至少包含媒体权限、`MediaStream`、音轨活动、音频帧产生和后端识别。工程上应让 UI 从真实状态机投影，而不是点击后先乐观地假设成功；后者叫**乐观 UI（Optimistic UI）**。

### 当时唯一下一步

先确认浏览器是否真实获得麦克风流并产生音频数据，不同时诊断追问和 TTS。

→ 系统提出确定性问题

### 对应的专业知识

这是**故障域缩小（Fault-domain Isolation）**和**差分诊断（Differential Diagnosis）**：寻找正常路径与异常路径的最小差异。方案模式正常、自由模式异常，说明共享的 clarification 基础设施大概率仍工作，应优先检查模式分支、评估来源和覆盖优先级。

→ 界面仍显示开启或当前声音没有停止
→ 页面没有单独显示“立即静音”操作
→ “以后不再播”和“立刻停止正在播”在交互上没有被清楚区分

### 代码位置

- TTS 设置：`web/frontend/tts_settings.js`
- 通用设置同步：`web/frontend/settings.js`
- 本地播放控制：`web/frontend/local_tts.js`
- 播放授权执行：`web/frontend/voice_delivery_client.js`
- 页面喇叭控件：`web/app.py` 生成的桌面页面

### 为什么重要

“禁用后续播报”和“停止当前播报”是两个不同动作。前者改变策略，后者调用执行层的 stop。如果 UI 把两者画成同一个喇叭，用户无法判断系统究竟做了什么。

### 对应的专业知识

这里要区分**配置状态（Configuration State）**和**运行时命令（Runtime Command）**。`tts_enabled=false` 是持久或会话配置，影响未来请求；`stopSpeech()` 是有即时副作用的命令，影响当前执行。交互设计上这属于**控制语义可发现性（Affordance）**：图标和反馈必须让用户知道自己是在改策略还是执行停止。

### 当时唯一下一步

先明确喇叭控件的正式语义：它只控制后续播报，还是同时承担立即停止；不要同时改动画和播放调度。

## 13. 真实验收：自由实验只剩“已记录”

### 一句话结果

自由实验的统一理解其实能够生成追问，但 Web 桥没有完整传递，随后自由模式的空方案评估又覆盖了它，所以最终只剩“已记录”。

### 用户操作发生了什么

用户口述一条信息不完整的自由实验记录
→ 统一理解识别实体和缺失字段
→ 统一理解生成 `should_ask_follow_up` 和问题文本
→ Web 桥只保留了部分实体信息
→ 自由模式方案评估返回空追问
→ 空评估覆盖语义追问
→ 保存后页面只显示记录成功

### 代码位置

- 统一理解到 Web 的桥：`web/llm_bridge.py`
- 共享记录服务：`web/record_service.py`
- 有效评估选择：`_select_effective_evaluation()`
- 桥接回归测试：`tests/test_web_llm_bridge.py`
- 自由/方案模式回归：`tests/test_shared_record_service.py`

### 为什么重要

这证明问题不是“模型不会问”，而是“已经生成的信息在集成链路里丢失并被覆盖”。如果只改提示词，模型即使生成更强的追问，后面的代码仍会丢掉它。

### 对应的专业知识

这类问题属于**数据合同漂移（Data Contract Drift）**和**信息丢失（Information Loss）**。上游对象增加了 `missing_fields` 和追问字段，但适配器没有完整映射；随后默认空评估发生**覆盖（Overwrite）**。诊断时应逐层检查 schema，而不是从最终 UI 直接推断上游模型失败。

### 当时唯一下一步

把这个遗漏正式加入唯一任务路线，定义自由模式和方案模式各自的追问权威。

## 14. 第 28 项：恢复自由实验语义追问

### 一句话结果

自由实验现在保留统一理解生成的追问，方案模式继续使用确定性方案问题，而且两种追问都只能在记录保存成功后呈现。

### 用户操作发生了什么

用户说“加热样品”
→ 统一理解识别 `action=加热`、`object=样品`
→ 判断缺少 `duration`
→ 生成“样品加热了多长时间？”
→ Web 桥完整传递追问字段
→ 自由模式选择语义追问作为有效评估
→ 当前记录先保存
→ 保存成功后产生 clarification
→ 页面显示或申请播报追问

### 代码位置

- 字段透传：`web/llm_bridge.py`
- 模式权威选择：`web/record_service.py::_select_effective_evaluation()`
- 保存后结果：`web/record_service.py::_shared_result_after_save()`
- 自由模式测试：`tests/test_shared_record_service.py::test_free_mode_preserves_unified_follow_up_after_save`
- 方案模式保护测试：`tests/test_shared_record_service.py::test_protocol_mode_keeps_deterministic_follow_up_authority`

### 为什么重要

实体抽取回答“目前记录到了什么”，追问回答“还缺什么”。两者必须一起保存，后续用户回答“10 分钟”时，系统才能知道它是在补充上一条加热记录，而不是一条孤立的新记录。

### 对应的专业知识

`_select_effective_evaluation()` 实现的是**决策权威规则（Source of Truth / Authority Rule）**：自由模式没有确定性方案依据，所以采用正常模型分支的语义追问；方案模式有结构化步骤，因此继续采用确定性评估。保存成功后才生成 clarification 则属于**提交后副作用（Post-commit Side Effect）**：对外呈现必须服从持久化事实。

### 当时唯一下一步

做一次真实自由实验录音，确认浏览器最终确实显示追问；自动测试通过不能替代真实体验。

## 15. 性能诊断：为什么第一句回复慢

### 一句话结果

第一条可见反馈慢的主要原因是旧 `/record` 必须串行等待统一理解、完整结构化结果和保存，最近样本仅模型理解就耗时约 3.42～4.73 秒。

### 用户操作发生了什么

用户停止录音
→ 浏览器等待 ASR 转写
→ 浏览器调用旧 `/record`
→ 服务端等待统一理解返回完整 JSON
→ 服务端选择评估并保存记录
→ 服务端生成最终消息和播放事件
→ HTTP 完整返回后页面才第一次更新

### 代码位置

- 桌面录音流程：`web/frontend/voice_asr.js`
- 记录 HTTP 路由：`web/api/record.py`
- 统一理解桥：`web/llm_bridge.py`
- 共享记录事务：`web/record_service.py`
- 模型耗时字段：`llm_seconds`

### 为什么重要

用户感受到的不只是总耗时，还有“等待期间系统完全没有反馈”。即使暂时不能缩短模型计算，也可以先告诉用户系统已经进入理解阶段，避免把正常计算误认为按钮失效。

### 对应的专业知识

这里区分**端到端延迟（End-to-end Latency）**和**首次反馈延迟（Time to First Feedback）**。模型耗时没有下降，但通过提前返回进度事件降低了首次反馈时间。性能优化前先测量各阶段耗时属于**可观测性驱动优化（Observability-driven Optimization）**，避免凭感觉修改错误环节。

### 当时唯一下一步

只增加一条安全的流式处理状态，不尝试把结构化 JSON 和成功回执逐字流出。

## 16. 第 29 项：记录链路流式首反馈

### 一句话结果

录音转写完成后，服务器会先流式发送“正在理解实验内容…”，但最终“已记录”或追问仍然必须等完整分析和保存成功。

### 用户操作发生了什么

用户停止录音
→ ASR 返回转写文本
→ 浏览器显示“正在连接理解服务…”
→ 浏览器请求 `POST /record/stream`
→ 服务端立即发送 `record_status/understanding`
→ 浏览器显示“正在理解实验内容…”
→ 服务端继续执行统一理解和保存
→ 成功后发送 `record_result`
→ 失败时发送 `record_error`，不发送成功结果

### 代码位置

- 流式接口：`web/api/record.py::record_stream()`
- 事件生成：`web/api/record.py::_record_events()`
- 桌面增量读取：`web/frontend/voice_asr.js::streamRecord()`
- 手机增量读取：`web/frontend/mobile.js::postRecord()`
- 流式顺序测试：`tests/test_web_record_messages.py`

### 为什么重要

这一步改善的是首次可见反馈，不是伪造更快的最终结果。提前显示“正在理解”没有数据承诺；提前显示“已记录”却可能在后续保存失败时欺骗用户。

### 对应的专业知识

接口使用的是 **NDJSON 流式协议**：每一行是一个完整 JSON 事件，浏览器用 `ReadableStream` 增量读取，并用行缓冲处理任意网络分片。`record_status` 是**非承诺型进度事件**，`record_result` 是**提交后最终事件**。这不是模型 token streaming；结构化 JSON 仍需完整解析和验证后才能进入业务事务。

### 当时唯一下一步

在真实浏览器录一条内容，只观察状态是否分块到达以及主观等待是否改善，不同时继续做 token 流式或流式 TTS。

## 17. 本段对话的总体关系

整个过程可以压缩成一条主线：

```text
先统一记录业务
→ 再统一工具呈现
→ 把屏幕正文和语音资格拆开
→ 删除旧的直接播报旁路
→ 建立唯一浏览器授权入口
→ 三个入口共用调度
→ 用自动测试冻结职责
→ 真实验收发现自由模式追问丢失
→ 修复追问字段传递和覆盖规则
→ 真实体验发现首次反馈慢
→ 增加安全的流式状态反馈
```

这里最重要的三条工程原则是：

1. 能显示的文字，不等于允许播放的语音。
2. 模型生成了追问，不等于追问已经穿过所有模块到达用户。
3. 可以提前显示处理状态，但成功回执和追问必须服从真实保存结果。

## 当前证据边界

### 已经能够证明

- 第 19～29 项对应的自动测试在各自完成时通过。
- 记录入口已经共享核心业务服务。
- 屏幕正文和语音播放授权已经拆开。
- 已知的 `delta`、`task_queued` 和记录消息直播旁路已受到自动测试保护。
